# 전체 검색 성능 측정 (0.16.0)

전체 검색(일정·할 일·메모·프로젝트·개발 기록)과 검색 인덱스를 갱신하는 저장이 데이터가 늘 때 어떻게 느려지는지 측정하고, 측정으로 확인된 병목만 고친 기록이다. 50ms 같은 목표치는 사전에 정해진 것이 없었고, 아래 판단 기준은 이 작업에서 스스로 정한 것이다.

## 측정 방법

```powershell
. .\scripts\toolchain.ps1
$env:TS_SEARCH_BENCH_SIZES = '1000,10000,50000'   # 생략하면 1000,10000
cargo test --release --locked -p timeschedule-core --test search_perf -- --ignored --nocapture
```

- `crates/timeschedule-core/tests/search_perf.rs`. 기본 테스트에서는 실행되지 않는다(`#[ignore]`).
- 크기마다 `%TEMP%`에 새 DB를 만든다. 앱과 같은 `Storage::open`으로 스키마와 트리거를 만들고, 고정 시드로 만든 한국어 문장을 한 트랜잭션에 넣은 뒤, 앱과 같은 설정(WAL, `synchronous=FULL`)으로 다시 열어 공개 API의 시간을 잰다. 끝나면 DB를 지운다(`TS_SEARCH_BENCH_KEEP=1`이면 남긴다). **사용자 데이터는 읽지 않는다.**
- 항목 구성: 개발 기록 40%(본문 1,500~3,900자), 일정 25%(메모 0~400자), 할 일 25%(상세 0~400자), 메모 10%(300~1,500자). 실제 사용자 DB는 이 작업 시점에 개발 기록 19개(본문 평균 약 2,700자)였다. 사본에서 행 수와 본문 길이만 세고 사본은 바로 지웠다. 1만 항목은 하루 3개씩 약 9년, 5만 항목은 부하 확인용이다.
- 드문 검색어(`견적`, `배포일정점검`)는 기록의 약 0.5%에 들어가도록 넣었다.
- 각 측정은 한 번 데운 뒤 15회 반복한 중앙값·p95·최대다. 저장 시간에는 `synchronous=FULL`의 디스크 반영이 포함된다.
- 측정 PC: 개발 PC(Windows 10, 로컬 SSD), release 빌드, 번들 SQLite. 절대값은 PC·디스크·백그라운드 작업에 따라 달라지므로 같은 PC의 전후 비교로만 읽는다. 5만 항목 DB는 약 550MB다.

## 측정으로 확인한 병목 (수정 전, 0.15.3)

| 측정 (중앙값 ms) | 1천 | 1만 | 5만 |
|---|---:|---:|---:|
| 검색 3글자+ 흔함 `회의록` | 8.9 | 75.9 | 339.7 |
| 검색 3글자+ 드묾 `배포일정점검` | 0.2 | 0.6 | 4.7 |
| 검색 2글자 흔함 `회의` | 10.0 | 96.1 | 430.9 |
| 검색 2글자 드묾 `견적` | 11.3 | 110.3 | 548.5 |
| 검색 2글자 일치 없음 | 10.4 | 109.1 | 535.9 |
| 검색 1글자 `회` | 9.0 | 88.6 | 425.5 |
| 할 일 상세 저장 | 5.6 | 51.9 | 258.5 |
| 비교: 일정 저장 | 0.7 | 0.6 | 0.7 |
| 2글자 검색 중 월 화면 새로 고침 대기 | 7.8 | 89.5 | 445.4 |
| 비교: 검색 없을 때 월 화면 새로 고침 | 0.2 | 1.0 | 8.6 |

원인은 실험(같은 DB의 사본에서 질의만 바꿔 비교)으로 가렸다.

1. **할 일 상세 저장이 항목 수에 비례**했다. 스키마 4의 `task_details` 트리거가 검색 인덱스를 인덱스 없는 열(`kind`, `id`) 조건으로 고쳐 써서, 저장할 때마다 인덱스 전체를 읽었다. 일정·메모 저장은 행 번호로 고쳐 써서 항목 수와 무관했다.
2. **흔한 3글자 검색이 일치 건수에 비례**했다. 1만 항목에서 `회의록` 일치 7,133건을 인덱스로 찾는 데는 0.4ms였다. 나머지 70ms는 최신순 정렬에 쓰는 `updated_at`을 일치한 행마다 읽느라 걸렸다. FTS5는 행을 통째로 읽으므로 긴 본문의 넘침 페이지까지 읽었다.
3. **1~2글자 검색은 전체 본문을 훑는다.** 3글자 인덱스(trigram)를 쓸 수 없기 때문이다. 영문자가 없는 검색어에도 `lower()`로 본문 사본을 만들어 비교했다(SQLite의 `lower()`는 ASCII만 바꾸므로 한국어에는 효과가 없다).
4. **검색이 화면 새로 고침과 저장을 막았다.** 앱의 DB 연결 하나를 잠금으로 함께 써서, 느린 검색이 끝날 때까지 다른 작업이 기다렸다.

## 수정 (스키마 6)

- `search_order` 표(행 번호, `updated_at`, `id`, 최신순 인덱스)를 추가했다. 3글자 이상 검색은 인덱스에서 일치 행 번호만 얻고, 이 작은 표로 정렬해 돌려줄 50개의 본문만 읽는다.
- 1~2글자 검색은 최신 1,000개를 최신순으로 살펴 50개를 채우면 멈춘다. 이 창은 정렬 순서의 앞부분이므로 그 안에서 50개를 찾으면 그것이 정답이다. 50개를 못 채우면 기존처럼 저장 순서대로 전체를 훑는다(최신순 무작위 읽기보다 빠르다). 전체가 1,000개 이하면 처음부터 한 번만 훑는다. 영문자가 없는 검색어는 `lower()`를 쓰지 않는다(결과는 같다).
- 할 일 상세 트리거가 할 일의 행 번호로 인덱스 행을 바로 고친다.
- 검색은 별도 읽기 전용 연결에서 실행한다. WAL에서 읽기 연결은 쓰기를 기다리지 않으므로 검색 중에도 저장·화면 새로 고침이 진행된다. 저장된 내용은 다음 검색에 바로 보인다. `:memory:` DB(테스트)는 연결을 나눌 수 없어 기존 연결을 쓴다.
- 검색 SQL과 트리거 정의를 `crates/timeschedule-core/src/search.rs` 한 곳으로 모았다. 과거 스키마 단계(2, 4)는 이미 만들어진 DB의 이전 결과가 바뀌지 않도록 내용을 그대로 옮기기만 했고, 바꾼 정의는 새 단계(6)에만 있다.

## 남은 한계

- **드물거나 없는 1~2글자 검색어는 여전히 전체를 훑는다**(1만 항목 약 110ms, 5만 항목 약 500ms). 3글자 미만을 인덱스로 찾으려면 2글자 인덱스를 따로 만들어야 하는데, 새 확장·사용자 함수 없이 트리거만으로는 만들 수 없어 이번 범위에서 제외했다. 다만 이제 별도 연결에서 실행되므로 화면 새로 고침과 저장을 막지 않는다.
- 입력이 바뀌어도 이미 시작한 이전 검색은 끝까지 실행된다(결과는 버린다). 검색 취소는 앱 화면 코드 변경이 필요해 이번 범위 밖이다.
- 1천 항목처럼 작은 DB에서는 1~2글자 검색이 기존과 같은 약 10ms다(전체를 한 번 훑는 쪽이 빠르다).
- 흔한 3글자 검색은 여전히 일치 건수에 비례하는 부분(인덱스 목록 읽기와 작은 표 정렬)이 있어 5만 항목에서 약 20ms다.
- 수치는 생성한 문장으로 잰 것이다. 실제 기록의 단어 분포가 다르면 "흔함/드묾"의 경계가 달라진다.

## 자동 테스트

`search.rs`의 테스트는 시간을 재지 않고 결정적인 양을 센다. 할 일 저장·짧은 검색어의 SQLite 명령 실행 수가 항목 수와 함께 늘지 않는지, 3글자 검색이 디스크에서 읽는 페이지 수가 일치 건수와 함께 늘지 않는지를 본다. 수정 전 코드에서는 할 일 저장 18→644, 짧은 검색어 78→1,522(명령 실행 수, 100회 단위), 3글자 검색 420→2,130(페이지)으로 늘었다. 그 밖에 결과 순서(최신순·같은 시각은 ID순·창 경계의 동점), 오래된 일치 찾기, 영문 대소문자, 스키마 5 DB의 이전과 `pre-v6` 백업, 쓰기 연결을 잡은 동안의 검색을 확인한다.
