# 프로젝트 기록

[방향 문서](product-direction.md)의 "순서" 4번 "완료 시 종합"이다. 0.43.0부터 `TimeSchedule.exe record project`가 한 프로젝트의 하루 기록과 그 밖의 기록을 모아 상위 모델을 한 번 불러, 포트폴리오에 쓸 프로젝트 기록을 만든다. 설계는 사용자가 2026-11-26에 승인했다.

- 프로젝트가 끝났을 때 한 번 만드는 것이 기본이다. 완료 전에도 만들 수 있고, 그 기록에는 "완료 전 종합"이라고 남는다.
- 완료로 표시해도 모델을 부르지 않는다. 명령이나 앱의 ‘프로젝트 기록 만들기’ 버튼으로만 만든다.
- 0.44.0부터 앱의 프로젝트 ‘포트폴리오’ 탭에서 만들고, 다이어리에 ‘포트폴리오 초안’ 항목 하나로 보인다(아래 "다이어리 표시", "앱에서 만들기").
- 예전 "채팅에서 경험 검토"와 "백엔드 포트폴리오 · Markdown 생성"은 그대로 둔다(사용자 결정). 프로젝트 기록의 품질을 본 뒤 따로 정한다.

## 명령

```
TimeSchedule.exe record project --project <프로젝트 ID 또는 폴더 경로> [--dry-run] [--model <모델>] [--data-dir <폴더>]
```

| 인자 | 뜻 |
| --- | --- |
| `--project` | 프로젝트 ID 또는 프로젝트 폴더의 절대 경로. 로컬 Git 저장소 경로가 없는 프로젝트는 하루 기록이 없어 만들지 않는다 |
| `--dry-run` | 모델을 부르지 않고 아무것도 쓰지 않는다. 보낼 입력의 크기와 빈 날을 알린다 |
| `--model` | 모델 이름. 기본 `gpt-6.2-astra`. 노력은 `high`로 고정 |

- 다른 `record` 명령의 `--result`도 문서 저장소의 `daily`, `originals`, `project` 폴더 안이면 아무것도 하지 않고 오류로 끝난다. `configure-sync`는 지금 등록된 저장소와 새로 등록할 저장소를 모두 본다. 저장소를 찾지 못하면 이 검사는 하지 않는다.
- 결과는 표준 출력의 JSON 하나다. 읽기 명령처럼 `--result`를 받지 않는다. 이 명령은 DB를 열기 때문에, 결과 파일 경로가 DB나 그 옆 파일을 가리키는 경우를 경로 비교로 다 막을 수 없어서다(아스트라 검토). 파일로 받으려면 `> 결과.json`처럼 셸로 받는다.
- DB는 읽기 전용으로 연다. 앱이 켜져 있어도 된다. DB 형식이 실행 파일과 다르면 읽지 않는다. 0.44.0의 명령은 형식 18만 읽으므로, 형식 17 이하의 DB(0.43.0 이하 앱이 쓰던 DB)는 0.44.0 앱을 한 번 켜서 형식 18로 올린 뒤 실행한다.
- 실행 파일은 창 프로그램이라 PowerShell 창에서 출력을 보려면 `| Out-String`을 붙인다.
- 출력의 `outcome`: `dry_run`, `saved`, `unchanged`(입력이 같아 모델을 부르지 않음), `busy`(다른 실행이 만드는 중, 종료 코드 2), `error`.

`--dry-run`과 모든 실행이 알리는 것:

| 항목 | 뜻 |
| --- | --- |
| `days`, `firstDay`, `lastDay` | 넣은 하루 기록의 날 수와 기간 |
| `records` | 그 밖의 기록 출처별 건수(`agent`, `manual`, `experience`) |
| `citable` | 모델이 근거로 들 수 있는 항목 수. 0이면 모델을 부르지 않는다(항목이 모두 빠진 하루 기록만 있을 때 등) |
| `chars`, `estimatedInputTokens`, `limit`, `tooLarge` | 모델에 보낼 글자 수, 추정 입력 토큰, 한도 20만, 한도를 넘는지 |
| `missingDays` | 보관된 세션에 활동이 있는데 하루 기록이 없는 날의 수와 날짜. 도구 행만 있어 하루 기록을 만들 수 없는 날도 들어갈 수 있다. 보관 폴더가 같은 폴더를 쓰는 다른 프로젝트의 것이면 세지 않고 `warnings`에 적는다 |
| `beforeCompletion`, `completedOn` | 완료 전인지, 완료 날짜 |
| `current` | 지난 기록이 같은 입력으로 만들어졌는지(그러면 모델을 부르지 않는다) |
| `warnings` | 넣지 못한 하루 기록 파일, 대화가 있는 날을 세지 못한 이유 |

## 모델에 주는 것

하루 기록이 중심이고 그 밖의 기록을 보조로 더한다. 채팅 발췌는 넣지 않는다.

- 하루 기록: 문서 저장소 `daily/<프로젝트 폴더>/<날짜>.json`의 최신 판, 날짜순. 다른 프로젝트나 다른 폴더의 파일은 넣지 않고 `warnings`에 적는다.
- 그 밖의 기록: [기록 읽기](record-reading.md)의 `reading` 모듈(`read_whole_records`, 한 번의 조회)로 읽은 출처 `agent`(자동 개발 기록), `manual`(직접 쓴 기록), `experience`(확인한 경험)의 본문 전체. 본문의 줄마다(모든 종류의 줄바꿈을 줄의 끝으로 보고) 앞에 `| `를 붙여, 본문이 묶음의 항목(`[D:…]`)처럼 보이지 않게 한다. `daily`(다이어리에 보인 하루 정리)는 하루 기록 파일과 같은 내용이라 빼고 `chat`은 넣지 않는다.
- 항목마다 근거 열쇠가 붙는다. 하루 기록 항목은 `D:<날짜>:<칸>:<번호>`(칸: 개요, 개발, 트러블, 결정, 남은일. 번호는 1부터), 그 밖의 기록은 `R:<기록 ID>`.
- 하루 기록의 결정 항목은 결정, 이유(없으면 "이유 기록 없음"), 버린 대안, 제안한 쪽, 정한 쪽을 한 줄로 보인다.
- 맨 위에 프로젝트 이름과 상태(‘진행 중’ 또는 ‘완료 · 날짜’)가 있다.

지시문 전문은 `crates/timeschedule-core/src/project_record.rs`의 `INSTRUCTIONS`에 있다(판 1). 독자는 포트폴리오를 보는 사람과 몇 달 뒤의 프로젝트 주인이고, 날짜별 일지가 아니라 프로젝트 단위로 묶어 쓰게 한다. 자료 안의 지시는 따르지 않고, 누가 제안하고 정했는지는 어느 글에도 쓰지 않게 한다.

## 답의 모양

JSON 스키마로 정한다.

| 칸 | 내용 |
| --- | --- |
| `overview` | 프로젝트가 무엇이고 어디까지 왔는지 한 문단 |
| `features` | 만든 기능과 구조(`title`, `detail`) |
| `decisions` | 방향을 정한 결정(`decision`, `reason` 또는 null, `rejected`) |
| `troubleshooting` | 문제(`problem`, `cause`, `fix`, `verification`, 없는 칸은 null) |
| `results` | 검증한 결과와 성과 |
| `limits` | 하지 않은 일, 확인하지 못한 것, 한계 |

모든 항목에 `evidence`(근거 열쇠 목록)가 있다. 결정에는 제안·확정 칸이 없다. 모델에게 이유와 버린 대안은 근거 글에서 글자 그대로 옮기라고 한다.

저장한 결정은 모델의 문장(`decision`)과, 인용한 하루 기록 결정을 그대로 옮긴 `daily` 목록을 함께 지닌다. `daily`의 항목마다 열쇠, 날짜, 결정, 이유, 버린 대안, 제안한 쪽, 정한 쪽이 하루 기록에 있던 그대로 들어 있다. 확인 표시는 이 옮긴 항목에만 붙는다. 모델의 문장 자체에는 확인 표시가 없다.

## 확인 규칙

1. 묶음에 없는 열쇠를 하나라도 들면 답 전체를 버린다(`usage.jsonl`에 `refused`).
2. 근거가 없는 항목은 뺀다(`checks.withoutEvidence`).
3. 결정의 제안한 쪽·정한 쪽은 인용한 하루 기록의 결정 항목을 글자 그대로 옮긴 `daily` 목록에만 있다. 모델이 승인된 결정과 다른 문장을 쓰고 그 결정을 인용해도, 승인은 하루 기록의 원래 문장에만 붙어 보인다(2026-11-26 사용자 승인, 아스트라 검토 뒤 A안).
   - 결정 항목을 하나도 인용하지 않은 결정은 `daily`가 비고 "제안 알 수 없음 · 확인 기록 없음"으로 보인다(`checks.decisionsWithoutDaily`).
   - 처음 승인한 규칙(인용한 결정들의 값이 엇갈리면 "알 수 없음")은 이 방식으로 바뀌어 쓰지 않는다. 결정마다 옮긴 하루 기록 결정이 각자의 값을 지닌다.
4. `results`의 숫자(숫자 덩어리, 숫자 사이의 `.`와 `,`는 한 숫자, 바로 앞의 부호 `-`·`+`·`−`도 숫자에 넣는다. 다만 영문자나 숫자 바로 뒤의 `-`는 부호가 아니다: `2026-11`, `v1-2`)가 인용한 근거 글에 같은 모양으로 없으면 그 항목을 뺀다(`checks.resultsUnsupported`). `0.30`은 `0.3`과, `+3`은 `-3`과 다른 숫자로 본다. 전각 숫자처럼 읽지 못하는 숫자가 있는 결과는 빼고, 근거 글에서 읽지 못하는 숫자가 섞인 숫자 덩어리(`１.25`, `1,２００`)는 통째로 근거로 치지 않는다.
5. 모델이 쓴 이유는 인용한 근거 글(공백 차이는 무시)에 글자 그대로 있을 때만 남긴다. 아니면 null이고 "이유 기록 없음"으로 보인다(`checks.reasonsUnsupported`). 인용한 하루 기록 결정은 그 결정의 이유 칸만 근거로 친다(결정 문장이나 버린 대안의 글은 이유가 아니다). "이유 기록 없음"이라는 글은 공백이 달라도 이유로 치지 않는다.
6. 모델이 쓴 버린 대안도 근거 글에 글자 그대로 있는 것만 남긴다(`checks.rejectedUnsupported`). 인용한 하루 기록 결정은 그 결정의 버린 대안 칸만 근거로 친다. 채택한 결정의 문장이 버린 대안으로 남지 않게 하려는 것이다.
7. 개요처럼 자유롭게 쓴 글에 "사용자가 승인했다" 같은 말이 있는지는 확인하지 못한다. 지시문으로 막는다. 하루 정리와 같은 한계다.

## 저장

`<문서 저장소>/project/<프로젝트 폴더>/<프로젝트 ID>/`. 프로젝트 폴더 이름은 `originals`, `daily`와 같고, 그 아래에 프로젝트마다 자기 폴더를 둔다(0.44.0부터, 0.43.0은 `project/<프로젝트 폴더>/`였다). 0.43.0은 배포하지 않았으므로 옮겨 주는 코드는 두지 않았다. 0.43.0 시험판으로 만든 기록이 `project/<프로젝트 폴더>/record.json`에 있으면, 그 폴더의 `record.json`과 `record.r<N>.json`, `usage.jsonl`을 `project/<프로젝트 폴더>/<프로젝트 ID>/`로 옮기면 판이 이어진다. 옮기지 않으면 새 위치에서 1판부터 다시 만든다. 0.44.0 시험판(커밋 97c2a51)으로 그 기록을 다이어리에 반영해 보았다면 꼭 옮긴다. 다이어리의 수령 기록이 예전 판 번호를 기억하고 있어, 새 위치의 낮은 판은 반영되지 않기 때문이다.
- `project`, 프로젝트 폴더, 프로젝트 ID 폴더를 문서 저장소에서 한 단계씩 열어 링크(정션 포함)가 아닌지 연 폴더로 확인하고, 실행이 끝날 때까지 열어 둔다(0.44.1부터). 기록 파일(`record.json`, `record.r<N>.json`), 잠금 파일(`.record.lock`, `.usage.lock`), 사용량 파일(`usage.jsonl`), 임시 파일은 열어 둔 폴더를 기준으로 이름 하나로 열고 링크를 따라가지 않는다. 하루 정리와 같은 코드(`vault_folder`)이며, 실행 중에 폴더를 옮길 수 없는 것과 문서 저장소 위의 정션이 바뀌어도 따라가지 않는 것도 같다([하루 정리](daily-record.md)). 그래서 0.44.0이 모델을 기다린 뒤 폴더를 경로로 다시 보던 검사는 지웠다. 사용량 파일은 잠금을 얻은 뒤에 연다.
- 묶음을 모을 때(`gather`)는 문서 저장소를 한 번 열고, 거기서 `record.json`과 `daily/<프로젝트 폴더>`의 하루 기록을 모두 읽는다. 다이어리에 프로젝트 기록을 보일 때도 저장소를 한 번 열고, 보이기 직전에 다시 읽는 `record.json`도 같은 저장소에서 읽는다. 대화가 있는 날을 세는 `originals` 읽기는 예전처럼 경로로 읽는다. 묶음을 모으는 것과 기록을 만드는 것은 따로 부르는 일이라 저장소를 따로 연다. 그 사이에 `record.json`이 달라졌으면 만들기가 멈춘다(아래 "맨 먼저 `record.json`을 읽어 둔다").

- `record.json`: 최신 판. `revision`, 모델, 노력, 지시문 판, `completedOn`(만들 때의 완료 날짜, 없으면 "완료 전 종합"), 입력 요약(`input`: 지문, 넣은 하루 기록마다 날짜·판·지문(`daily`)), 사용량, `checks`, 각 칸. 하루 정리를 다시 만들어 `D:` 열쇠가 다른 항목을 가리키게 되어도 `input.daily`의 판으로 읽은 하루 기록(`<날짜>.r<N>.json`)을 찾는다.
- 프로젝트마다 폴더가 따로라서, 한 폴더를 두 프로젝트가 같이 쓰거나 프로젝트를 지우고 같은 폴더로 다시 만들어도 서로의 기록과 이전 판이 부딪히지 않는다. 각자 1판부터 이어 간다. 지운 프로젝트의 기록은 자기 폴더에 그대로 남는다. `record.json`의 프로젝트 ID가 그 폴더의 프로젝트가 아니면(다른 폴더에서 옮겨 온 파일) 모델을 부르지 않고 멈춘다. `--dry-run`도 같은 이유로 오류를 낸다.
- 실행은 맨 먼저 `record.json`을 읽어 둔다. 잠금을 잡았을 때 그 사이 다른 실행이 새 판을 만들어 두었으면, 더 먼저 읽은 입력으로 새 판을 덮지 않도록 멈춘다(입력이 같으면 `unchanged`).
- 프로젝트 이름과 경로도 `record.json`을 읽은 뒤에 다시 읽는다. 그 사이 이름을 바꿨으면 새 이름이 들어가고, 경로를 바꿨으면 다시 실행하라고 멈춘다.
- 완료 날짜는 기록보다 먼저 읽는다. 그 사이 완료로 표시된 프로젝트라면 완료 전에 쓴 기록은 모두 들어간다.
- `record.r<N>.json`: 새 판을 쓰기 전에 이전 판을 옮겨 둔다. 같은 이름의 다른 내용이 있으면 덮어쓰지 않고 멈춘다.
- `.record.lock`: 한 번에 하나의 실행만. 다른 실행이 쥐고 있으면 기다리지 않고 `busy`.
- `usage.jsonl`: 모델을 부를 때마다 한 줄(`saved`, `refused`, `save_failed`, `call_failed`).
- 입력 지문(지시문 판, 모델, 노력, 스키마, 묶음 전체)이 최신 판과 같으면 모델을 부르지 않는다. 완료로 표시하면 묶음 맨 위의 상태가 바뀌므로 다음 실행은 새 판을 만든다.
- 모델을 기다리는 동안 `record.json`이 바뀌면 새 판을 쓰지 않는다. 하루 정리와 같은 코드(`daily_record::record`의 `keep`, `set_aside`, `log_usage`)를 쓴다.

## 다이어리 표시

0.44.0부터 앱이 `record.json`을 다이어리 항목으로 보여 준다. 하루 정리의 [다이어리 표시](daily-record.md)와 같은 규칙을 프로젝트 단위로 쓴다.

- 로컬 Git 저장소 경로(절대 경로)가 있는 프로젝트마다 `project/<프로젝트 폴더>/<프로젝트 ID>/record.json`만 읽는다. 기록을 만들 때도 절대 경로를 요구한다. 남겨 둔 판, 사용량 기록, 잠금 파일은 읽지 않는다. 채팅 수집을 켰는지와 관계없다.
- 프로젝트와 폴더(`repoKey`)마다 항목 하나다. 종류 ‘포트폴리오 초안’(`portfolio`), 제목 ‘프로젝트 기록 · <이름>’(다이어리 제목 한도 200자에 맞게 이름을 자른다), 날짜는 그 판을 만든 날(한국 시각), 출처 표시는 `project-record:<프로젝트 ID>:<폴더>`다. [기록 읽기](record-reading.md)에서는 출처 `other`로 보이고, 프로젝트 기록의 입력(`agent`, `manual`, `experience`)에는 다시 들어가지 않는다.
- 본문은 첫 줄 "완료 전 종합" 또는 "완료 · 2026-12-01", 그 아래 `## 개요`, `## 기능`, `## 결정`, `## 트러블슈팅`, `## 결과`, `## 한계`다. 빈 칸은 제목도 쓰지 않는다. 결정마다 모델의 문장, "이유: …"(없으면 "이유 기록 없음"), 남은 버린 대안, 그리고 "하루 기록의 결정:" 아래 인용한 하루 기록의 결정을 "- 2026-11-20 [제안 AI · 사람 승인] <하루 기록의 원래 문장> (버린 대안: …)"으로 옮긴다. 하루 기록의 결정을 인용하지 않은 결정은 "확인: 제안 알 수 없음 · 확인 기록 없음"이다. 누가 제안하고 정했는지는 이 줄들에만 있다. 모델이 쓴 글(결정 문장, 이유, 기능, 결과 등)과 옮긴 하루 기록의 글에 든 대괄호 `[` `]`는 `(` `)`로 바꿔 보인다. 모델이 `[제안 AI · 사람 승인]` 같은 표시를 글에 써도 프로그램이 붙인 확인 표시처럼 보이지 않게 하려는 것이다. 근거 열쇠, `checks`, 판 번호와 모델은 본문에 쓰지 않고 `record.json`에 남는다.
- 본문이 다이어리 한도(100,000자)를 넘으면 앞부분만 넣고 끝에 전체가 `project/<폴더>/<프로젝트 ID>/record.json`에 있다고 적는다.
- DB의 새 표 `project_record_entries`에 프로젝트와 폴더마다 수령 기록을 남긴다. 어느 항목에 보여 주었는지, 그 항목에 마지막으로 넣은 날짜와 본문, 마지막으로 본 판 번호와 지문이다. 이 표는 항목을 가리키는 외래 키가 없어서 항목을 지워도 남는다.
- 판 번호가 수령 기록보다 높은 기록이 오면, 그 항목이 아직 그 프로젝트에, 프로그램이 마지막으로 넣은 날짜에, 그 본문 그대로 있을 때만 본문을 새 판으로 바꾸고 날짜를 새 판을 만든 날로 옮긴다(`updated`). 제목이나 종류만 고친 항목은 그 값을 두고 본문과 날짜를 바꾼다.
- 그 밖에는 사용자의 항목이다. 본문을 고쳤거나, 다른 날짜나 프로젝트로 옮겼거나, 지웠으면 어떤 값도 바꾸지 않고 다시 만들지도 않는다(`kept`). 수령 기록에는 그 판을 보았다는 것만 적는다. 판 번호와 지문이 같은데 본문이나 만든 날이 달라졌으면(앱을 새로 받아 보여 주는 형식이 바뀐 경우, `record.json`을 지우고 같은 입력으로 다른 날 다시 만든 경우) 같은 조건으로 본문과 날짜를 바꾼다. 판 번호가 수령 기록보다 높지 않으면 반영하지 않는다(`older`).
- 기록의 `project.repoKey`가 프로젝트의 지금 폴더와 다르면 보여 주지 않고 `otherFolder`로 센다. 같은 폴더를 쓰는 프로젝트는 각자 자기 기록을 보인다. 기록 파일의 프로젝트 ID가 그 폴더의 프로젝트와 다르면(옮겨 온 파일) 실패로 센다. 쓰기 직전에 같은 트랜잭션 안에서 프로젝트의 폴더가 그대로인지, `record.json`이 읽은 것과 같은지 다시 본다. 그 사이 다른 반영이 새 판을 보여 주었으면 먼저 읽은 예전 파일로는 아무것도 쓰지 않는다.
- 이 표를 더하느라 DB 형식이 17에서 18로 올랐다. 형식이 낮은 DB를 열 때 먼저 `schedule.pre-v18-<UUID>.db`로 백업한다. 0.43.0 이하 배포판은 형식 18인 DB를 열지 않는다.
- 언제 반영하나: 앱의 버튼으로 만든 직후, 그리고 채팅 수집 때마다(하루 기록 반영과 같은 자리). 명령으로 만든 기록은 다음 채팅 수집 때 나타난다. `record scan-local-chats` 출력의 `project`(`added`, `updated`, `kept`, `unchanged`, `older`, `otherFolder`, `failed`)에 결과가 나온다. 반영한 항목이 있으면 알림 줄에 "프로젝트 기록 N건을 다이어리에 반영했습니다.", 실패가 있으면 오류 줄에 나온다.
- 채팅 수집을 켠 프로젝트가 하나도 없어도 문서 저장소를 찾아 프로젝트 기록을 보여 준다. 그때 문서 저장소를 찾지 못하면 오류로 보지 않고 보여 줄 것이 없는 것으로 센다.

## 앱에서 만들기

프로젝트 화면의 ‘포트폴리오’ 탭 맨 위에 있다(화면은 [화면별 명칭표](ui-names.md)의 "프로젝트 기록 만들기 영역").

- 로컬 Git 저장소 경로(절대 경로)가 없는 프로젝트에는 버튼 대신 "로컬 Git 저장소 경로를 넣으면 프로젝트 기록을 만들 수 있습니다"가 나온다.
- **언제 누르나(0.44.2부터).** 진행 중인 프로젝트는 버튼 아래에 "진행 중에 만들면 ‘완료 전 종합’이 됩니다. 프로젝트가 끝나면 ‘완료로 표시’한 뒤 다시 만들어 최종본으로 쓰세요."가 나온다. 완료한 프로젝트에서는 버튼 이름이 ‘최종 프로젝트 기록 만들기’다. 완료한 프로젝트의 정보 줄(‘● 완료 · 날짜’ 아래)에는 "프로젝트를 완료했습니다. 최종 프로젝트 기록을 만들어 두세요."와 ‘최종 기록 만들기’ 버튼이 나온다. 누르면 이 탭으로 옮겨 아래의 확인부터 한다. 이 줄은 `record.json`의 `completedOn`이 프로젝트의 완료 날짜와 같아지면(그 완료로 기록을 만들면) 사라진다. 다른 날 다시 완료하면 다시 나온다. 앱은 화면을 새로 읽을 때 연 프로젝트 하나만, 완료 여부와 관계없이 그 프로젝트 폴더의 `record.json`을 읽는다(`project_record::kept_completion`, 읽기만 하고 다른 프로젝트의 파일이면 오류). 진행 중일 때도 읽어 두므로 최종본을 만든 뒤 ‘진행 중으로’ 되돌렸다가 같은 날 다시 완료해도 줄이 나오지 않는다. 그 프로젝트의 화면을 다 읽기 전(막 옮겨 온 때, 기록을 막 만든 때)에는 줄을 보이지 않는다. 저장소를 찾지 못하거나 읽지 못하면 기록이 없는 것으로 보고 줄을 보인다. 완료로 표시해도 모델은 부르지 않는다는 규칙은 그대로다.
- **확인.** ‘프로젝트 기록 만들기’를 누르면 모델을 부르지 않고 `--dry-run`과 같은 묶음을 읽는다("프로젝트 기록 입력 확인 중…"). 끝나면 "하루 기록 3일 · 그 밖의 기록 70건 · 추정 입력 약 8.8만 토큰 · gpt-6.2-astra", 하루 기록이 없는 대화 날(처음 5개와 나머지 수), 묶음의 경고(3개까지), "완료 전 종합으로 만듭니다" 또는 "완료(12월 1일) 뒤 종합으로 만듭니다"를 보인다.
- **묻기.** ‘만들기’를 눌러야 모델을 부른다. ‘취소’는 아무것도 하지 않고 닫는다. 근거로 들 것이 없거나 추정 입력이 한도를 넘으면 이유를 보이고 ‘만들기’를 두지 않는다. 지난 기록과 입력이 같으면 "지난 기록과 입력이 같아 모델을 부르지 않습니다"를 보이고 ‘만들기’를 두지 않는다.
- **만들기.** "프로젝트 기록 만드는 중… (몇 분 걸릴 수 있습니다)". 묶음은 이때 다시 읽는다. 확인한 뒤 몇 분이 지났을 수 있어서다. 확인 때 읽은 폴더를 기억해 두었다가, 그 사이 프로젝트의 폴더가 바뀌었으면 모델을 부르지 않고 다시 확인하라고 적는다. 모델이 답한 뒤 저장하기 직전에도 프로젝트가 아직 있고 폴더가 그대로인지 본다(`project_record::holds`, 명령도 같다). 아니면 저장하지 않는다. 지운 프로젝트의 기록이 남아 같은 폴더의 다음 프로젝트가 기록을 만들지 못하게 되는 일을 막는다. 이 확인과 파일 저장 사이의 아주 짧은 틈에 프로젝트를 지우거나 폴더를 바꾸면 기록이 남을 수 있다(DB와 파일을 함께 잠그지 않는다). 남아도 지운 프로젝트 자기 폴더(`project/<폴더>/<그 프로젝트 ID>/`)에 남을 뿐이라, 같은 폴더의 다른 프로젝트는 막히지 않는다. 명령과 같은 함수(`record_project::summarize_project`)로 만들고, 끝나면 바로 다이어리에 반영한다. "프로젝트 기록을 만들었습니다(판 N). 다이어리에 ‘프로젝트 기록 · 이름’으로 보입니다."처럼 결과를 적는다. 결과 문장은 그 프로젝트의 기록만 반영한 결과로 정한다(`import_project_record`). 새 항목이면 그 제목을, 이미 있던 항목을 바꿨으면 "다이어리의 프로젝트 기록 항목을 새 판으로 바꿨습니다."를 적는다(사용자가 제목을 고쳤을 수 있다). 다이어리 항목을 사용자가 고쳤거나 옮겼거나 지웠으면 그렇다고 적는다. 실패하면 이유를 적는다.
- 한 번에 한 프로젝트만 확인하거나 만든다. 다른 프로젝트의 것이 도는 동안 버튼은 눌리지 않는다. 이 작업은 앱의 작업 중 표시(`busy`)를 쓰지 않는다. 몇 분 걸리는 동안 다른 기록을 저장할 수 있어야 하고, 하루 정리와는 읽고 쓰는 파일이 달라서다. 앱을 닫을 때 만드는 중이면 끝난 뒤 닫는다.
- 단일 실행 잠금을 쥔 앱만 만든다. 확인은 읽기만 한다.
