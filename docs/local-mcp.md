# 로컬 일정 MCP (0.10.1)

TimeSchedule을 실행하면 같은 Windows PC의 ChatGPT Desktop·Codex·Claude Code·Claude Desktop이 공통 일정 도구를 사용할 수 있다. 앱의 SQLite에 직접 저장하며 앱·위젯·열린 빠른 일정 목록에 다음 500ms 갱신 시점부터 반영한다. 저장 중인 작업이나 UI 부하에 따라 화면 반영은 늦어질 수 있다. 모델 실행·외부 전송·Space 호출은 MCP 자체에 포함되지 않는다.

## 연결 상태 확인 (0.14.0)

**MCP 끄기**를 누르면 해당 데이터 폴더의 서버와 Claude Desktop 중계가 종료된다. 앱과 Claude를 다시 실행해도 끄기 선택이 유지된다. EXE를 교체할 때는 TimeSchedule도 트레이에서 완전히 종료한다. **MCP 켜기**를 누르면 서버가 다시 시작된다. Claude에서 MCP를 재연결하거나 Claude를 다시 열면 기존 등록으로 접속한다.

**설정 → AI 연결 (MCP)**의 맨 위에 서버 상태(초록 = 실행 중, 빨강 = 꺼짐·시작 실패)가 있고, 그 아래 **연결 상태**판이 AI 앱별로 한 줄씩 보여준다. Codex와 ChatGPT Desktop은 같은 설정 파일을 쓰므로 한 줄이다.

| 표시 | 뜻 | 할 일 |
| --- | --- | --- |
| 연결됨 (초록) | 등록이 맞고, 그 AI 앱이 실제로 접속한 기록이 있다. 마지막 접속 시각과 앱이 보낸 이름·버전을 함께 보여준다 | 없음 |
| 등록됨 (노랑) | 설정 파일의 등록은 맞지만 아직 접속 기록이 없다 | AI 앱을 다시 시작하거나 MCP 서버를 다시 불러온다 |
| 재등록 필요 (빨강) | 등록이 있지만 지금 앱이 쓸 내용과 다르다. 0.13.1 이전 형식이거나 앱 위치·데이터 폴더·포트가 바뀌었다 | `다시 등록` → 아래 도우미의 `등록 적용` |
| 미등록 (회색) | 이 PC의 그 앱 설정에 `timeschedule`이 없다 | `등록 준비` → `등록 적용` |
| 확인 실패 | 설정 파일을 읽지 못했다(형식 오류 등). 이유를 함께 보여준다 | 파일을 확인한 뒤 `다시 확인` |
| 서버 꺼짐 | TimeSchedule의 MCP 서버가 꺼져 있어 비교할 수 없다 | 위 서버 상태를 확인하고 `MCP 켜기`를 누른다 |

- 설정 화면을 열 때, 등록·검사가 끝났을 때, `새로 고침`을 누를 때 각 AI 앱 설정 파일을 **읽기만** 해서 다시 확인한다. 화면 작업과 분리해 처리한다. Claude Desktop은 아래 "Claude Desktop 설정 위치"의 규칙으로 실제로 사용 중인 설정 파일 하나를 골라 확인한다.
- 행의 `등록 준비`·`다시 등록`은 아래 도우미에 그 앱의 미리보기를 띄울 뿐이다. 실제 저장은 미리보기를 확인한 뒤 `등록 적용`으로 한다.
- **접속 기록**: AI 앱은 연결을 시작할 때 자기 이름과 버전을 보낸다(MCP `initialize`). 인증을 통과한 요청에서만 그 이름·버전·시각을 기록하고, TimeSchedule 자신의 연결 검사는 제외한다. 앱을 다시 켜도 보이도록 데이터 폴더의 `mcp-clients.json`에 최대 16개를 저장하며 일정 내용·토큰·요청 본문은 남기지 않는다. 파일을 지우면 기록만 사라진다.
- 이후 도구 호출에는 앱 이름이 담기지 않으므로 "마지막 접속"은 AI 앱이 **연결을 시작한 시각**이다. 오래 켜 둔 AI 앱은 실제로는 더 최근에 도구를 썼을 수 있다.
- 0.14.0으로 업데이트하기 전부터 연결되어 있던 AI 앱은 기록이 없으므로 `등록됨`으로 보인다. AI 앱을 한 번 다시 시작하면 `연결됨`으로 바뀐다.
- 어느 줄에도 해당하지 않는 이름(다른 MCP 클라이언트)은 추측하지 않고 상태판 아래 `그 밖의 접속`에 이름 그대로 보여준다. AI 앱이 예상과 다른 이름을 보내 엉뚱한 줄이나 `그 밖의 접속`에 나타나면 그 이름을 알려 주면 연결 규칙을 고칠 수 있다.
- 여러 AI 앱이 동시에 연결해도 된다. 서버는 하나이며 연결 16개·동시 요청 8개까지 처리한다.

## 인증 토큰 재발급과 손상 복구 (0.15.0)

**설정 → AI 연결 (MCP) → 인증 토큰**에서 토큰을 바꿀 수 있다. 토큰이 다른 곳에 노출됐다고 의심될 때 쓴다.

1. `토큰 재발급`을 누르면 무엇이 끊기는지 안내가 나오고 버튼이 `취소`·`재발급 확인`으로 바뀐다. 이때까지는 아무것도 바뀌지 않는다.
2. `재발급 확인`을 누르면 새 토큰을 저장하고 실행 중인 서버에 바로 적용한다. 앱을 다시 시작할 필요가 없다.
3. 결과가 같은 칸에 표시된다. 등록·연결 검사가 진행 중일 때는 버튼이 꺼져 있다.

| 연결 방식 | 재발급 후 |
| --- | --- |
| 도우미로 등록한 Codex·ChatGPT Desktop·Claude Code | 다시 연결할 때 도우미가 새 토큰을 내준다. AI 앱이 이전 토큰을 들고 있는 동안의 요청은 401로 거절되므로, 연결이 끊겨 보이면 AI 앱에서 MCP 서버를 다시 불러오거나 앱을 다시 시작한다. 다시 등록할 필요는 없다 |
| Claude Desktop (중계) | 요청마다 토큰 파일을 다시 읽으므로 그대로 동작한다 |
| 연결 검사 | 그대로 동작한다 |
| 환경변수에 토큰을 넣은 예전 수동 연결 (`mcp-session.ps1`, `-PersistToken`) | **끊긴다.** `scripts/mcp-session.ps1`을 다시 실행하고(`-PersistToken`을 썼다면 그 옵션으로), AI 앱을 새로 시작한다 |

- 이전 토큰은 재발급이 끝난 순간부터 거절된다. 이전 토큰으로 이미 열려 있던 연결의 다음 요청도 401이다. 이미 처리 중이던 요청 한 건은 끝까지 처리된다.
- 서버가 꺼져 있을 때 재발급하면 토큰 파일을 갱신한다. 다음에 **MCP 켜기**를 누르면 새 토큰으로 연결된다.
- 재발급에 실패하면 이전 토큰이 파일과 서버 양쪽에 그대로 남는다. 다른 프로그램이 `mcp-token.dpapi`를 잡고 있으면 약 0.2초 동안 다시 시도한 뒤 실패로 알린다.
- 재발급은 그 데이터 폴더를 차지한(먼저 실행한) TimeSchedule에서만 된다. 같은 폴더로 나중에 띄운 두 번째 창에는 서버가 없다. 거기서 파일만 바꾸면 첫 번째 앱의 서버는 이전 토큰을 계속 받고 도우미는 새 토큰을 읽어 어긋나므로, 두 번째 창의 재발급은 거절되고 아무것도 바뀌지 않는다.

**시작할 때의 손상 복구.** 앱은 시작할 때 `mcp-token.dpapi`를 읽는다. 다음 경우는 기다려도 고쳐지지 않으므로 새 토큰을 발급하고, 인증 토큰 칸에 "시작할 때 인증 파일을 읽을 수 없어 새 토큰으로 바꿨습니다"라고 표시한다. 쓸 수 없던 파일은 새 파일로 교체되고 사본을 남기지 않는다. 직접 붙여 넣은 평문 토큰처럼 무엇이 들어 있을지 알 수 없기 때문이다. 판정 사유(빈 파일, 크기 초과, 복호화할 수 없음, 다른 PC·Windows 계정의 키, 토큰 형식 아님)만 데이터 폴더의 `native.log`에 한 줄 기록한다.

- 파일이 비어 있다(만들다가 꺼짐) / 16KiB를 넘는다
- Windows가 복호화를 "데이터가 잘못됨"(잘림·깨짐) 또는 "매개 변수가 틀림"(너무 짧음)으로 거절했다
- Windows가 "지정된 상태에서 사용할 수 없는 키"로 거절했고, 일반 로컬 프로필로 로그인한 상태이며, 파일이 가리키는 보호 키가 그 프로필(`%APPDATA%\Microsoft\Protect`)에 없다. 다른 PC·Windows 계정에서 복사한 파일이 이렇다
- 복호화한 내용이 64자리 16진수 토큰이 아니다

반대로 **파일이 멀쩡할 수 있는 오류에서는 토큰을 바꾸지 않는다.** 접근 거부, 다른 프로그램이 파일을 잡고 있음, 읽기 오류, 그 밖의 Windows 보호 기능 오류는 서버 상태에 `시작하지 못함`과 사유로 표시된다. "사용할 수 없는 키" 오류인데 그 키가 이 프로필에 있거나(이 계정의 키를 Windows가 잠시 못 쓰는 상태일 수 있다) 있는지 판단할 수 없을 때도 같다. Windows가 프로필을 불러오지 못해 임시 프로필로 로그인시킨 경우, 그리고 로밍·필수 프로필에서는 키가 지금 이 자리에 없을 뿐일 수 있으므로 키가 없어도 손상으로 보지 않는다. 정상적으로 다시 로그인하면 같은 토큰을 그대로 쓴다. 원인을 해결하고 앱을 다시 실행한다. 그래도 해결되지 않으면 `토큰 재발급`으로 파일을 바꾼 뒤 앱을 다시 실행할 수 있다. AI 앱 도우미와 Claude Desktop 중계는 파일을 읽기만 하고, 손상을 발견해도 바꾸지 않고 오류만 돌려준다.

**저장 방식.** 토큰 파일은 처음 만들 때와 바꿀 때 모두 같은 폴더에 `mcp-token.dpapi.<난수>.tmp`로 새 내용을 쓰고 디스크에 내린 다음 이름을 바꿔 한 번에 교체한다. 쓰는 도중 전원이 꺼지면 이전 파일이 그대로 남고(임시 파일은 다음 시작 때 지운다), 교체가 끝났으면 새 파일이 남는다. 반쯤 쓰인 토큰 파일은 생기지 않는다. 교체 순간에 파일을 읽고 있던 도우미는 자기가 연 이전 파일을 끝까지 온전히 읽는다. 그 토큰으로 한 서버 확인이 어긋나면 도우미는 토큰을 한 번 더 읽고, 바뀌었을 때만 한 번 더 확인한다. 교체되는 순간 Windows가 파일 열기를 잠깐 거절하면 최대 0.1초 동안 몇 번 다시 읽는다(0.15.2).

한계: 이름 바꾸기로 한 번에 교체되는 것은 NTFS와 Windows 10 1607 이상 기준이다. 관리자가 Windows 계정 비밀번호를 강제로 바꾼 경우처럼 보호 키가 프로필에 남아 있지만 영영 쓸 수 없게 된 파일은 자동으로 바꾸지 않으므로 `토큰 재발급` 후 앱을 다시 실행해야 한다. 키가 프로필에 있는지는 Windows가 공식 문서로 보장하지 않는 파일 머리말 형식과 키 파일 위치로 확인하며, 형식이 예상과 다르면 판단하지 않고 토큰을 바꾸지 않는다. 재발급은 같은 Windows 계정으로 실행되는 프로그램이 새 토큰 파일을 복호화하는 것을 막지 못한다. 토큰이 어떻게 노출됐는지는 알려 주지 않으며, 접속 기록(`mcp-clients.json`)에서 낯선 이름을 확인할 수 있을 뿐이다. 환경변수에 평문으로 저장해 둔 이전 토큰은 자동으로 지우지 않는다.

## 설정에서 연결하기 (권장)

1. 대표 EXE를 실행하고 **설정 → AI 연결 (MCP) → AI 연결 도우미**로 이동한다.
2. ChatGPT Desktop, Codex, Claude Code, Claude Desktop 중 사용할 앱을 선택한다. `경로 찾기`로 설정 위치를 찾거나 실제 설정 파일의 절대 경로를 입력한다. 이 기능은 AI 앱을 설치하지 않는다.
3. `등록 미리보기`에서 대상 파일, 추가/갱신 여부, 서버 주소와 인증 방법을 확인한다.
4. `등록 적용`을 누른다. 같은 Windows 사용자의 전체 프로젝트에서 쓰는 `timeschedule` 연결을 등록한다. 다른 서버와 기존 도구 제한·활성화 여부는 보존한다.
5. AI 앱에서 연결을 다시 불러오거나 앱을 재시작한 뒤 `timeschedule` 도구를 확인한다. 클라이언트의 신뢰·도구 사용 승인은 해당 앱에서 처리한다.
6. TimeSchedule의 `연결 검사`는 서버 초기화·인증·도구 4개와 등록 설정을 검사한다. 개인 일정 조회·추가·수정이나 모델 호출은 하지 않는다. AI 앱이 설정을 실제로 불러왔는지는 해당 앱에서도 확인한다.

ChatGPT Desktop과 Codex는 `%USERPROFILE%\.codex\config.toml` 또는 `CODEX_HOME`의 `config.toml`, Claude Code는 `%USERPROFILE%\.claude.json` 또는 `CLAUDE_CONFIG_DIR`의 `.claude.json`을 사용한다. Claude Desktop은 아래 "Claude Desktop 설정 위치"를 참고한다.

**Claude Desktop 설정 위치 (0.14.0 수정).** Claude Desktop은 자기 데이터 폴더의 `claude_desktop_config.json`만 읽는다. 일반 설치는 `%APPDATA%\Claude`, Microsoft Store 설치는 `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude` 또는 `%LOCALAPPDATA%\Claude-Data\claude_*`를 쓴다. Store 설치는 `%APPDATA%\Claude`를 패키지 폴더로 연결해 두기도 하므로, 같은 폴더로 이어지는 경로는 한 곳으로 본다. Claude Desktop은 실행한 적 있는 폴더에 `lockfile`·`config.json`을 남기고, 실행 중에는 `lockfile`을 다른 프로그램이 열 수 없게 잡고 있다. 그래서 지금 실행 중인 폴더가 하나면 그 폴더를, 아니면 실행 흔적이 있는 폴더가 하나일 때 그 폴더를 쓴다. 실행 흔적이 있는 폴더가 여럿이면 임의로 고르지 않고, 도우미가 경로를 직접 입력하라고 안내한다. Claude Desktop을 켜 둔 채로 설정 화면을 열면 가장 확실하게 찾는다. 한계: 잠금은 누가 잡고 있는지 알려 주지 않으므로 백신·백업 프로그램이 같은 파일을 잠시 잡고 있으면 잘못 판단할 수 있다. 등록 전에 미리보기에 표시되는 대상 경로를 확인한다. 0.14.0 초기 빌드는 `Claude-Data` 폴더를 몰라서, 이 위치를 쓰는 PC에서는 Claude Desktop이 읽지 않는 파일에 등록하고 상태판에 `등록됨`으로 잘못 표시했다. 이 경우 수정된 빌드에서 상태판이 `미등록`으로 바뀌며, `등록 준비` → `등록 적용`으로 올바른 파일에 다시 등록하면 된다. Claude Desktop의 설정 → Developer → Edit Config에서 실제 경로를 확인한다.

ChatGPT Desktop과 Codex는 **같은 로컬 호스트의 설정 파일을 공유**한다. 둘 중 하나로 이미 등록했다면 같은 경로·실행 파일·데이터 폴더·주소의 등록은 중복 생성하거나 재작성하지 않는다. 미리보기에서 두 앱에 함께 적용되는 범위를 확인한다. ChatGPT에서 **Settings → MCP servers → Restart**로 다시 불러온 뒤 `/mcp`에서 `timeschedule`을 확인한다. 로컬 MCP를 지원하는 최신 데스크톱 앱 기준이며, ChatGPT 웹이나 클라우드 실행은 이 로컬 설정을 사용하지 않는다. 원격 호스트를 선택했다면 해당 호스트에 TimeSchedule과 연결 설정이 있어야 하며 이 PC의 `127.0.0.1`에 연결되는 것으로 해석하지 않는다.

ChatGPT Desktop·Codex·Claude Code는 최신 버전의 `http_headers_helper` / `headersHelper`를 사용한다. 연결 시 숨겨진 PowerShell이 같은 EXE의 `--mcp-auth-headers`를 실행하고 바로 종료한다. 설정에 토큰 값을 넣지 않으며 사용자 환경변수에도 저장하지 않는다. 이전에 수동으로 저장한 환경변수는 자동 삭제하지 않는다. Claude Desktop은 같은 EXE의 `--mcp-stdio`를 실행하여 인증된 로컬 HTTP로 중계한다. 연결 중 작은 중계 프로세스 하나가 대기하며 일정 DB나 두 번째 GUI를 열지 않는다. 앱이 완전히 종료되면 도구 호출은 실패한다.

**토큰을 보내기 전 서버 확인 (0.13.1).** 도우미·중계·연결 검사는 토큰을 내보내기 전에 대상 포트에 `GET /proof`를 보내, 상대가 같은 토큰을 이미 알고 있는지 확인한다. 요청마다 새로 만든 64자리 16진수 난수를 `TimeSchedule-Challenge` 헤더로 보내면 서버는 `TimeSchedule MCP server proof v1`, 자신의 `주소:포트`, 그 난수를 줄바꿈으로 이은 문자열을 토큰으로 HMAC-SHA256 서명한 값만 답한다. 토큰 자체는 전송하지 않는다. 앱이 꺼져 있거나, 다른 프로세스가 포트를 차지했거나, 다른 포트의 응답을 중계한 경우에는 값이 일치하지 않아 토큰을 보내지 않고 오류를 반환한다. 앱이 비정상 종료해 `mcp-status.json`이 남아 있어도 같다.

ChatGPT Desktop·Codex·Claude Code는 도우미가 출력한 토큰을 **자기 설정 파일의 주소**로 보낸다. 도우미는 그 설정을 볼 수 없으므로, 새 도우미 명령은 등록한 주소를 `--endpoint`로 전달하고 그 주소만 확인한다. **0.13.1 이전에 등록한 설정에는 이 인자가 없어 토큰이 갈 곳을 확인할 수 없다. 이 경우 도우미는 토큰을 출력하지 않고 재등록 안내 오류를 반환하므로, 업데이트 후 연결 도우미에서 등록 미리보기 → 등록 적용을 한 번 다시 실행한다.** 0.14.0의 연결 상태판은 이전 등록을 `재등록 필요`로, 연결 검사는 `다시 등록하세요`로 표시한다. 포트를 바꾼 뒤에도 다시 등록한다. Claude Desktop의 중계는 `mcp-status.json`의 주소를 스스로 확인하고 그 주소로만 보내므로 다시 등록할 필요가 없다.

Claude Desktop 중계와 연결 검사는 확인에 사용한 **바로 그 연결**로 토큰이 담긴 요청을 보낸다. 확인 뒤 앱이 종료되고 다른 프로세스가 포트를 차지해도 그 연결은 새 프로세스로 넘어가지 않으므로 요청이 실패할 뿐 토큰은 전달되지 않는다.

이 확인의 한계: 도우미가 출력한 토큰은 AI 앱이 별도 연결로 보내고, `mcp-session.ps1 -Status`도 확인과 전송에 서로 다른 요청을 쓴다. 이 두 경로는 확인 직후 앱이 종료되고 그 사이 다른 프로세스가 같은 포트를 여는 짧은 순간을 막지 못한다. 같은 Windows 계정으로 실행되는 프로그램은 DPAPI 파일을 직접 복호화할 수 있으므로 보호 대상이 아니다. 유출이 의심되는 토큰은 위 "인증 토큰 재발급"으로 교체한다(0.15.0).

같은 이름의 프로젝트 설정이나 관리자가 정한 제한이 사용자 설정보다 우선할 수 있다. 등록이 정상이더라도 AI 앱에서 꺼진 연결·상위 정책·프로젝트별 중복 항목은 별도로 확인한다. 설정 도우미는 이 제한을 해제하지 않는다.

**기존 설정 파일을 바꾸는 방식 (0.15.1).** 기존 파일을 제자리에서 고쳐 쓰지 않는다. 같은 폴더에 새 내용을 `<파일 이름>.timeschedule-UUID.tmp`로 끝까지 쓰고 디스크에 내린 다음, 이름을 바꿔 원래 파일과 한 번에 교체한다. 그래서 등록 도중 앱이 강제 종료되거나 전원이 꺼져도 설정 파일 이름은 이전 내용 전체 또는 새 내용 전체 중 하나를 가리키고, 잘리거나 섞인 파일은 생기지 않는다. 0.15.0까지는 제자리에서 덮어썼기 때문에 그 순간 꺼지면 `~/.claude.json`·`config.toml`이 깨질 수 있었다.

- 미리보기 이후 변경된 파일과 다른 프로그램이 열고 있는 파일은 거절한다. 내용을 비교한 때부터 교체할 때까지 파일을 잡고 있어서 그동안 다른 프로그램은 이 파일을 읽거나 제자리에서 고쳐 쓸 수 없다. 그 사이 다른 프로그램이 자기 새 파일로 이름을 바꿔 교체했거나, 파일을 옮기고 그 자리에 링크를 두었거나, 파일에 두 번째 이름(하드 링크)을 붙였거나, 사용자가 설정 파일 자리에 둔 심볼릭 링크가 다른 파일을 가리키게 바뀌었거나, 원본의 접근 권한·레이블이 바뀌었다면(예: 그 사이 본인만 접근하도록 막음) 알아채고 등록을 중단하며 그 프로그램이 해 둔 것은 그대로 둔다.
- 새 파일은 원래 파일의 접근 권한을 그대로 갖는다. 폴더의 권한을 물려받던 파일은 계속 물려받고, 본인만 접근하도록 따로 막아 둔 파일은 똑같이 막힌다. 폴더 권한에 자기 규칙을 더해 둔 파일은 규칙은 그대로 유지하되 이후로는 폴더 권한을 물려받지 않는다. 낮은 무결성 수준의 프로그램을 막는 무결성 레이블(예전 폴더에서 물려받은 것 포함), EFS 암호화(등록한 계정 기준), 숨김·시스템 표시도 유지한다. 백업에도 같은 권한·레이블·암호화를 적용한다. 새 파일과 백업은 **내용을 쓰기 전에** 실제로 원본과 같은 권한·레이블·암호화를 갖게 됐는지 확인하고, 다르면 빈 파일을 지우고 등록하지 않는다.
- 파일을 교체하려면 그 파일을 지울 권한이 필요하다. 읽고 쓸 수는 있지만 지울 수 없는 파일은 아무것도 쓰기 전에 거절한다. 이런 곳에 백업이나 작업 파일을 만들면 다시 지울 수 없어 시도할 때마다 설정 사본이 쌓이기 때문이다.
- 교체에 실패하면(읽기 전용 파일, 교체를 막는 다른 프로그램 등) 원본은 그대로이고, 이번 시도에서 만든 백업과 작업 파일은 지운다. 이번 시도가 만들지 않은 파일은 지우지 않는다. 지우지 못한 사본이 있으면 오류 메시지에 그 경로를 표시한다.
- 중단된 등록이 남긴 `.tmp` 작업 파일은 같은 설정 파일의 다음 등록 때 지운다. 설정 파일이 아직 없던 첫 등록이 중단된 경우도 같다. 내용이 이미 같아 바꿀 것이 없는 등록에서도 지우고, 그때 백업 개수도 다시 맞춘다. 정리하는 사이 AI 앱이 설정 파일을 자기 것으로 바꿨으면 "이미 등록됨"이라고 하지 않고 다시 미리보기를 요청한다. 설정 파일 자체는 건드려지지 않았으므로 복구할 것이 없다.
- 설정 파일이 심볼릭 링크면 링크는 두고 링크가 가리키는 실제 파일을 그 폴더에서 교체한다. 하드 링크로 다른 이름과 연결된 파일은 교체하면 서로 다른 파일이 되어 버리므로 자동 등록을 거절한다.
- **백업.** 교체 전에 원본을 `<파일 이름>.timeschedule-UUID.bak`으로 **같은 접근 권한**을 적용해 백업한다. 백업은 비밀값을 포함한 설정 전체의 사본이므로 설정 파일 하나당 **최근 3개만 남기고**, 등록에 성공할 때 더 오래된 TimeSchedule 백업을 지운다. 이전 버전이 쌓아 둔 백업도 같은 규칙으로 정리된다. 이름이 비슷하지만 이 형식이 아닌 파일은 건드리지 않는다. 설정 파일이 심볼릭 링크 뒤에 있으면 링크 옆(이전 버전이 백업하던 곳)과 실제 파일 옆의 백업을 합쳐서 센다. 백업 이름은 경로의 대소문자를 어떻게 입력했든 디스크에 저장된 파일 이름을 따르므로 한 파일의 백업은 한 묶음으로 센다. 이전 버전에서 대소문자를 다르게 입력해 만든 백업은 이름이 달라 세지 않는다(대소문자를 구분하는 폴더에서는 그것이 다른 파일의 백업일 수 있어서 합치지 않는다). 다른 프로그램이 열고 있거나 읽기 전용이라 지우지 못한 이전 백업은 넘어가지 않고 등록 결과에 개수와 경로를 표시한다.
- 설정 파일의 JSON·TOML 형식이 깨져 있으면 등록하지 않고, TimeSchedule 백업이 있으면 가장 최근 백업의 경로를 함께 알려 준다. 0.15.0 이전 버전의 등록 도중 꺼져 파일이 깨졌다면 그 백업을 설정 파일 이름으로 복사해 되돌릴 수 있다. 자동으로 되돌리지는 않는다.
- 설정 파일이 아직 없으면 새 파일을 같은 폴더에 다 쓴 뒤 이름을 한 번에 붙인다. 미리보기 이후 그 이름으로 파일이 생겼으면 덮어쓰지 않고 거절한다. AI 앱이 설정을 초기화해 설정 파일만 없어진 경우에도 예전 등록이 남긴 백업은 같은 규칙으로 정리한다.
- 설정 폴더(심볼릭 링크 뒤에 있으면 링크가 있는 폴더와 실제 파일의 폴더 모두)의 파일 목록을 읽을 수 없으면 등록을 거절한다(바꿀 것이 없는 등록 포함). 백업을 세거나 지울 수 없어 등록할 때마다 쌓이기 때문이다.

전제와 한계:

- **무엇을 막는가.** 이 방식이 다루는 것은 ① 어느 순간에든 PC·앱이 멈추는 경우 ② AI 앱이 평소처럼 자기 설정을 읽고 저장하는 경우(제자리 저장, 새 파일로 교체 모두) ③ 접근 권한이 원본보다 넓어지는 경우다. 같은 Windows 계정으로 실행되는 프로그램이 일부러 `...timeschedule-<UUID>.tmp`·`.bak` 이름의 파일을 만들거나 등록 중인 작업 파일을 바꾸는 경우는 다루지 않는다. 그런 프로그램은 설정 파일 자체를 직접 바꿀 수 있기 때문이다. 정리 대상은 이름(`<설정 파일 이름>.timeschedule-<UUID>.bak`·`.tmp`)으로만 판단하며, 이전 버전이 만든 백업에는 이름 말고 남긴 기록이 없다.
- 이름 바꾸기로 한 번에 교체되는 것은 NTFS와 Windows 10 1607 이상 기준이며, 그렇지 않은 위치에서는 교체가 실패하고 원본이 남는다.
- **확인과 교체 사이의 틈.** 파일을 잡고 있는 동안 다른 프로그램은 이 파일을 읽거나 제자리에서 고칠 수 없지만, 자기 새 파일로 이름을 바꿔 통째로 교체하는 것은 막지 못한다(우리의 교체도 같은 방식이라 막으면 우리도 교체할 수 없다). 교체 직전에 "아직 비교한 그 파일인지" 확인해 이런 교체를 알아채지만, 그 확인과 실제 교체 사이의 아주 짧은 순간에 일어난 교체는 알아채지 못하고 덮어쓴다. Windows에는 확인과 교체를 한 번에 하는 기능이 없다. 이 틈을 없애려면 설정 파일이 잠깐 없어지는 순간이 생기거나(그때 AI 앱이 읽으면 설정이 없는 것으로 본다) 제자리 덮어쓰기로 돌아가야 해서, 가장 피해가 작은 쪽을 택했다. 덮어쓰이는 것은 그 순간 그 프로그램이 저장한 한 번의 변경이다.
- 새 파일의 소유자는 등록한 계정이 된다. 원래 파일의 대체 데이터 스트림은 옮기지 않는다. EFS로 암호화된 파일은 등록한 계정으로 다시 암호화되며, 원래 파일에 추가로 등록돼 있던 다른 사용자의 복호화 권한은 옮기지 않는다. 암호화된 파일에 시스템 표시도 있었다면 시스템 표시는 유지하지 않는다(Windows가 둘을 함께 요청하면 암호화를 무시하기 때문이다). 접근 권한 목록의 "자동 상속으로 계산됨" 표시는 보존하지 않는다(접근에는 영향이 없다).
- 실제 전원 차단으로 검증하지는 않았다.

새 PC에서는 앱 실행 → 새 로컬 인증정보 생성 → 연결 도우미 등록 순서로 사용한다. Git 소스에는 실행 파일·일정 DB·인증정보가 포함되지 않는다. 기존 `mcp-token.dpapi`는 다른 Windows 계정/PC에서 쓸 수 없다. 데이터 폴더째 복사했다면 0.15.0부터 앱이 시작할 때 새 토큰으로 바꾸고 알려 준다. 일정·다이어리 백업 복원은 MCP 연결 등록과 별개다.

공식 등록 규약: [ChatGPT Desktop·Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=desktop), [Claude Code](https://code.claude.com/docs/en/mcp#use-dynamic-headers-for-custom-authentication), [Claude Desktop 로컬 설정](https://modelcontextprotocol.io/docs/develop/connect-local-servers).

## 기존 수동 연결: 인증 준비

아래는 이전 환경변수 방식의 수동 연결 안내다. 새 연결에는 위 설정 도우미를 권장한다. 이 방식은 AI 앱이 환경변수의 토큰을 설정된 주소로 직접 보내므로 0.13.1의 서버 확인이 적용되지 않는다. `mcp-session.ps1 -Status`의 연결 검사만 서버를 확인한 뒤 토큰을 보내며, 0.13.1 이상의 앱이 실행 중이어야 한다. **설정에서 토큰을 재발급하거나 앱이 손상된 인증 파일을 새 토큰으로 바꾸면 환경변수의 토큰은 더 이상 통하지 않는다.** 아래 스크립트를 다시 실행해야 하며, `-PersistToken`으로 저장했다면 그 옵션으로 다시 실행한 뒤 로그아웃/로그인한다.

최초 실행 시 데이터 폴더의 `mcp-token.dpapi`에 244비트 이상의 난수 토큰을 Windows CurrentUser DPAPI로 암호화해 보관한다. 같은 Windows 계정에서 다음 명령을 실행하면 복호화한 토큰을 현재 PowerShell 프로세스의 `TIMESCHEDULE_MCP_TOKEN`에 넣는다. 토큰 자체는 출력하지 않는다. `mcp-status.json`에는 주소·PID·버전만 들어간다.

```powershell
# Windows PowerShell에서 스크립트 실행이 제한된 경우, 이 창에만 적용
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\mcp-session.ps1 -Status
# 별도 fixture라면
.\scripts\mcp-session.ps1 -DataDir C:\LSH\TimeSchedule\.cache\mcp-fixture -Status
```

`running`과 네 도구 이름이 나오면 인증된 초기화와 도구 목록 조회가 성공한 것이다. 원문 일정은 조회하지 않는다. 이 스크립트는 기본적으로 사용자 환경변수나 클라이언트 설정 파일을 수정하지 않는다.

## Codex CLI 및 데스크톱 앱

한 번만 실행하여 서버를 등록한다. [Codex MCP 설정](https://developers.openai.com/codex/mcp)의 Streamable HTTP와 환경변수 인증을 사용한다.

```powershell
codex mcp add timeschedule --url http://127.0.0.1:39281/mcp --bearer-token-env-var TIMESCHEDULE_MCP_TOKEN
.\scripts\mcp-session.ps1 -Status
codex
```

동일한 설정의 TOML 형식은 다음과 같다. 이미 같은 이름의 항목이 있으면 중복 추가하지 않고 해당 항목을 수정한다.

```toml
[mcp_servers.timeschedule]
url = "http://127.0.0.1:39281/mcp"
bearer_token_env_var = "TIMESCHEDULE_MCP_TOKEN"
```

현재 실행 중인 Codex 데스크톱 앱은 PowerShell에서 새로 설정한 환경변수를 받지 않는다. 데스크톱에서 지속적으로 사용하려면 아래 옵션을 **사용자가 선택해 실행**한 뒤 Windows에서 로그아웃/로그인하고 Codex를 새로 실행한다. 이 옵션은 사용자 환경변수에 토큰을 **평문으로 저장**하므로 DPAPI 파일과 보호 수준이 다르다. 이를 원하지 않으면 매번 위 스크립트를 실행한 PowerShell에서 Codex CLI를 시작한다. 개발 작업 중 이 옵션이나 전역 설정 변경을 자동 실행하지 않는다.

```powershell
.\scripts\mcp-session.ps1 -PersistToken -Status
# 나중에 사용자 환경변수에서 제거할 때
[Environment]::SetEnvironmentVariable('TIMESCHEDULE_MCP_TOKEN', $null, 'User')
```

## 도구와 충돌 처리

| 도구 | 필수 입력 | 결과 |
| --- | --- | --- |
| `calendar_list` | `from`, `to` (YYYY-MM-DD) | 본문 없는 일정 목록, `truncated` |
| `calendar_get` | `id` | 메모와 `updatedAt`을 포함한 일정 |
| `calendar_create` | `title`, `date` | 실제 저장된 일정 |
| `calendar_update` | `id`, `expectedUpdatedAt`, 변경 필드 1개 이상 | 실제 저장된 일정 또는 충돌 |

생성 기본값은 `allDay=true`, `notes=""`, `color="sage"`, `completed=false`다. 시간 일정은 `allDay=false`, `startTime`, `endTime`을 함께 지정하고 같은 날짜에서 종료가 시작보다 늦어야 한다. 시간은 로컬 달력의 `HH:mm`이며 시간대 변환이나 여러 날 일정은 제공하지 않는다. 색상은 `sage`, `blue`, `amber`, `rose` 중 하나다.

수정할 때 상세 조회 결과의 `updatedAt`을 `expectedUpdatedAt`에 그대로 넣는다. 생략한 필드는 유지하고 `null`은 거절한다. `allDay=true`로 바꾸면 시간을 비운다. 앱과 다른 클라이언트의 변경이 먼저 저장됐다면 충돌을 반환한다. 다시 상세를 읽고 변경 내용을 확인한 다음 새 버전으로 수정한다. 열린 앱 편집 초안도 유지되며, 오래된 초안을 저장하면 충돌을 알려준다. 초안을 보관한 뒤 편집을 닫고 최신 일정을 다시 열어 내용을 합칠 수 있다.

응답을 받지 못했거나 시간이 초과된 쓰기는 이미 저장됐을 수도 있다. 특히 생성은 같은 입력을 다시 호출하면 중복 일정이 생길 수 있으므로 먼저 목록·상세를 확인한다. 삭제·할 일·프로젝트·개발 기록·임의 파일/SQL/명령 실행 도구는 없다.

## 전송과 자원 제한

공식 Rust SDK `rmcp 3.8.0`과 `axum 0.8.9`를 고정한다. [Streamable HTTP 표준](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)의 JSON 응답 모드를 사용한다. 지원 버전은 `2025-11-25`, `2025-06-18`, `2025-03-26`이며 세션·상주 SSE·서버 푸시·OAuth는 사용하지 않는다. GET은 405다. 클라이언트는 `Accept: application/json, text/event-stream`, `MCP-Protocol-Version`과 Bearer 헤더를 보낸다.

- 127.0.0.1에만 바인딩. Host는 정확한 주소/포트만 허용. 브라우저 Origin이 있는 요청은 모두 403으로 거절한다.
- `/mcp`의 모든 메서드에 인증 필요. 인증 없는 도구 목록/데이터 공개 없음. 인증 없이 응답하는 경로는 서버 확인용 `GET /proof` 하나이며 서명값만 돌려준다. 같은 Host·Origin 검사와 연결 상한을 적용하고, 난수 형식이 맞지 않으면 400이다. 요청/응답 본문과 토큰을 로그에 남기지 않는다.
- 인증 전 연결부터 최대 16개로 제한하고, HTTP 헤더를 5초 안에 완성하지 않는 연결을 닫는다. 연결 상한을 넘으면 HTTP 파서/작업을 만들기 전에 소켓을 닫는다.
- 본문 128KiB, 동시 HTTP 요청 8개, 동시 저장소 작업 4개. 헤더 이후 HTTP 처리 제한 10초. 초과 요청은 413/429 또는 도구 오류를 반환한다.
- 목록은 최대 366일·100개. `truncated=true`이면 날짜 범위를 좁힌다. 메모는 상세 조회로 읽는다. 제목은 200자, 메모는 20,000자.
- 이미 시작한 저장 작업은 요청 연결이 끊겨도 완료될 수 있다. 완전 종료 시 HTTP 요청에 최대 1초, 저장소 작업 정리에 최대 5초를 기다린다. 불완전한 헤더/본문을 보낸 클라이언트가 종료를 무한히 붙잡지 못한다. 응답 없는 쓰기는 재실행 전에 저장 결과를 확인한다.

## 0.15.1 검증 범위 (2026-11-16)

- Workspace 테스트 **278개 통과 / 8개 기본 제외**, Node 테스트 **57개 통과 / 1개 건너뜀**. 새 테스트는 고치기 전 코드에서 실패하는 것을 먼저 확인했다. 접근 권한 테스트는 권한 보존 코드를 일부러 빼면 실패하는 것도 확인했다(본인 전용 파일이 폴더의 규칙 11개로 넓어졌다).
- 실제 파일과 Windows 권한으로 확인한 것: 등록이 기존 파일을 고쳐 쓰지 않고 새 파일로 교체한다(파일 식별자가 바뀐다). 교체 전에 멈춘 상태를 재현하면 원본이 온전하고 다음 등록이 작업 파일을 지운다. 준비하는 동안 다른 프로그램이 자기 파일로 교체했거나, 두 번째 이름을 붙였거나, 접근 권한을 강화했으면 등록을 중단하고 그 상태를 그대로 둔다. 폴더 권한을 물려받는 파일·본인 전용 파일·자기 규칙을 더한 파일의 접근 규칙과 숨김 표시가 유지된다. 직접 지정한 무결성 레이블과 예전 폴더에서 물려받은 레이블이 새 파일과 백업에 바이트 단위로 같게 유지된다. EFS 암호화가 유지된다(시스템 표시가 함께 있는 경우 포함). 지울 권한이 없는 파일과 목록을 읽을 수 없는 폴더에서는 아무것도 쓰지 않고 거절한다. 읽기 전용 파일은 교체에 실패하고 폴더에 아무것도 남기지 않는다. 백업은 3개만 남고 이름이 비슷한 다른 파일은 그대로다. 바꿀 것이 없는 등록과 설정 파일이 없어진 뒤의 첫 등록에서도 정리한다. 다른 프로그램이 열고 있어 지우지 못한 백업은 결과에 표시된다. 실패한 시도는 이름이 겹친 남의 파일을 지우지 않는다. 깨진 설정에서는 가장 최근 백업 경로를 알려 준다.
- 심볼릭 링크 테스트 4개(링크 뒤의 실제 파일 교체, 준비 중 끼어든 링크, 다른 파일을 가리키게 된 링크, 링크가 있는 폴더의 목록을 읽을 수 없는 경우)는 개발 PC 계정에 링크 생성 권한이 없어 건너뛰었고, **GitHub Actions에서 실행되어 통과했다.** CI에서는 링크를 만들지 못하면 실패하도록 해서 건너뛴 채 통과할 수 없다.

- GPT-6 Astra 독립 리뷰를 일곱 차례 받았고 각 지적은 실패 테스트를 먼저 작성한 뒤 고쳤다. 주요 지적: 무결성 레이블·EFS 암호화 유실(1·2차), 지울 수 없는 곳에 쌓이는 사본과 변경 없는 등록의 정리 누락(1차), 준비 중 끼어든 링크와 정리 실패 미보고(2차), 첫 등록이 중단되면 남는 하드 링크가 이후 등록을 막는 문제(3차), 준비 중 강화된 권한을 되돌리는 문제(4차), 백업 개수 제한이 빠지는 경우들(4~6차), 마지막 확인의 순서(7차). 확인과 교체 사이의 틈, 같은 계정의 프로그램이 작업 파일을 조작하는 경우는 위 "전제와 한계"대로 범위 밖으로 두었고 리뷰도 받아들였다. 7차 지적 2건을 반영한 최종본은 다시 검토받지 않았다. 리뷰는 코드 읽기만 했다.
