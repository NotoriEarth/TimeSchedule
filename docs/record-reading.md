# 기록 읽기 명령

[방향 문서](product-direction.md)의 "순서" 3번이다. 0.41.0부터 `TimeSchedule.exe record` 아래에 읽기만 하는 명령 여섯 개가 있다. 포트폴리오를 만들 때 Codex나 Claude Code 같은 에이전트가 명령줄로 프로젝트의 기록을 찾고, 그 기록이 나온 원문 대화까지 따라가 읽는 데 쓴다(방향 문서 사용 흐름 5번).

- 모델을 부르지 않는다.
- 앱이 켜져 있어도, 꺼져 있어도 읽는다. 앱의 실행 잠금을 잡지 않는다.
- 새 화면이나 버튼은 없다.
- 출력은 표준 출력의 JSON 하나다. 성공하면 `outcome`이 `ok`이고 종료 코드는 0, 실패하면 `outcome`이 `error`, `message`에 이유가 있고 종료 코드는 1이다.
- 다른 `record` 명령과 달리 `--result`를 받지 않는다. 주면 실행하지 않고 오류로 끝난다. 결과 파일이 이 명령들의 유일한 쓰기였는데, 경로 글자를 비교해서는 네트워크 공유처럼 같은 폴더를 다른 경로로 가리키는 경우를 막지 못해 없앴다(아래 결정).
- 실행 파일은 창 프로그램으로 빌드되어 있어 PowerShell 창에 직접 치면 출력이 보이지 않을 수 있다. 그때는 `TimeSchedule.exe record list | Out-String`처럼 뒤에 `| Out-String`을 붙인다. 파일로 받으려면 `> 결과.json`처럼 셸로 받는다. 에이전트는 출력을 파이프로 받으므로 그대로 읽는다.

## 명령

| 명령 | 하는 일 | 읽는 곳 |
| --- | --- | --- |
| `projects` | 프로젝트 목록. 출처별 기록 수, 첫·마지막 기록 날짜, 보관된 원문 파일 수, 하루 기록 날 수 | DB, 문서 저장소 |
| `list` | 기록 목록. 본문 대신 앞 240자 | DB |
| `search --query 낱말` | 기록의 제목과 본문에서 찾기. 찾은 곳 앞뒤 발췌 | DB |
| `show --id ID` | 기록 하나의 본문 | DB, 문서 저장소 |
| `show --id ID --evidence` | 하루 정리 기록의 항목과, 항목이 근거로 든 블록의 원문 위치 | DB, 문서 저장소 |
| `transcript --project P ...` | 그날 대화의 블록(사람과 AI의 글). 줄 하나의 앞뒤, 낱말 찾기, 여러 날 찾기 | 문서 저장소 |
| `original --project P --file F --line N` | 보관본의 줄을 그대로 | 문서 저장소 |

공통 인자:

| 인자 | 뜻 |
| --- | --- |
| `--project` | 프로젝트 ID 또는 프로젝트 폴더의 절대 경로. `record daily`와 같다. `list`·`search`에서 한 폴더에 프로젝트가 둘 이상이면 실행하지 않고 프로젝트 ID를 지정하라고 알린다 |
| `--from`, `--to`, `--date` | `YYYY-MM-DD`. `record daily`의 `--date`와 같은 규칙이다 |
| `--offset`, `--max-chars` | 쪽 나누기(아래 "쪽 나누기") |
| `--data-dir` | 다른 `record` 명령과 같다. 폴더를 만들지 않는다 |

## 무엇을 읽는가

다이어리 기록 가운데 프로젝트에 붙은 것만 읽는다. 일정, 할 일, 메모, 프로젝트가 없는 기록은 읽지 않는다. 기록마다 `origin`으로 어디서 왔는지 알린다. 기록의 `source_ref` 앞머리로 가린다.

| `origin` | 무엇인가 | 기본으로 읽는가 |
| --- | --- | --- |
| `daily` | 하루 정리 | 예 |
| `agent` | 자동 개발 기록(에이전트가 작업을 마치고 보낸 기록) | 예 |
| `experience` | 채팅에서 확인한 경험 | 예 |
| `manual` | 사람이 직접 쓴 기록 | 예 |
| `other` | 위에 없는 앞머리 | 예 |
| `chat` | 채팅 발췌(세션의 앞 40KB와 뒤 48KB) | `--origin`에 넣을 때만 |

`--origin daily,agent`처럼 쉼표로 여럿을 고른다. 이 고르기는 `list`와 `search`에만 있다. `show --id`는 ID를 준 기록이면 채팅 발췌도 보여 준다. 채팅 발췌를 기본에서 뺀 것은 2026-11-26 사용자가 승인한 설계다. 이 PC에서 발췌 16건이 기록 글자 수의 대부분(30만 자)이었고, 같은 대화를 `transcript`가 말한 쪽별로 온전히 읽는다.

## 쪽 나누기

응답 하나에 담는 글은 기본 20,000자이고 `--max-chars`(1,000~1,000,000)로 바꾼다. 넘치면 거기서 끊고 `next`에 이어 읽을 인자를 준다. `next`가 `null`이면 끝이다.

| 명령 | 세는 단위 | `next` | 이어 읽기 |
| --- | --- | --- | --- |
| `projects` | 프로젝트 | `{"offset": 10}` | 같은 명령에 `--offset 10` |
| `list`, `search` | 기록 | `{"offset": 40}` | 같은 명령에 `--offset 40` |
| `show` | 본문 글자 | `{"offset": 20000}` | 같은 명령에 `--offset 20000` |
| `show --evidence` | 항목 | `{"offset": 12}` | 같은 명령에 `--offset 12` |
| `transcript`(하루) | 블록 | `{"offset": 36}` | 같은 명령에 `--offset 36` |
| `transcript`(여러 날) | 블록 | `{"from": "2026-11-20", "offset": 3}` | `--from`을 그 날로 바꾸고 `--offset 3` |
| `original` | 줄 글자 | `{"line": 415, "offset": 20000, "lines": 2}` | `--line 415 --offset 20000 --lines 2`(`lines`는 처음 요청한 줄 가운데 남은 수, `offset`이 0이면 빠진다) |

- 기록, 항목, 블록은 그 JSON의 글자 수로 센다. 쪽 하나에는 크기와 관계없이 적어도 하나가 들어간다. 블록은 대화록에서 이미 8,000자 이하로 잘려 있다. `show --evidence`의 항목은 그 항목이 처음 드는 블록의 원문 위치까지 함께 센다. `show`의 첫 쪽은 하루 정리·자동 개발 기록의 정보(`edited`, `daily`, `agent`)를 먼저 세고 남은 만큼 본문을 담는다. 그래도 본문은 적어도 1,000자를 담는다.
- `original`은 다음 줄이 실제로 있을 때만 그 줄을 `next`로 준다.
- 경고는 앞의 20개만 주고 `warningsTotal`에 전체 수를 적는다.
- 출력은 들여쓰기한 JSON이라 실제 출력은 이보다 조금 크다. 2026-11-26에 이 PC의 실제 데이터로 기본값의 `list`가 23,334자, 하루 `transcript`가 22,361자였다. Claude Code는 명령 출력을 30,000자에서 자른다.
- 목록은 한 번에 기록 200개까지 읽고 그 안에서 자른다. `total`은 조건에 맞는 전체 수다. `total`과 그 쪽의 기록은 한 번의 읽기 안에서 함께 읽는다.
- `--offset`은 앞에서부터 센 수다. 이어 읽는 사이에 앱이 기록을 더하거나 고치면 순서가 바뀌어 같은 기록이 두 번 나오거나 하나가 빠질 수 있다(아래 "알려진 한계").

## 명령별 출력

예시의 값은 지어낸 것이다. 키의 순서는 출력과 다를 수 있다.

### projects

```json
{"outcome": "ok", "projects": [
  {"id": "41aa…", "title": "TimeSchedule", "folder": "C:\\LSH\\TimeSchedule", "capture": true,
   "records": {"agent": 55, "chat": 16, "daily": 7}, "firstDate": "2026-10-31", "lastDate": "2026-11-26",
   "originals": 634, "dailyDays": 3}]}
```

`capture`는 앱이 그 프로젝트의 채팅을 지금 수집하는가이다. 앱과 같은 규칙으로, 수집을 켤 때 등록한 폴더가 프로젝트의 지금 폴더와 같을 때만 `true`다. `originals`는 그 폴더 보관 목록(`index.jsonl`)의 줄 수, `dailyDays`는 하루 기록 파일의 날 수다. 폴더가 없으면 0이고, 경로에 링크(정션 포함)가 있거나 읽지 못하면 `null`이다. 날 수는 `<날짜>.json` 이름의 파일만 센다. 이 두 값은 그 쪽에 든 프로젝트만 센다. 문서 저장소를 찾지 못하면 둘 다 `null`이고 `storeError`에 이유가 있다. 프로젝트의 폴더를 바꾼 적이 있으면 예전 폴더의 보관본은 세지 않는다. `total`, `offset`, `next`는 다른 목록과 같다.

### list, search

```json
{"outcome": "ok", "total": 3, "offset": 0, "next": null, "records": [
  {"id": "8f0c…", "project": "41aa…", "date": "2026-11-20", "kind": "development", "origin": "daily",
   "title": "하루 정리 · 2026-11-20", "chars": 3051, "updatedAt": "2026-11-21T00:12:09.120Z",
   "summary": "## 오늘 한 일 - 하루 정리의 답 검사를 만들고 …"}]}
```

- 날짜가 늦은 것부터, 같은 날이면 늦게 고친 것부터다.
- `search`는 `summary` 대신 `matches`(본문에서 찾은 횟수)와 `excerpts`(앞의 세 곳, 앞 60자와 뒤 140자)를 준다. 제목에서만 찾았으면 `excerpts`가 비어 있다.
- 찾는 규칙은 앱 상단 검색과 같다. 세 글자 이상은 검색 색인(`diary_search`)으로, 띄어쓰기까지 그대로인 글귀를 찾는다. 두 글자 이하는 본문을 직접 비교하며, 영문이 섞인 낱말만 대소문자를 가리지 않는다. 검색어는 200자까지다.
- `--query` 값은 `--`로 시작해도 검색어로 읽는다.

### show

```json
{"outcome": "ok", "id": "8f0c…", "project": "41aa…", "date": "2026-11-20", "kind": "development",
 "origin": "daily", "title": "하루 정리 · 2026-11-20", "updatedAt": "…", "chars": 3051, "offset": 0,
 "body": "## 오늘 한 일\n- …", "next": null, "edited": false,
 "daily": {"file": "daily/c--lsh-timeschedule-ec0dc820b6a643d1/2026-11-20.json"}}
```

- `body`는 다이어리에 보이는 본문이다. 사람이 다이어리에서 고쳤으면 고친 글이다.
- 하루 정리에는 `edited`(앱이 마지막으로 넣은 본문과 다른가)와 `daily`(기록 파일의 위치)가 붙는다. `edited`가 `true`이면 사람이 본문을 고쳤고, 그 뒤에 만든 판은 다이어리에 반영되지 않았다.
- 이 정보와 아래 `agent`는 첫 쪽(`--offset 0`)에만 있다.
- 자동 개발 기록에는 `agent`가 붙는다. `workId`, `startedAt`, `completedAt`, `status`, 다이어리가 가진 커밋 목록(`commits`), 원본 `record.md`의 절대 경로(`document`)다. 원본은 문서 저장소의 목록(`.sync/catalog`)으로 찾고, 찾지 못하면 `documentError`에 이유가 있다.

### show --evidence

하루 정리 기록에만 쓴다. 기록 파일(`daily/<폴더>/<날짜>.json`)의 최신 판을 읽는다. 다이어리 항목을 다른 프로젝트로 옮겼으면 근거를 주지 않는다. 근거는 처음 만든 프로젝트의 그날 것이기 때문이다. 기록 파일의 프로젝트 ID, 날짜, 폴더가 그 자리의 것이 아니면(다른 기록을 옮겨 놓은 파일) 읽지 않는다. 다이어리에 보여 주는 코드와 같은 확인이다. 근거를 본문과 함께 주면 하루 기록 하나가 20,000자를 넘는 날이 있어(2026-11-26에 이 PC의 하루 기록 7개를 재 보니 근거만 약 1천~1만 1천 자) 따로 읽는다.

```json
{"outcome": "ok", "id": "8f0c…", "file": "daily/…/2026-11-20.json", "date": "2026-11-20", "revision": 2,
 "total": 19, "offset": 0, "next": null,
 "items": [
   {"section": "troubleshooting", "problem": "하루 기록이 두 번 보임", "cause": "…", "fix": "…",
    "verification": null, "blocks": [37, 40]},
   {"section": "decision", "decision": "…", "reason": null, "rejected": [], "proposedBy": "AI",
    "decidedBy": "사람 승인", "proposal": [{"block": 40, "quote": "…"}], "decided": [{"block": 41, "quote": "…"}],
    "blocks": [40, 41]}],
 "blocks": [
   {"block": 37, "speaker": "사람", "at": "2026-11-20T14:02:11+09:00",
    "file": "claude/C--LSH-TimeSchedule/1b5d….jsonl.zst", "line": 412}]}
```

- `section`은 다이어리에 보이는 순서대로 `overview`, `summary`(판 3까지의 기록), `development`, `troubleshooting`, `decision`, `nextStep`이다.
- `blocks`에는 그 쪽의 항목이 든 블록만 있다.
- `proposedBy`, `decidedBy`는 확인 규칙을 거친 값이다([하루 정리](daily-record.md) "답을 확인하는 규칙"). 글귀가 맞지 않은 근거는 `quote`가 `null`이다.

### transcript

`--project`와 다음 중 하나를 준다.

| 인자 | 주는 블록 |
| --- | --- |
| `--date D` | 그날의 모든 블록 |
| `--date D --query 낱말` | 그날 그 낱말이 든 블록 |
| `--date D --file F --line N [--context K]` | 파일 F의 N번 줄에서 시작하는 블록과 앞뒤 K개(기본 3, 최대 50). 그 줄에서 시작하는 블록이 없으면 그 파일에서 N번 줄 앞의 마지막 줄의 블록. 한 줄에서 블록이 여럿 나오면(Claude Code의 한 행에 실패한 명령이 둘 있는 경우 등) 그 블록을 모두 주고 첫 블록이 `focus`다 |
| `--from D1 --to D2 --query 낱말` | 그 기간에 그 낱말이 든 블록, 날짜와 시각 순서. 한 번에 31일까지 |

```json
{"outcome": "ok", "project": {"id": "41aa…", "title": "TimeSchedule"}, "date": "2026-11-20", "focus": 37,
 "total": 7, "offset": 0, "next": null, "warnings": [],
 "blocks": [{"date": "2026-11-20", "number": 37, "at": "2026-11-20T14:02:11+09:00", "speaker": "사람",
   "source": "S3", "file": "claude/C--LSH-TimeSchedule/1b5d….jsonl.zst", "line": 412, "clipped": false,
   "text": "같은 날 기록이 두 개 보여"}]}
```

- 블록은 `record daily`가 모델에 보내는 하루 대화록과 같다. 말한 쪽, 남기는 글, 자르는 길이가 모두 같다([하루 정리](daily-record.md) "하루 대화록"). `clipped`가 `true`이면 대화록이 글을 잘랐으므로 `original`로 그 줄을 읽는다.
- 여러 날 찾기는 `focus`, `total` 대신 `daysRead`(읽은 날 수)를 주고, `warnings`의 줄마다 앞에 날짜를 붙인다. 쪽이 차면 남은 날은 읽지 않고, 다음 날부터 이어 읽게 `next`를 준다. 그 뒤의 날에 찾는 낱말이 없으면 다음 쪽은 비어 있다.
- 낱말 찾기는 블록의 글에서 대소문자를 가리지 않고 찾는다. 대화록에 없는 도구 출력과 명령 출력에서는 찾지 않는다.

### original

```json
{"outcome": "ok", "project": {"id": "41aa…", "title": "TimeSchedule"},
 "file": "claude/C--LSH-TimeSchedule/1b5d….jsonl.zst", "earlier": [], "next": null,
 "lines": [{"line": 412, "chars": 542, "offset": 0, "text": "{\"type\":\"user\",…}", "clipped": false, "long": false, "lossy": false}]}
```

- `--file`은 프로젝트 보관 목록(`index.jsonl`)에 있는 파일이어야 한다. 세션 파일 옆의 도구 결과 파일도 목록에 있으면 읽는다. 경로는 `record daily`와 같은 규칙으로 확인한다(`..`, 드라이브 문자, 링크를 거치는 경로는 읽지 않는다).
- `--lines`로 여러 줄(1~200, 기본 1)을 읽는다.
- 줄은 압축을 푼 파일의 줄 그대로다(줄 끝의 `\n`과 그 앞의 `\r`은 뺀다). JSON 한 행이 문자열 하나로 나온다. 8 MiB를 넘는 줄은 앞 8 MiB만 읽고 `long`이 `true`다. 도구가 아직 다 쓰지 않은 마지막 줄(줄 끝이 없는 줄)은 길이와 관계없이 줄로 치지 않는다. 줄 번호는 하루 대화록이 세는 방법과 같다.
- 줄에 UTF-8 글이 아닌 바이트가 있으면 `�`로 바꿔 보여 주고 `lossy`가 `true`다. 세션 파일 옆의 도구 결과 파일은 다른 인코딩일 수 있다.
- `earlier`는 같은 폴더에 남아 있는 그 파일의 이전 내용(`<이름>.prev-<시각>`)이다. 원본이 덧붙기가 아닌 방식으로 바뀌어 보관본을 바꿨을 때 생긴다([채팅 원문 보관](chat-originals.md) "보관본을 바꾸는 규칙"). 비어 있지 않으면 그 전에 만든 하루 기록이 가리키는 줄에 지금은 다른 글이 있을 수 있다. 이전 내용은 보관 목록에 없어 이 명령으로 읽지 않는다. 그 폴더를 읽지 못하면 `earlier`는 `null`이다. 요청한 줄이 지금 내용에 없으면 오류 글에 이전 내용의 이름을 적는다.
- 보관본은 세션 파일 전체라 붙여 넣은 내용과 명령 출력이 그대로 있다. 비밀값을 채팅에 넣었다면 이 명령의 출력에도 나온다.

## 원문 위치

원문 위치는 보관본 파일의 상대 경로(`file`)와 압축을 푼 파일의 줄 번호(`line`, 1부터)다. 세션 파일은 뒤에 덧붙기만 하므로 둘은 나중에도 같은 글을 가리킨다. 드물게 원본이 덧붙기가 아닌 방식으로 바뀌면 보관본이 새 내용으로 바뀌는데, 그때는 `original`의 `earlier`가 비어 있지 않다. 블록 번호(`number`, `block`)는 그날 대화의 순서라, 늦게 보관된 세션이 그날의 대화를 바꾸면 달라질 수 있다. 하루 기록의 블록 번호는 그 판을 만들 때의 번호다. 블록을 다시 찾을 때는 `transcript --file --line`을 쓴다.

## 읽기만 한다

- **DB.** 데이터 폴더의 `schedule.db`를 SQLite 읽기 전용 연결로 열고 `query_only`를 켠다. DB 형식을 올리지 않는다. 형식이 이 실행 파일과 다르면(16이 아니면) 읽지 않고 같은 버전의 앱을 한 번 켜라고 알린다. DB가 없으면 만들지 않고 오류로 끝난다.
- **SQLite 보조 파일.** 앱이 꺼진 뒤 읽으면 `schedule.db-shm`과 `schedule.db-wal`이 생겨 남을 수 있다. 읽는 쪽은 `-shm` 파일에 읽는 중이라는 표시를 남기므로 `-shm`의 수정 시각은 읽을 때마다 바뀐다. 이 명령이 두 파일에 기록 내용을 쓰지는 않는다. `-wal`에는 앱이 쓰는 동안 DB의 바뀐 쪽이 들어가므로 앱이 켜져 있으면 기록 내용이 있을 수 있다. 앱이 그렇게 쓰는 것이고 이 명령과는 관계없다. 2026-11-26에 이 PC에서 앱이 꺼진 채 `list`를 실행하기 전과 뒤에 `schedule.db`의 해시가 같았고 `-wal`의 크기와 시각도 그대로였다. 앱이 켜져 쓰는 중에도 맞는 내용을 읽으려고 이 방법을 골랐다(아래 결정).
- **잠금.** 앱의 실행 잠금(`native-instance.lock`)을 잡지 않으므로 앱이 켜져 있어도 읽고, 읽는 중에 앱을 켤 수 있다. 문서 저장소에서는 하루 정리의 날짜별 잠금이나 원문 보관의 `.lock`을 잡지 않는다. 쓰는 중인 보관본의 마지막 줄은 읽지 않는다.
- **폴더와 파일.** 데이터 폴더, 문서 저장소, 그 안의 폴더를 만들지 않는다. 결과 파일도 쓰지 않는다(`--result`를 받지 않는다). SQLite가 큰 정렬이나 묶음을 위해 시스템 임시 폴더에 쓰는 임시 파일도 쓰지 않게 메모리에 둔다(`temp_store = MEMORY`).

```text
결정: DB를 보통의 읽기 전용 연결로 연다. 앱이 꺼져 있을 때 읽으면 SQLite 보조 파일 둘(-shm, -wal)이 데이터 폴더에 남을 수 있다.
- 이유: 앱이 켜져 쓰는 중에도 항상 맞는 내용을 읽는 방법이다. 이 명령은 보조 파일에 기록 내용을 쓰지 않는다(처음 설계안에는 "보조 파일에는 기록 내용이 없다"고 적었으나, -wal에는 앱이 쓰는 동안 기록 내용이 들어갈 수 있어 고쳐 적었다).
- 제안: AI
- 확정: 사람 승인
- 버린 대안: 파일을 전혀 만들지 않는 방식(immutable. 그 순간 앱이 쓰면 그 한 번의 읽기가 틀릴 수 있고, 앱이 켜져 있으면 최근 변경을 못 봄), DB를 임시 폴더에 복사해 읽기(복사 도중 앱이 쓰면 깨진 사본)
```

```text
결정: 읽기 명령에서 --result를 없애고 표준 출력만 쓴다.
- 이유: 경로 글자 비교로는 네트워크 공유를 거친 같은 폴더를 가리지 못한다. 결과 파일이 읽기 명령의 유일한 쓰기다. 에이전트는 표준 출력을 파이프로 받으므로 영향이 없다.
- 제안: AI
- 확정: 사람 승인
- 버린 대안: 유지하고 한계로 적기(사람이 직접 칠 때 파일로 볼 수 있지만 record daily와 같은 한계가 남는다), 파일 식별자로 비교하기(코드가 늘고 네트워크 공유에서는 식별자도 다를 수 있다)
```

## 쓰는 장면

에이전트가 "하루 기록이 두 번 보이던 버그를 어떻게 고쳤나"를 찾는 순서다.

1. `record projects`로 TimeSchedule의 ID와 폴더를 안다.
2. `record search --project C:\LSH\TimeSchedule --query "두 번"`으로 2026-11-20 하루 정리가 나온다.
3. `record show --id <그 기록> --evidence`로 트러블슈팅 항목의 문제·원인·해결과 근거 블록의 위치(파일, 412번 줄)를 읽는다.
4. `record transcript --project C:\LSH\TimeSchedule --date 2026-11-20 --file <파일> --line 412 --context 5`로 그때 사람과 AI가 주고받은 글을 읽는다.
5. 답이 잘려 있거나(`clipped`) 그 줄 전체가 필요하면 `record original --project C:\LSH\TimeSchedule --file <파일> --line 415`로 그 줄을 그대로 본다.
6. 기록에 없는 낱말(오류 문구 등)은 `record transcript --project C:\LSH\TimeSchedule --from 2026-11-01 --to 2026-11-26 --query "UNIQUE constraint"`로 대화에서 직접 찾는다.

## 알려진 한계

- `record daily` 명령으로 방금 만든 하루 기록은 앱이 다음에 채팅을 수집해 다이어리에 보여 준 뒤부터 `list`, `search`, `show`에 나온다. 그 전에도 `transcript`와 `original`은 그날의 원문을 읽는다.
- `show --evidence`는 기록 파일의 최신 판을 읽는다. 사람이 다이어리 본문을 고쳤으면(`edited`가 `true`) 본문과 항목이 다를 수 있다.
- `list`, `search`, `projects`, `show --evidence`의 이어 읽기는 앞에서 센 `--offset`이다. 읽는 사이에 앱이 기록을 수집하거나 사람이 기록을 고치면 같은 기록이 두 번 나오거나 하나가 빠질 수 있다. 앱은 한 시간마다와 프로젝트 화면을 열 때 수집한다. 결과를 다시 받으려면 처음부터 다시 읽는다.
- 여러 날 찾기는 날마다 하루 대화록을 새로 만들어 찾으므로 느리다(아래 "검증"). 색인은 없다.
- 기록 검색은 띄어쓰기까지 그대로인 글귀 검색이다. 낱말 여럿을 따로 찾거나 비슷한 말을 찾지 않는다.
- 세 글자 이상의 검색은 SQLite 색인이 대소문자를 접어 찾고, `matches`와 `excerpts`는 이 프로그램이 다시 찾아 만든다. 둘이 대소문자를 접는 방법이 다른 드문 글자(그리스어의 끝 시그마 `ς` 등)에서는 기록은 찾았는데 `matches`가 0이고 `excerpts`가 빌 수 있다.
- 프로젝트의 폴더를 바꾸면 `transcript`와 `original`은 `--project`에 지금 폴더나 예전 폴더의 경로를 줘야 한다. 프로젝트 ID로는 보관 폴더가 둘이라 실행하지 않는다(`record daily`와 같다).
- 채팅 발췌(`chat`)는 기록이 만들어진 때의 앞뒤 발췌라 대화 전체가 아니다.

## 검증

자동 테스트는 임시 폴더와 만든 자료로 한다.

- `apps/timeschedule-native/src/record_read/tests.rs`: 시험용 보관본을 두고, 고정된 모델 답으로 하루 기록을 만들어 앱의 반영 경로로 다이어리에 넣고, 자동 개발 기록과 직접 쓴 기록을 더한 데이터 폴더에서 명령을 실행해 출력 JSON을 확인한다. 위 "쓰는 장면"의 흐름, 쪽 나누기와 이어 읽기, 출처·날짜·검색어 고르기, 여러 날 찾기, 앱이 잠금을 쥔 동안 읽기, 읽은 뒤 DB 파일과 문서 저장소가 그대로인지, `--result`를 받지 않는지, 데이터 폴더를 만들지 않는지를 본다.
