# 채팅 원문 보관

0.33.0부터 앱은 채팅 수집을 켠 프로젝트의 Codex·Claude Code 세션 파일을 문서 저장소에 압축해 보관한다. 도구가 자기 폴더의 세션 파일을 지워도 보관본은 남는다. 방향과 순서는 [TimeSchedule 방향](product-direction.md)의 "순서" 1번이다.

보관은 다이어리에 들어가는 채팅 발췌와 별개다. 발췌는 이전과 같이 만들어진다.

## 왜 필요한가

- Claude Code는 설정이 없으면 30일이 지난 세션 파일을 지운다(공식 문서의 `cleanupPeriodDays` 기본값).
- Codex는 2026-11-24 기준 이 PC에서 6월 파일까지 남기고 있고 오래된 파일을 `.jsonl.zst`로 압축해 둔다. 보관 기간 설정은 찾지 못했다. 도구가 앞으로도 그렇게 한다는 보장은 없다.
- 다이어리에는 세션마다 앞 40KB와 뒤 48KB 발췌만 있다.

## 무엇을 보관하는가

세션의 작업 폴더가 프로젝트 폴더와 같거나 그 안에 있으면 그 프로젝트의 세션이다. 작업 폴더(worktree)에서 연 세션도 여기에 들어간다. 여러 프로젝트 폴더가 겹치면 더 긴 경로의 프로젝트가 가져간다. 그 프로젝트가 채팅 수집을 켜지 않았으면 보관하지 않는다. 수집을 켠 프로젝트 안에 수집을 끈 프로젝트를 따로 등록해 두면 안쪽 폴더의 세션은 보관되지 않는다.

| 도구 | 보관하는 파일 |
| --- | --- |
| Codex | `sessions/연/월/일/rollout-*.jsonl`과 `rollout-*.jsonl.zst`, `archived_sessions/`의 같은 파일. 하위 에이전트와 `codex exec` 실행도 각각 하나의 파일이다 |
| Claude Code | `projects/<폴더>/<세션 ID>.jsonl`과, 같은 이름의 폴더 `<세션 ID>/` 아래 모든 파일(하위 에이전트 기록, 도구 결과) |

CLI에서 연 세션과 데스크톱 앱에서 연 세션을 가리지 않는다. 다이어리 발췌는 Claude Code 중 CLI 세션만 읽으므로, 발췌에 없는 세션도 보관본에는 있다. Claude Code 파일은 프로젝트의 채팅 수집에 Claude Code가 포함돼 있을 때만 보관한다.

## 어디에 보관하는가

[개인 문서 저장소](document-vault.md)의 `originals` 폴더다. 기본 위치는 `Documents\TimeScheduleData\originals`다.

```text
originals/
  c--lsh-timeschedule-ec0dc820b6a643d1/
    project.json                프로젝트 ID, 제목, 폴더 경로
    index.jsonl                 보관한 파일 목록
    .lock                       실행 중 잠금
    codex/2026/11/04/rollout-….jsonl.zst
    codex/archived_sessions/rollout-….jsonl.zst
    claude/C--LSH-TimeSchedule/<세션 ID>.jsonl.zst
    claude/C--LSH-TimeSchedule/<세션 ID>/subagents/agent-….jsonl.zst
```

- 프로젝트 폴더 이름은 프로젝트 경로의 앞 60자에서 영문 소문자와 숫자가 아닌 글자를 `-`로 바꾼 것에, 경로 전체의 해시 16자를 붙인 것이다. 경로가 다르면 이름도 다르다.
- 도구 폴더 안에서의 경로를 그대로 따른다. Codex는 `sessions/` 아래 경로, Claude Code는 `projects/` 아래 경로다.
- 파일 하나를 zstd 압축 파일 하나로 두고 이름에 `.zst`를 붙인다. Codex가 스스로 압축한 `rollout-*.jsonl.zst`만 바이트 그대로 복사하고 이름도 그대로 둔다. 그래서 같은 대화의 `.jsonl`과 `.jsonl.zst`는 보관본 하나가 된다. 그 밖의 파일은 원래 이름이 `.zst`로 끝나도 다시 압축해 `.zst`를 붙인다.
- 새 보관본은 `.tmp` 폴더에 다 쓴 뒤 끝까지 풀어 보고 제자리로 옮긴다. 쓰는 도중 앱이 종료돼도 반쯤 쓰인 보관본이 남지 않는다. 남은 `.tmp`는 다음 실행이 지운다.
- `project.json`의 폴더 경로가 다른 프로젝트 것이면 그 폴더에는 쓰지 않고 실패로 센다.
- `originals`부터 보관본까지의 폴더 중 하나라도 링크(정션 포함)이면 쓰지 않고 실패로 센다. 저장소 폴더 자체가 링크인 것은 허용하고, 가리키는 실제 폴더를 저장소로 쓴다.

## 보관본을 바꾸는 규칙

세션 파일은 뒤에 덧붙기만 한다. 그래서 보관본을 바꿔도 되는 경우는 하나다.

- **이전 보관본의 내용이 새 내용의 앞부분과 같을 때만** 새 보관본으로 바꾼다. 두 압축 파일을 풀어 가며 비교해서 확인한다.
- 그렇지 않으면 이전 보관본을 `<이름>.prev-<UTC 시각>`으로 복사해 둔 뒤 새 보관본으로 바꾼다. 원본이 줄었거나, 같은 크기로 내용이 바뀌었거나, 이전 보관본을 풀 수 없는 경우가 여기에 든다. `.prev-` 파일은 덮어쓰지 않는다. 같은 시각의 이름이 있으면 번호를 붙인다. 복사가 끝나기 전에는 제자리의 보관본을 건드리지 않는다.
- 보관본이 있는지 확인하다가 "없음"이 아닌 오류가 나면 없는 것으로 보지 않고 실패로 센다.
- 새 보관본을 끝까지 풀 수 없으면 바꾸지 않고 실패로 센다. Codex가 아직 다 쓰지 않은 `.jsonl.zst`가 여기에 든다.
- Codex의 `.jsonl`과 `.jsonl.zst`가 함께 있으면 `.jsonl`을 보관하고 `.jsonl.zst`는 열지 않는다. `.jsonl`이 없어지면 `.jsonl.zst`가 그 자리를 잇는다.
- 원본은 열었을 때의 크기까지만 읽는다. 읽는 동안 도구가 덧붙인 내용은 다음 실행에서 보관한다.
- 원본이 지워져도 보관본과 목록 줄은 그대로다. 이 기능은 보관본을 지우지 않는다.

이 판단은 디스크에 있는 보관본을 보고 한다. 목록 파일이 없거나 틀려도 보관본을 잘못 덮어쓰지 않는다.

## 목록 파일

`index.jsonl`은 보관한 파일마다 한 줄이다. 무엇을 어디서 보관했는지 적고, 바뀌지 않은 원본을 다시 읽지 않게 한다.

| 항목 | 뜻 |
| --- | --- |
| `file` | 보관본의 상대 경로 |
| `tool` | `codex` 또는 `claude` |
| `session` | 세션 ID |
| `cwd` | 세션의 작업 폴더 |
| `client` | 세션을 연 프로그램. Codex는 `Codex Desktop`·`codex_exec`, Claude Code는 `claude-desktop`·`cli`·`sdk-cli` |
| `started` | 세션 시작 시각 |
| `source` | 원본 파일 경로 |
| `sourceSize`, `sourceModified` | 보관할 때의 원본 크기와 수정 시각(나노초) |
| `archivedAt` | 보관한 시각 |

- Claude Code 세션에 딸린 파일은 그 세션의 `session`, `cwd`, `client`, `started`를 갖는다.
- 목록의 원본 경로·크기·수정 시각이 지금 원본과 같고 보관본이 있으면 그 파일은 건너뛴다. 바뀐 것이 없는 실행은 아무것도 쓰지 않는다.
- 목록을 지우면 다음 실행이 모든 원본을 다시 읽어 보관본과 비교하고 목록을 새로 만든다. 원본이 이미 지워진 파일의 줄은 돌아오지 않지만 보관본은 남는다.
- `.prev-` 파일은 목록에 없다.

## 언제 보관하는가

- 앱을 켤 때
- 프로젝트 화면을 열 때
- 앱을 켜 둔 동안 한 시간마다
- 프로젝트의 채팅 자동 수집을 켤 때
- `TimeSchedule.exe record scan-local-chats`를 실행할 때. 결과 JSON의 `originals`는 `{"archived", "unchanged", "failed"}`이고, 문서 저장소를 찾지 못한 경우처럼 보관을 시작하지 못했으면 `{"error": "이유"}`다. 실패나 오류가 있으면 `outcome`이 `attention`이다

0.32.0까지는 60초마다 모든 세션 파일을 훑었다. 진행 중인 세션은 수십 MB라 매분 다시 압축하지 않도록 바꿨다. 다이어리 발췌도 같은 시점에 갱신된다. 기록 수신함 확인은 이전처럼 1분마다 한다. 수집이 도는 중에 수집 요청이 또 들어오면(한 시간이 됨, 프로젝트 화면을 엶, 채팅 수집을 켬) 그 수집이 끝난 뒤에 한 번 더 돈다.

프로젝트 폴더마다 `.lock` 파일을 잠그고 실행한다. 다른 프로세스가 같은 프로젝트를 보관하는 중이면 그 프로젝트는 이번 실행에서 건너뛴다. 잠금은 프로세스가 끝나면 풀린다.

## 실패했을 때

파일 하나를 읽지 못하거나 쓰지 못하면 그 파일만 실패로 세고 나머지를 계속한다. 다음 실행에서 다시 시도한다. 실패가 있으면 앱의 오류 표시 줄에 "채팅 원문 N개를 보관하지 못했습니다. 다음 확인 때 재시도합니다."가 나온다.

- 문서 저장소가 없으면 보관하지 않고 "문서 저장소를 찾지 못해 채팅 원문을 보관하지 못했습니다."를 표시한다. `node scripts/document-vault.mjs init --root <경로>`로 만든다.
- 첫 줄을 아직 다 쓰지 않은 새 세션은 실패가 아니다. 다음 실행에서 보관한다.
- 첫 줄이 있는데 세션 정보로 읽을 수 없는 Codex 파일은 실패로 센다. Claude Code 파일은 200줄을 다 읽고도 세션 ID와 작업 폴더를 찾지 못하면 실패로 세고, 그 전에 파일이 끝나면 다음 실행으로 넘긴다. 도구가 파일 형식을 바꾼 것을 놓치지 않기 위해서다.
- 도구 폴더 안의 링크(정션 포함)는 따라가지 않고 실패로 센다. Claude Code의 `projects/<폴더>`가 링크인 경우만 따라간다. 그 폴더를 다른 드라이브로 옮기고 링크를 둔 경우를 위해서다.
- 원본을 읽는 도중 파일이 짧아지면 그 파일은 실패로 세고 보관본을 바꾸지 않는다.
- `index.jsonl`에 읽을 수 없는 줄이 있으면 그 프로젝트는 아무것도 쓰지 않고 실패로 센다. 파일을 확인하거나 지우면 다음 실행이 새로 만든다.

## 알려진 한계

- 원본의 크기와 수정 시각이 둘 다 그대로인 채 내용만 바뀌면 알아채지 못한다.
- 보관본을 바꾼 직후 목록을 저장하기 전에 앱이 종료되면 목록의 줄이 한 실행 전 상태로 남는다. 다음 실행이 원본을 다시 비교해 고친다. 그 사이 도구가 원본을 지웠으면 줄은 고쳐지지 않는다. 내용은 제자리나 `.prev-` 파일에 있다.
- 파일을 찾은 뒤 보관하기까지의 짧은 사이에 도구가 같은 경로를 다른 세션의 파일로 바꾸면 그 내용이 처음 찾은 세션의 이름으로 보관된다. 두 도구는 세션마다 고유한 파일 이름을 쓰므로 실제로 일어난 적은 없다.
- 폴더 경로는 대소문자를 구분하지 않고 비교한다. 대소문자 구분을 켠 폴더에서 이름이 대소문자만 다른 폴더나 파일은 서로 섞인다.
- 보관 이름이 255자를 넘거나, 한 폴더에 `out` 파일과 `out.zst` 폴더가 함께 있는 경우처럼 이름이 겹치면 그 파일은 매번 실패로 센다.
- 저장소 위치는 자동 개발 기록 전달이 등록한 상태 폴더의 `vault-settings.json`에서 읽는다. 등록이 없으면 기본 위치 `Documents\TimeScheduleData`를 쓴다. 등록된 Node나 스크립트 경로가 없어졌으면 위치를 읽지 못하고 오류를 표시한다.
- 실행 중에 프로젝트의 채팅 수집을 꺼도 그 실행은 시작할 때의 프로젝트 목록으로 끝까지 간다.
- 세션의 작업 폴더가 지워진 뒤에는 폴더 경로의 글자만 비교한다. 지워진 폴더가 링크 아래에 있었다면 링크가 가리키던 곳이 아니라 적힌 경로의 프로젝트로 본다.
- Claude Code가 세션 파일을 지운 뒤 딸린 폴더에만 새 파일이 생기면 그 파일은 찾지 못한다. 공식 문서는 딸린 폴더를 세션 파일과 함께 지운다고 적고 있다.

## 원문 읽기

보관본은 표준 zstd 파일이다. Node.js 22.15 이상에서는 다음처럼 푼다.

```js
import fs from 'node:fs';
import zlib from 'node:zlib';
const text = zlib.zstdDecompressSync(fs.readFileSync('<세션 ID>.jsonl.zst')).toString('utf8');
```

프로젝트와 날짜로 찾아 읽는 명령은 방향 문서 순서 3번(읽기용 CLI)에서 만든다. 지금은 `index.jsonl`에서 세션을 찾고 파일을 직접 푼다.

## 담기는 내용

보관본은 세션 파일 전체다. 채팅에 붙여 넣은 내용, 명령 출력, 도구가 읽은 파일 내용이 들어 있다. 비밀 값을 채팅에 넣었다면 보관본에도 있다. 문서 저장소 폴더를 백업하거나 옮길 때 이 점을 고려한다. 앱은 이 파일을 어디에도 보내지 않는다.

## 검증

자동 테스트(`crates/timeschedule-core/tests/chat_originals.rs`)는 임시 폴더와 만든 내용으로 위 규칙을 확인한다. 실제 세션 파일로 자동 테스트하지 않는다.

2026-11-24에 빌드한 0.33.0 실행 파일을 격리된 데이터 폴더와 임시 문서 저장소로 실행했다. 이 PC의 실제 세션 폴더는 읽기만 했고, 사용자의 문서 저장소에는 쓰지 않았다. 프로젝트 하나를 `C:\LSH\TimeSchedule`에 연결하고 `record configure-local-chats`와 `record scan-local-chats`를 실행했다.

| 크기 | 원본 360.4MB, 보관본 129.3MB. 이 중 72.9MB는 Codex가 이미 압축해 둔 파일이라 그대로 복사했다 |

| 원본과 비교 | 453개가 풀어서 원본과 같았다. 1개는 실행 뒤 원본이 커져서(진행 중인 세션) 비교하지 않았다 |
| 실패 | 0개. `.prev-` 파일과 남은 임시 파일도 없었다 |
| 저장소 폴더가 없을 때 | `originals`가 `{"error": "문서 저장소를 찾지 못해 채팅 원문을 보관하지 못했습니다."}`, `outcome`이 `attention`, 종료 코드 2였다. 발췌 수집은 그대로 돌았고 폴더는 만들어지지 않았다 |

같은 날 릴리스 빌드의 보관 코드만 따로 실행해, 바뀐 것이 없는 실행이 0.6초이고 목록 파일을 지운 뒤의 실행이 10.7초(448개를 다시 비교해 모두 이전 보관본을 잇는 것으로 확인, `.prev-` 0개)임을 확인했다.

시간은 한 번씩 잰 값이다. 디스크 캐시 상태에 따라 달라진다.

같은 실행 파일을 같은 방식의 격리된 데이터 폴더로 창을 띄워 실행했을 때, 앱이 켜지면서 스스로 454개를 임시 저장소에 보관했다(시작 후 11.3초에 목록 파일이 생겼다). 프로젝트 화면을 열 때와 한 시간마다 도는 것은 자동 테스트로만 확인했다. 확인 당시 화면이 잠겨 있어 창을 클릭할 수 없었다.
