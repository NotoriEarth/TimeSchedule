# 하루 정리

[방향 문서](product-direction.md)의 "순서" 2번이다. 그날 채팅 원문을 모델이 읽고 하루 기록과 하루 요약을 만든다. 지금은 **하루 대화록**(아래)과 그것으로 모델을 한 번 불러 만드는 **하루 기록**(아래 "하루 기록")까지 있다. 다이어리 표시는 다음 단계에서 붙인다.

## 하루 대화록

한 프로젝트의 한국 시간 하루 동안 사람과 AI가 주고받은 글이다. [채팅 원문 보관](chat-originals.md)의 보관본만 읽는다. DB를 열지 않으므로 앱이 켜져 있어도 만들 수 있다.

### 고르는 파일

프로젝트의 `originals/<폴더>/index.jsonl`에서 대화 파일만 고른다. Codex 세션 파일과 Claude Code 본 세션 파일, Claude Code 하위 에이전트 기록(`subagents/`)이다. Claude Code 세션 옆의 도구 결과 파일은 읽지 않는다.

- 세션 시작 시각이 그날 끝 이후이거나, 보관할 때 원본의 수정 시각이 그날 시작 이전이면 열지 않는다.
- 연 파일에서는 행의 시각이 그날(한국 시간 자정 기준)인 행만 쓴다. 시각이 없는 행은 파일에서 바로 앞에 읽은 행의 시각을 따른다. 대화록에 넣지 않는 행의 시각도 센다. 여러 날에 걸친 세션은 날마다 나뉜다.
- 목록의 `file`은 프로젝트 폴더 안의 경로여야 한다. `..`이나 드라이브 문자가 든 경로, 프로젝트 폴더부터 보관본까지 링크(정션 포함)를 거치는 경로는 읽지 않고 경고로 남긴다. 다른 프로젝트의 보관본이 섞이지 않게 하기 위해서다.
- `originals`, 프로젝트 폴더, `project.json`, `index.jsonl`이 링크인지는 읽기 전에 본다. 프로젝트 ID로 찾을 때 링크인 폴더와 링크인 `project.json`은 열지 않고 건너뛴다. `originals`나 `index.jsonl`이 링크이면 오류로 끝난다. 하드 링크는 가리지 못한다.
- 한 행이 8 MiB를 넘으면 그 행은 읽지 않는다. 줄 끝까지 적혀 있는데 JSON이 아닌 행도 읽지 못한다. 둘 다 행 번호에는 센다. 그 행이 그날에 있거나 있을 수 있으면 경고를 낸다. 행의 시각을 읽지 못하므로, 바로 앞 행의 시각이 그날이면 그날의 행으로 본다. 앞 행의 시각이 그날 전이면, 다음에 시각이 적힌 행이 그날 시작 이후이거나 그런 행 없이 파일이 끝날 때 그날에 있을 수 있다고 본다. 빈 줄은 세지 않는다.
- 줄 끝 없이 끝나는 마지막 행은 읽지 않고 경고도 내지 않는다. 도구가 쓰고 있는 세션의 보관본은 그렇게 끝날 수 있다. 그 행이 8 MiB를 넘을 때는 경고가 난다("알려진 한계").

### 세션

말한 쪽은 파일이 아니라 세션 단위로 정한다.

- **Codex:** 목록의 세션 ID가 같은 파일은 한 세션이다. Codex가 세션 파일을 `archived_sessions/`로 옮기거나 한 세션을 두 번째 파일에 이어 쓰면 보관본이 둘이 된다. 2026-11-24에 이 PC의 보관본 367개 중 한 세션이 두 파일에 나뉘어 있었다. 한 파일이라도 그날 범위에 들면 그 세션의 파일을 모두 읽는다. 사람이 글을 쳤는지를 세션 전체에서 보기 위해서다.
- **Claude Code:** 파일 하나가 한 세션이다. 하위 에이전트 기록은 본 세션의 세션 ID를 갖고 있지만 따로 센다. 세션 ID는 보관 경로에서 읽는다. 본 세션 파일은 `claude/<폴더>/<세션 ID>.jsonl.zst`이고 하위 에이전트 기록은 `claude/<폴더>/<세션 ID>/subagents/` 아래에 있다. 목록의 `session`은 본 세션 파일에서 세션 ID가 적힌 첫 행의 값이라, 도구가 이어받은 세션의 행을 파일 앞에 복사해 두면 그 세션의 ID가 된다. 그래서 쓰지 않고, 경로의 ID와 다르면 경고를 낸다.
- 같은 글이 세션의 파일에 두 번 적혀 있으면 한 번만 센다. Codex는 항목 ID(`item.id`), Claude Code는 행의 `uuid`, Claude Code의 도구 결과는 `tool_use_id`로 가린다. 첫 사본이 비어 있으면 글이 있는 사본을 쓴다.
- 사본은 모두 사람 글이어야 한다. 대화록에 넣지 않는 행도 사본으로 센다. 다른 세션의 ID가 적힌 행, 세션 ID가 없는 행, `isMeta`인 행, 작업 알림 같은 행이 사람 글과 같은 ID를 갖고 있으면 그 글은 `다른 세션의 지시`가 되고 경고가 난다. 그런 행에 든 도구 결과도 같은 `tool_use_id`의 결과의 사본으로 센다. 질문 창에서 고른 답은 사본이 엇갈리면 블록을 만들지 않고 경고만 낸다. 다른 세션이 보낸 지시가 아니기 때문이다. 사본이 모두 고른 답이라고 해도 답의 글이 서로 다르면 엇갈린 것이다.
- 세션의 파일 가운데 하나라도 읽지 못하면 그 세션에는 `사람`이 없다. 읽지 못한 파일의 사본이 무엇이라고 하는지 알 수 없기 때문이다. 사람 표시가 있던 글은 `다른 세션의 지시`가 되고 경고가 난다. AI의 답은 `AI`로 남는다.
- 세션에 사람 글이 하나도 없으면 에이전트 실행이다. 두 도구에 같은 규칙을 쓴다. `codex exec`, Codex 하위 에이전트(첫 행의 `source`가 객체이거나 `exec`), Claude Code 하위 에이전트는 파일이 스스로 프로그램이 시작했다고 적은 세션이라 처음부터 에이전트 실행이다.
- 에이전트 실행은 그날 마지막 답만 남긴다. 마지막 답은 시각이 가장 늦은 답이고, 시각이 같으면 파일에서 뒤에 있는 답이다. Claude Code가 그 답을 여러 행에 나눠 적었으면(같은 `message.id`) 그날의 행을 시각 순서로 이어 첫 행의 자리에 둔다.

### 말한 쪽

| 표시 | 무엇인가 |
| --- | --- |
| 사람 | 사람이 친 글, 질문 창에서 고른 답(질문과 함께) |
| AI | 사람이 글을 친 세션에서 AI가 보여 준 답 |
| 에이전트 실행 | 아무도 글을 치지 않은 세션의 그날 마지막 답 |
| 검사 출력 | 실패한 명령의 종료 코드와 진단 줄 |
| 다른 세션의 지시 | 다른 세션이나 자동 실행이 보낸 글 |

다음 단계는 `사람` 블록을 사람이 그렇게 말했다는 근거로 쓴다. 그래서 `사람`은 파일에 적힌 표시가 모두 맞고 어긋나는 표시가 하나도 없을 때만 붙인다. 표시가 없거나 엇갈리면 `사람`이 아니다. 모델이 추측하지 않는다.

**Codex.** 화면에 보인 항목(`event_msg`의 `item_completed`)만 읽는다. 사용자 발화(`UserMessage`)가 `사람`이려면 다음이 모두 맞아야 한다.

1. 행의 `thread_id`가 이 세션의 ID다. 다른 세션의 ID가 적힌 행은 포크가 부모에게서 복사한 것이므로 버린다. `thread_id`가 없는 행도 버리고 경고를 낸다.
2. `client_id`가 있다. 없으면 `다른 세션의 지시`다.
3. 같은 항목 ID의 사본이 모두 위 둘에 맞는다. 하나라도 어긋나면 `다른 세션의 지시`로 두고 경고를 낸다.
4. 세션의 파일을 모두 읽었다.

세션의 ID와 누가 시작했는지는 파일의 첫 행(`session_meta`)에서만 읽는다. 포크는 둘째 행에 부모의 `session_meta`를 갖고 있다.

2026-11-24에 이 PC의 보관본으로 확인했다. 앱에서 사람이 연 세션의 발화 346개에는 모두 `client_id`가 있었다. `codex exec`, 하위 에이전트, 자동 실행이 쓴 발화 722개에는 하나도 없었다. CLI 0.164부터 0.169.1까지 같았다. 필드의 뜻을 Codex 문서로 확인한 것은 아니다. 포크 115개는 부모의 글을 `response_item` 행으로만 복사했고 `item_completed` 행으로는 복사하지 않았다. `thread_id`가 없는 항목과 같은 ID가 두 번 나온 항목은 없었다.

**Claude Code.** `user` 행의 글이 `사람`이려면 다음이 모두 맞아야 한다.

1. 행의 `sessionId`가 보관 경로에 적힌 이 세션의 ID다. 다른 세션의 ID가 적힌 행은 버린다. `sessionId`가 없는 행도 버리고 경고를 낸다.
2. 본 세션 파일의 행이고 `isSidechain`, `isMeta`, `isCompactSummary`가 아니다.
3. `origin.kind`가 `human`이다. `origin`이 없거나 `kind`를 읽을 수 없으면 `사람`이 아니다.
4. `turnOrigin`이 없거나 `human`이다.
5. 같은 `uuid`의 행이 모두 위 넷에 맞는다. 하나라도 어긋나면 `다른 세션의 지시`로 두고 경고를 낸다.
6. 세션의 파일을 읽었다.

- `turnOrigin`이 `host_synthetic`이면 `origin`이 무엇이든 `다른 세션의 지시`다.
- 그 밖의 `user` 행은 쓰지 않는다. 작업 알림, 슬래시 명령의 출력, 중단 표시(`[Request interrupted by user]`)가 여기에 든다. 표시가 없는 이런 행이 앱의 것인지는 글로 가린다. 슬래시 명령과 그 출력은 글의 시작(`<command-name>`, `<local-command-`)으로, 중단 표시는 글 전체가 `[Request interrupted by user]`나 `[Request interrupted by user for tool use]`와 같은지로 본다. 중단 표시로 시작하는 글은 사람이 쓸 수 있으므로 시작만으로는 앱의 글로 보지 않는다.
- 도구 결과(`tool_result`)는 사람 글이 아니다. 한 행에 도구 결과와 글(`text`)이 함께 있으면 글은 위 규칙으로 따로 본다.
- `AskUserQuestion`의 결과 행은 사람이 질문 창에서 고른 답을 갖고 있다. 블록의 글은 행의 `toolUseResult.answers`에서 만든다. 질문마다 `질문: …`과 `고른 답: …` 두 줄이고, 질문은 `toolUseResult.questions`의 순서다. 도구 결과의 글(`tool_result.content`)은 도구가 쓴 문구라서 쓰지 않는다. 고르지 않은 선택지를 인용할 수 있기 때문이다. 질문 문구는 AI가 쓴 것이고 고른 답만 사람의 것이다. 고른 답은 블록의 글과 따로, 답마다 통째로 블록에 함께 둔다(`Block`의 `picked`). 어디까지가 답인지를 글에서 다시 읽어 내지 않기 위해서다.
- 고른 답은 다음이 모두 맞을 때만 `사람`이다. 본 세션 파일의 행이다. 그 행에 `AskUserQuestion` 결과가 하나뿐이다(`answers`가 어느 질문의 것인지 행에 적혀 있지 않다). 그 결과가 `is_error`가 아니다. `answers`에 비어 있지 않은 문자열 답이 하나 이상 있다. `origin`과 `turnOrigin`이 다른 쪽을 가리키지 않는다. 같은 `tool_use_id`의 결과가 모두 이에 맞고, 만들어진 블록의 글(질문과 고른 답)이 서로 같다. `isMeta`인 행이나 다른 세션의 ID가 적힌 행처럼 쓰지 않는 행에 든 결과도 센다. 하나라도 아니면 블록을 만들지 않는다. 사본이 엇갈린 경우에는 경고를 낸다.
- 앱은 사람 글 앞에 `<system-reminder>…</system-reminder>` 알림을 넣는다. 사람 글의 `text` 블록 앞에 따로 둔 `text` 블록이다. 그래서 `content`가 블록 목록일 때, 글 전체가 짝을 이룬 알림뿐인 `text` 블록을 앞에서부터 뺀다. 목록의 마지막 블록은 빼지 않는다. 마지막인지는 이미지 같은 다른 종류의 블록까지 세어 본다. 그래서 `[알림, 이미지]`에서는 알림이 빠져 사람 글이 남지 않고, 블록이 알림 하나뿐인 글은 사람이 쓴 것으로 남는다. 사람 글의 블록 안에 있는 태그와, `content`가 문자열 하나인 글의 태그는 사람이 쓴 것이므로 그대로 둔다.
- `다른 세션의 지시`는 문자열 하나가 알림으로 시작한다. 맨 앞에 짝을 이룬 알림만 뺀다. 가운데와 끝의 태그, 닫히지 않은 태그는 그대로 둔다.
- AI의 답 한 행에 `text` 블록이 여럿이면 한 블록으로 잇는다. 답 하나가 여러 행에 나뉘어 있으면(같은 `message.id`) 행마다 블록 하나다. 행마다 `uuid`, 행 번호, 시각이 따로 있어서, 다시 적힌 행을 한 번만 세고 자정을 넘긴 행을 제 날짜에 둘 수 있다. 에이전트 실행의 마지막 답만 그날의 행을 잇는다.

2026-11-24에 이 PC의 본 세션 12개(Claude Code 2.1.325~2.1.330)로 확인했다. `origin.kind`가 `human`인 행은 119개였다. 두 필드가 모두 없는 일반 행 20개는 모두 앱이 쓴 것이었다(슬래시 명령 11개, 그 출력 8개, 중단 표시 1개. 중단 표시의 글 전체는 `[Request interrupted by user]`였다). 도구 결과 행 3,393개에는 `origin`이 하나도 없었다. `AskUserQuestion` 결과 행은 4개였다. 모두 결과가 하나였고 `answers`는 질문 문구에서 답 문자열로 가는 표였으며(답 1~4개), 질문은 모두 `questions`에 있었다. 본 세션 12개 모두 목록의 `session`과 첫 행의 `sessionId`가 파일 이름과 같았다. 하위 에이전트 기록 13개의 대화 행 1,085개는 모두 경로의 세션 ID를 갖고 있었다. 한 파일에 같은 `uuid`가 두 번 나온 행과, 같은 `message.id`의 글이 두 행에 나뉜 답은 없었다. 같은 `tool_use_id`의 결과가 두 번 적힌 파일도 없었다. `origin.kind`가 `human`인 행 119개는 `content`가 문자열인 행 110개, `text` 블록 둘인 행 6개, 이미지 블록 뒤에 `text` 블록이 온 행 3개였다. 알림 태그가 든 행은 `text` 블록이 둘인 6개였고, 첫 블록은 짝을 이룬 알림뿐(알림 9개)이고 둘째 블록이 사람 글이었다. 사람 글의 뒤나 가운데에 든 알림은 없었고, `content`가 문자열인 110개에는 태그가 없었다. `host_synthetic` 행 34개는 문자열이 알림 1~3개로 시작했다.

**경고.** 사람 판정을 믿기 어렵거나 글이 빠졌을 수 있는 세션은 경고로 알린다. 그 세션의 파일에 그날 시각의 행이 하나라도 있으면, 그날 남은 블록이 없어도 경고는 남는다. 대화록에 넣지 않는 행도 센다. 그날 시각의 행이 없는 날에는 내지 않는다.

- 앱이나 터미널에서 사람이 연 것으로 보이는 Codex 세션(`source`가 `vscode`나 `cli`, `thread_source`가 `user`)에 발화는 있는데 `client_id`가 있는 발화가 없다. Codex가 이 필드를 없애면 사람 글이 0개로 나오기 때문이다.
- Claude Code 본 세션에 `origin`도 `turnOrigin`도 적힌 행이 하나도 없는데 일반 글이 있고, 사람 글로 센 글이 없다. 이 필드가 생기기 전 버전의 파일이다. 사람 글을 가릴 수 없으므로 에이전트 실행으로 센다.
- Claude Code 본 세션의 그날 행 가운데 `origin`도 `turnOrigin`도 없는 일반 글이 있다. 앱이 쓴 것으로 아는 글(슬래시 명령과 그 출력, 글 전체가 중단 표시인 글)은 세지 않는다. 중단 표시로 시작하고 다른 글이 이어지는 행은 센다. 같은 파일의 다른 행에 표시가 있어도 낸다. 이전 버전에서 시작한 세션을 새 버전에서 이어 쓰면 앞쪽 사람 글이 이렇게 빠진다. 위 경고가 난 세션에는 따로 내지 않는다.
- 프로그램이 시작한 세션에 사람 표시가 있는 글이 있다. 에이전트 실행으로 센다.
- Codex 파일에 `UserMessage` 항목이 하나도 없는데 그날 `event_msg`의 `user_message` 행이 있다. 예전 Codex는 사람 글을 이 형식으로만 적었을 수 있고, 이 형식에는 누가 쳤는지 표시가 없어 읽지 않는다. 지금 형식은 같은 글을 `user_message`와 `UserMessage` 항목에 함께 적으므로 경고가 나지 않는다. 이 PC의 보관본(CLI 0.164~0.169.1)에는 `user_message` 행이 없다.
- 같은 글의 사본끼리 사람 표시가 다르거나, 질문 창에서 고른 답의 사본끼리 답이 다르다. 세션 ID가 없는 행이 있다. 시각을 알 수 없는 글이 있다.
- 8 MiB를 넘거나 JSON이 아니어서 읽지 않은 행이 그날에 있거나 있을 수 있다.
- Claude Code 파일에서 목록의 세션 ID가 경로의 세션 ID와 다르다.
- 세션의 파일을 읽지 못했다. 파일마다 경고가 하나 나고, 사람 표시가 있던 글이 있으면 세션에도 하나 난다. 읽지 못한 파일에 그날의 행이 있는지 알 수 없으므로, 목록으로 보아 세션이 걸칠 수 있는 날마다 낸다.

### 남기는 것과 버리는 것

도구 출력, 추론, 같은 내용의 복사본(Codex의 `response_item`, 압축 요약, Claude Code의 API 요청 사본), 시스템이 넣은 글은 버린다. 사람과 AI의 글은 거르지 않는다.

실패한 명령은 종료 코드와 진단 줄을 세 줄까지만 남긴다. 줄을 고르는 규칙은 `chat_history/command.rs`에 있다. 따옴표, `=`, 주소, `token` 같은 낱말이 든 줄은 비밀값일 수 있으므로 뺀다. 출력을 통째로 옮기는 경우는 없다. TAP 형식의 테스트 출력에서는 실패한 테스트 줄(`not ok`)과 `# fail` 줄을 진단 줄로 본다. Claude Code의 종료 코드는 행의 `toolUseResult.exitCode`에서 읽는다. 행에 도구 결과가 하나일 때만이다. 거기서 읽지 못하고 결과가 `is_error`이면 결과 글의 `Exit code N`에서 읽는다. `is_error`가 아닌 결과의 글에서는 읽지 않는다.

블록 하나에 남기는 글자 수는 다음과 같다. 넘치면 자르고 끝에 `…`를 붙인다.

| 표시 | 상한 | 근거 |
| --- | --- | --- |
| 사람 | 8,000자 | 2026-11-24에 가장 긴 사람 글이 6,093자였다 |
| AI | 4,000자 | AI 답의 99%가 3,359자 이하였다 |
| 에이전트 실행 | 2,000자 | 실행의 지시문(합계 5.6M자)은 버리고 답만 남긴다 |
| 검사 출력 | 1,000자 | 진단 줄은 세 줄, 한 줄 400자까지다 |
| 다른 세션의 지시 | 500자 | 어떤 지시였는지만 남긴다 |

### 형식

블록은 시각 순서다. 블록마다 번호와 출처 번호(`S1`, `S2`, …)가 붙는다. 프로그램은 번호마다 보관본 파일과 압축을 푼 파일의 행 번호(1부터)를 갖는다.

```text
# 하루 대화록 · TimeSchedule · 2026-11-24

## 출처

S1 · claude · claude-desktop · 사람이 연 세션
S2 · codex · codex_exec · 에이전트 실행

## 대화

[1] 09:14 사람 · S1
…

[2] 09:20 에이전트 실행 · S2 (그날 마지막 답)
…
```

`[번호] 시:분 `으로 시작하는 줄은 블록의 머리말뿐이다. 글 안에 그런 모양으로 시작하는 줄이 있으면 앞에 `> `를 붙인다. AI가 대화록을 인용한 글을 실제 사람 블록으로 읽지 않게 하기 위해서다. 글의 줄 끝(`\r\n`, `\r` 등)은 모두 `\n`으로 바꾼다. 글의 앞과 뒤에서는 빈 줄(공백뿐인 줄)만 뺀다. 첫 줄의 들여쓰기와 마지막 줄 끝의 공백은 그대로 둔다. 말한 쪽이 누구든 같다. 사람 글은 쓴 그대로여야 하고, AI의 답도 코드로 시작하면 들여쓰기가 뜻을 갖기 때문에 규칙을 둘로 나누지 않았다. 질문 창에서 고른 답도 같은 방법으로 다듬어 `고른 답: ` 뒤에 붙인다. 프로젝트 제목과 출처 줄의 도구, 연 프로그램은 줄 끝을 빈칸으로 바꿔 한 줄로 쓴다. 제목이나 목록의 값에 든 줄이 머리말처럼 보이지 않게 하기 위해서다.

## 하루 기록

`--dry-run` 없이 실행하면 하루 대화록을 모델에 한 번 보내 하루 기록을 만들고 문서 저장소에 남긴다.

모델의 답은 사실이 아니라 주장으로 다룬다. 답의 모양을 먼저 확인하고, 인용한 블록이 실제로 있는지 보고, 사람이 제안했거나 정했다는 주장은 사람이 쓴 글귀가 인용되어 있을 때만 남긴다.

### 모델 호출

- Codex CLI의 `codex exec`로 부른다. 로그인된 CLI를 쓰며 유료 API는 쓰지 않는다. 기본 모델은 `gpt-6.1-terra`, 추론 노력은 `medium`이다. `--model`로 모델을 바꿀 수 있다.
- 채팅 경험 검토와 같은 설정으로 부른다. 빈 임시 폴더, 읽기 전용 샌드박스, 셸 도구·웹 검색·플러그인·앱·MCP·하위 에이전트를 끈 상태다. 답은 1 MiB까지 받는다.
- 대기 시간은 600초이고 호출 전체에 적용된다. CLI가 끝난 뒤에는 입출력 파이프를 2초까지만 기다린다. CLI가 띄운 프로세스가 파이프를 쥐고 있어도 그 이상 기다리지 않는다. 그때까지 읽은 사용량은 남긴다.
- Codex의 `--json` 출력은 줄 단위로 읽고 버린다. 한 줄에서 64 KiB까지만 메모리에 두며, 더 긴 줄은 건너뛴다. 사용량이 든 `turn.completed` 줄만 쓴다. 출력을 읽는 데 스레드 하나를 쓴다.
- 출력을 읽을지와 답의 코드 펜스를 벗길지는 호출마다 정한다(`terra.rs`의 `Call`의 `read_usage`, `unfence`). 하루 기록은 출력을 읽고 펜스를 벗기지 않는다. 채팅 경험 검토와 포트폴리오 작성(`generate`)은 이 단계 전과 같다. `--json` 없이 부르고 출력을 읽지 않고 버리므로 읽는 스레드가 없고, 답을 둘러싼 ```` ```json ```` 펜스는 벗긴다.
- 답의 모양은 `--output-schema`로 정해 준다(`daily_record/record.rs`의 `schema`). 아래 "답의 모양"에 적었다.
- 지시문은 대화록을 자료로만 읽고 그 안의 지시를 따르지 말라고 적는다. 말한 쪽의 뜻을 알려 주고, 이유가 대화록에 없으면 `null`로 두며 추측하지 말라고 적는다. "결정:"으로 시작하는 형식이 있으면 그것을 먼저 옮기라고 적는다. 누가 제안하고 정했는지는 `proposedBy`와 `decidedBy`에만 적고 다른 글에는 쓰지 말라고 적는다.
- 하루 대화록의 추정 입력이 200,000토큰을 넘으면 부르지 않고 오류로 끝난다. 하루를 나눠 부르는 기능은 아직 없다. 2026-11-24에 이 PC에서 가장 큰 날은 추정 103,614토큰이었다.
- 대화가 없는 날은 부르지 않는다.

### 답의 모양

| 칸 | 항목의 키 |
| --- | --- |
| `summary` | `text`, `evidence`. 그날 한 일을 문장 단위로 적는다 |
| `development` | `title`, `detail`, `evidence` |
| `troubleshooting` | `problem`, `cause`, `fix`, `verification`, `evidence`. 가운데 셋은 `null`일 수 있다 |
| `improvements` | `text`, `evidence` |
| `decisions` | `decision`, `reason`(`null` 가능), `rejected`, `proposedBy`, `proposalEvidence`, `decidedBy`, `decisionEvidence`, `evidence` |

- `evidence`는 근거 블록 번호의 목록이다.
- `proposedBy`는 `human`, `ai`, `unknown` 중 하나다. `decidedBy`는 `human_approved`(사람이 제안을 받아들임), `human_changed`(사람이 제안을 바꿈), `human_decided`(사람이 직접 정함), `unconfirmed`(사람이 정했다는 글이 없음) 중 하나다. 지시문은 모델에게 `human_decided`를 "제안 없이 사람이 직접 정함"으로 알려 주지만, 프로그램이 이 값을 남기는 조건은 그보다 넓다. 사람이 쓴 글귀가 결정 근거로 인용되어 있고 그 블록이 가장 이른 제안 블록보다 앞서지 않으면 남는다. AI의 제안이 먼저 인용되어 있어도 같다. 제안이 없었는지는 프로그램이 확인하지 않는다.
- `proposalEvidence`는 제안이 처음 나온 블록, `decisionEvidence`는 정한 블록이다. 둘 다 `{block, quote}`의 목록이다. `quote`는 그 블록의 글에서 한 군데를 글자 그대로 옮긴 글귀다. 결정의 `evidence`에는 이유나 버린 대안처럼 그 밖의 근거를 적는다.
- 다섯 칸과 항목의 키는 모두 있어야 하고 다른 키는 없어야 한다. `null`일 수 있는 키도 빠지면 안 된다.

### 답을 확인하는 규칙

**통째로 버리는 답.** 다음 중 하나라도 해당하면 답 전체를 버리고 기록을 만들지 않는다. 이미 있는 기록은 그대로 둔다.

- 답이 JSON이 아니거나 위 모양과 다르다. CLI가 적은 답을 고치지 않고 그대로 확인한다. JSON을 ```` ```json ```` 펜스로 둘러싼 답도 JSON이 아니므로 버린다. 구조체로 읽기 전에 답의 JSON을 `schema`와 직접 대조한다. 객체 자리의 배열, 빠진 키, 모르는 키, 정해진 값이 아닌 `proposedBy`·`decidedBy`, 정수가 아닌 블록 번호가 모두 여기에 든다.
- 대화록에 없는 블록 번호를 어디에서든 근거로 들었다. 요약, 네 목록, 결정의 세 근거 목록이 모두 해당한다.

**빼는 항목.** 근거 블록이 하나도 없는 항목과 요약 문장은 뺀다. 결정은 세 근거 목록이 모두 비었을 때 뺀다. 뺀 수를 `checks.withoutEvidence`에 적는다.

**글귀.** `proposalEvidence`와 `decisionEvidence`의 항목은 `quote`가 그 블록을 말한 쪽이 쓴 글에 들어 있을 때만 근거로 센다.

- 글귀와 블록의 글은 연속한 공백과 줄바꿈을 빈칸 하나로 바꿔 비교한다. 그 밖에는 글자가 같아야 한다.
- 질문 창 블록(`질문: …`과 `고른 답: …`)에서는 고른 답만 사람의 글이다. 질문 문구는 AI가 쓴 것이므로 거기서 옮긴 글귀는 세지 않는다. 글귀는 블록의 글에 있어야 하고, 블록에 따로 둔 고른 답 가운데 하나에도 들어 있어야 한다. 답의 경계를 블록의 글에서 읽어 내지 않으므로, 블록이 잘려 다음 질문의 `질문:`만 남아도 그 이름표가 사람의 글이 되지 않는다. `질문: `이나 `고른 답: ` 같은 이름표, 질문 문구, 두 답에 걸친 글귀는 세지 않는다.
- 글귀가 비었거나 300자를 넘으면 세지 않는다.
- 대화록에서 잘린 블록의 끝에 프로그램이 붙인 `…`는 말한 쪽이 쓴 글이 아니다. 그 표시를 뗀 글과 비교하므로, `…`만 옮기거나 잘린 끝을 `…`까지 옮긴 글귀는 세지 않는다. 잘리지 않은 블록에서 말한 쪽이 직접 쓴 `…`는 그 사람의 글이다. 잘리기 전의 글 전체를 따로 두고 비교하지는 않는다. 모델이 읽은 것은 잘린 글뿐이라, 잘린 뒤쪽과 맞는 글귀는 모델이 읽고 옮긴 것일 수 없기 때문이다.
- 세지 않는 항목도 기록에는 남기되 `quote`를 `null`로 둔다. 그 수를 `checks.quotesNotFound`에 적는다.

**제안한 쪽.** 제안 근거 가운데 글귀가 맞은 것만 본다. 그중 번호가 가장 이른 블록이 "가장 이른 제안 블록"이다. 블록 번호는 시각 순서다. 글귀가 맞지 않은 제안 근거는 기록에 남기만 하고, 누가 제안했는지와 아래의 순서 비교에 쓰지 않는다. 모델이 제안 블록의 번호를 잘못 적었을 때 그 번호가 순서의 기준이 되지 않게 하기 위해서다.

- `human`은 가장 이른 제안 블록이 사람이 친 글일 때만 남는다. 질문 창에서 고른 답은 AI가 낸 선택지를 고른 것이라 사람의 제안으로 세지 않는다.
- `ai`는 가장 이른 제안 블록이 `AI`나 `에이전트 실행`일 때만 남는다.
- 맞지 않거나 글귀가 맞은 제안 근거가 하나도 없으면 `unknown`으로 바꾸고 `checks.proposedByUnsupported`에 센다.

**정한 쪽.** 사람이 정했다는 값은 결정 근거에 글귀가 맞는 `사람` 블록이 있을 때만 남는다. 질문 창에서 고른 답도 사람의 결정으로 센다. `다른 세션의 지시`와 `에이전트 실행`은 사람 블록이 아니다.

- 그 사람 블록은 가장 이른 제안 블록보다 앞설 수 없다. 아직 나오지 않은 제안을 정할 수는 없기 때문이다. 모델이 두 목록을 뒤바꾸거나 관계없는 앞쪽 사람 글을 든 경우가 여기서 걸린다.
- `human_approved`와 `human_changed`는 글귀가 맞은 제안 근거가 있어야 하고, 사람 블록이 가장 이른 제안 블록보다 뒤여야 한다. 모델이 1번을 제안으로 잘못 들고 실제 제안은 5번, 사람 글은 3번이면, 1번은 글귀가 맞지 않아 빠지고 3번은 5번보다 앞서므로 `unconfirmed`가 된다. 제안만 한 글이 그 제안의 승인으로 함께 쓰이지 않게 하기 위해서다. 사람이 "B안을 검토해 줘"라고 하고 AI가 "B안으로 적용했습니다"라고 답한 날은 제안한 쪽이 사람, 정한 쪽이 `unconfirmed`가 된다.
- `human_decided`는 사람 블록이 가장 이른 제안 블록과 같아도 된다. 사람이 한 글에서 말하고 정한 경우다. 글귀가 맞은 제안 근거가 하나도 없으면 순서를 비교할 제안이 없으므로, 글귀가 맞는 사람 블록만 있으면 남는다.
- 맞지 않으면 `unconfirmed`(확인 기록 없음)로 바꾸고 `checks.decidedByUnsupported`에 센다.

값을 바꾼 결정에는 모델이 답한 값을 `claimedProposedBy`, `claimedDecidedBy`로 남긴다. 그 결정의 본문에 모델의 원래 주장이 남아 있을 수 있음을 알리기 위해서다.

이유가 비어 있으면 `null`로 두고 다이어리에는 "이유 기록 없음"으로 적는다.

### 저장

`<문서 저장소>/daily/<originals와 같은 프로젝트 폴더 이름>/<YYYY-MM-DD>.json`에 쓴다. 근거는 블록 번호, 말한 쪽, 질문 창 블록인지(`picked`), 출처 번호, 보관본 파일, 압축을 푼 파일의 행 번호, 시각으로 남긴다. 원문 글은 옮기지 않는다. 예외는 제안과 결정 근거의 글귀로, 300자까지 남긴다. 출처 목록과 대화록의 경고, 블록 수, 글자 수도 함께 남긴다.

- **한 번에 한 실행.** 프로젝트와 날짜마다 잠금 파일(`.<날짜>.lock`)을 최신 판을 읽기 전부터 새 판을 내놓을 때까지 쥔다. 같은 날을 만드는 두 번째 실행은 기다리지 않고 모델도 부르지 않으며 `busy`로 끝난다(종료 코드 2). 첫 실행은 모델 답을 몇 분씩 기다릴 수 있고, 두 번째 실행이 할 일이 있는지는 첫 실행의 결과가 나와야 알 수 있기 때문이다. 나중에 다시 실행하면 된다. 잠금은 프로세스가 끝나면 풀린다.
- **같은 입력.** 마지막 판과 지문(`input.fingerprint`)이 같으면 모델을 부르지 않는다(`unchanged`). 지문은 FNV-1a 해시이고 다음을 모두 넣는다. 지시문 판 번호(`PROMPT_VERSION`), 모델, 추론 노력, 스키마, 모델에 보내는 글 전체(지시문과 대화록), 블록마다 번호·말한 쪽·출처 번호·보관본 파일·행 번호·초 단위 시각, 블록의 글과 잘렸는지, 질문 창 블록의 고른 답, 대화록의 경고. 모델이 읽는 글이 같아도 인용할 행 번호나 파일이 달라지면 새로 만든다. 블록의 글을 따로 넣는 것은 글귀를 대화록이 아니라 블록의 글과 비교하기 때문이다. 대화록은 서로 다른 글을 같게 보일 수 있다. `> [1] 09:20 승인`과 `[1] 09:20 승인`은 대화록에서 같은 줄이 된다("형식").
- **이전 판.** 새 판을 내놓기 전에 지금의 최신 판을 `<날짜>.r<판 번호>.json`으로 남긴다. 남기는 파일도 새 파일도 임시 파일에 다 쓴 뒤 제자리로 옮긴다. 그 이름의 파일이 이미 있고 최신 판과 내용이 같으면 앞선 실행이 거기까지 하고 멈춘 것으로 보고 이어서 한다. 내용이 다르면 아무것도 바꾸지 않고 오류로 끝난다. 이 확인은 모델을 부르기 전에 한 번, 내놓기 직전에 한 번 한다.
- 이전 판에서는 판 번호와 지문만 읽는다. 기록의 모양이 바뀌어도 이어서 판을 쌓을 수 있다.
- `daily`나 프로젝트 폴더가 링크이면 쓰지 않는다.
- 새 판을 내놓기 직전에 그날의 최신 판을 다시 읽는다. 모델을 부르기 전에 읽은 것과 다르면(없던 파일이 생겼거나 내용이 바뀌었으면) 새 판을 쓰지 않고 오류로 끝나며 그 자리의 파일은 그대로 둔다. 날짜별 잠금은 이 프로그램의 다른 실행만 막고, 사람이 백업을 되돌려 놓는 것 같은 일은 막지 못하기 때문이다. 그 호출의 사용량은 `save_failed`로 남는다. 다시 읽은 뒤 옮겨 쓰기까지의 아주 짧은 사이에 바뀌는 것은 막지 못한다.
- 최신 판(`<날짜>.json`)이나 남겨 둔 판(`<날짜>.r<판 번호>.json`)이 링크이면 읽지 않고 오류로 끝난다. 모델을 부르지 않고 기록도 바꾸지 않는다. 남겨 둔 판의 이름이 최신 판을 가리키는 링크이면 링크를 따라 읽은 내용이 언제나 최신 판과 같아서, 그대로 두면 새 판을 내놓은 뒤 두 이름이 모두 새 판을 읽게 되고 이전 판이 사라지기 때문이다. 하드 링크는 가리지 못한다. 새 파일은 임시 파일을 그 이름으로 옮겨 쓰므로 하드 링크의 다른 이름에는 이전 내용이 남는다.

### 사용량

- Codex가 `--json` 출력의 `turn.completed`에 적는 입력·캐시 입력·출력·추론 토큰을 남긴다. Codex가 적지 않은 값은 `null`이다. 0은 Codex가 0이라고 적은 경우뿐이다. 걸린 시간(초)도 남긴다.
- 기록 파일의 `usage`에는 그 판을 만든 호출의 사용량이 있다.
- 모델을 부른 호출은 답이 어떻게 되었든 `daily/<프로젝트 폴더>/usage.jsonl`에 한 줄씩 덧붙인다. 지우거나 고쳐 쓰지 않는다. 한 줄의 키는 `at`(기록한 시각, UTC), `date`(하루 기록의 날짜), `model`, `effort`, `promptVersion`, `outcome`, `revision`(`saved`일 때만), 토큰 값 넷, `seconds`, `message`(실패한 이유, 한 줄 500자까지)다.
- `outcome`은 `saved`(새 판을 남김), `refused`(답을 확인 규칙이 버림), `save_failed`(답은 통과했으나 파일을 쓰지 못함), `call_failed`(CLI가 실패하거나 시간을 넘김) 중 하나다. 실패한 호출도 그때까지 Codex가 알린 사용량과 걸린 시간을 적는다.
- 기록을 쓰지 못한 호출의 사용량 줄까지 쓰지 못하면 오류 글에 두 가지를 함께 적는다. 새 판을 남긴 뒤 사용량 줄만 쓰지 못하면 기록은 남아 있고 명령은 오류로 끝난다. 다시 실행하면 `unchanged`가 된다.
- 줄을 덧붙이기 전에 파일의 마지막 바이트를 본다. 줄 끝이 아니면 앞선 실행이 줄을 다 쓰지 못한 것이므로 줄 끝을 먼저 쓰고 새 줄을 쓴다. 쓰다 만 줄은 그대로 남고 JSON으로 읽히지 않는다. 그 뒤의 줄은 온전하다. 이 파일을 읽을 때는 JSON이 아닌 줄을 건너뛰어야 한다.
- 마지막 바이트를 보는 것부터 줄을 쓰는 것까지는 프로젝트의 잠금 파일(`.usage.lock`)을 쥐고 한다. `usage.jsonl`은 프로젝트의 모든 날짜가 함께 쓰는데 날짜별 잠금은 다른 날짜의 실행을 막지 않기 때문이다. 잠금이 없으면 마지막 바이트를 본 뒤에 다른 날짜의 실행이 줄을 쓰다 만 경우 두 줄이 한 줄로 붙는다. 이 잠금은 날짜별 잠금과 달리 풀릴 때까지 기다린다. 쥐는 시간이 한 줄을 쓰는 동안뿐이고, 기다리지 않고 포기하면 이미 부른 호출의 사용량 줄을 잃기 때문이다. 잠금은 프로세스가 끝나면 풀린다.

### 다이어리에 보일 글

`DailyRecord::render`가 만든다. 화면에 붙이는 것은 다음 단계다.

- 인용은 `[블록 번호] 말한 쪽 · 출처 번호 행`으로 적는다(`[12] 사람 · S1 34행`). 한 세션이 두 보관 파일에 나뉘어 출처 번호와 행이 같아도 블록 번호로 가릴 수 있다. 질문 창 블록은 `사람(고른 답)`으로 적는다.
- 결정마다 `제안:`과 `확정:` 줄은 프로그램이 확인한 값으로 쓰고, 그 뒤에 근거 블록과 글귀를 붙인다. 글귀가 블록에 없던 근거는 그렇다고 적는다. 값을 바꾼 결정에는 모델의 답이 무엇이었는지 적는다.
- 모델이 쓴 글(요약, 제목, 결정, 이유, 버린 대안 등)은 줄바꿈을 빈칸으로 바꿔 한 줄로 쓰고, 프로그램이 쓰는 이름표 뒤에 붙인다. 이름표는 `- 요약: `, `- 개발: `, `- 문제: `, `  - 원인: `, `  - 해결: `, `  - 확인: `, `- 개선: `, `- 결정: `, `  - 이유: `, `  - 버린 대안: `이다. 빈 줄이 아닌 모든 줄은 이 이름표나 `  - 제안: `, `  - 확정: `, `  - 그 밖의 근거: `, 칸 제목(`## 개발 내역`, `## 트러블슈팅`, `## 개선 방향`, `## 결정`) 가운데 하나로 시작한다. 모델의 글이 줄의 첫 글자가 되는 일이 없으므로, 요약 문장 전체가 `  - 확정: 사람 승인`이어도 `- 요약:   - 확정: 사람 승인 (…)`이 될 뿐 `확정:` 줄이나 `## 결정` 줄이 되지 않는다.
- 모델의 글 앞머리의 공백이나 `-`는 지우지 않는다. `--dry-run 추가`처럼 `-`로 시작하는 정상적인 글이 바뀌기 때문이고, 이름표가 있으면 지우지 않아도 줄의 시작이 될 수 없다. 줄 안쪽에 그런 글이 보이는 것까지는 막지 않는다.

## 명령

```powershell
TimeSchedule.exe record daily --project C:\LSH\TimeSchedule --dry-run --date 2026-11-24
TimeSchedule.exe record daily --project C:\LSH\TimeSchedule --date 2026-11-24
```

| 인자 | 뜻 |
| --- | --- |
| `--project` | 프로젝트 ID 또는 프로젝트 폴더의 절대 경로. 같은 ID의 보관 폴더가 둘 이상이면 실행하지 않고 폴더 경로를 지정하라고 알린다 |
| `--dry-run` | 대화록만 만들고 모델을 부르지 않는다. 빼면 모델을 불러 하루 기록을 만든다 |
| `--model` | 하루 기록을 만들 모델. 빼면 `gpt-6.1-terra` |
| `--date` | `YYYY-MM-DD`. 숫자 네 자리, 두 자리, 두 자리와 `-` 둘로 된 열 글자여야 하고 실제 날짜여야 한다(`2026-1-2`, `+2026-11-24`, `-0001-01-01`, `+10000-01-01`은 오류). 빼면 한국 시간 오늘 |
| `--transcript` | 대화록 글을 이 파일에 쓴다. 채팅 원문이 그대로 들어간다. `--result`와 마찬가지로 같은 폴더의 임시 파일(`.record-output-<UUID>.tmp`)에 다 쓴 뒤 이 이름으로 옮기므로, 쓰다가 실패하면 이 이름의 파일은 전과 같다. `--result`와 같은 경로이면 실행하지 않고, 그 파일에 아무것도 쓰지 않는다. 문서 저장소의 `daily`나 `originals` 폴더 안의 경로여도 같다. 경로의 대소문자와 상대 경로는 맞춰 본다. 파일 이름의 `:` 뒤는 NTFS 스트림 이름으로 보고 떼어 낸다(`day.md::$DATA`는 `day.md`). 경로에서 이미 있는 가장 가까운 상위 폴더까지를 링크(정션 포함)를 풀어 읽고 아직 없는 부분을 그 뒤에 붙여 비교하므로, 아직 없는 폴더 안의 파일을 정션을 거쳐 가리켜도 같은 경로로 본다. `daily`·`originals` 안인지 볼 때는 출력 이름 자체가 링크인 경우도 생각해, 링크를 따라간 곳과 함께 그 이름이 놓인 폴더(링크를 푼 것)에 이름을 붙인 곳도 본다. 쓰기는 링크가 가리키는 파일이 아니라 그 이름을 바꾸기 때문이다. 비교는 아무것도 쓰기 전에 한 번만 하고 결과 파일을 쓸지도 그 답으로 정한다. 하드 링크는 가리지 못한다 |
| `--data-dir`, `--result` | 다른 `record` 명령과 같다. 다만 `--result`가 문서 저장소의 `daily`나 `originals` 폴더 안의 경로이면 실행하지 않고, 그 파일에 아무것도 쓰지 않는다 |

문서 저장소는 채팅 원문 보관과 같은 방법으로 찾는다. 한 번의 실행에서 한 번만 찾고, 출력 파일의 위치를 확인할 때와 보관본을 읽고 기록을 쓸 때 그 경로를 함께 쓴다. 확인한 저장소와 실제로 쓰는 저장소가 달라지지 않게 하기 위해서다. 명령은 보관본을 새로 만들지 않는다. 앱이 마지막으로 보관한 데까지 읽고, 결과의 `latestArchived`에 가장 늦은 보관 시각을 적는다. 데이터 폴더가 없어도 만들지 않는다. 그때는 기본 위치의 문서 저장소를 읽는다.

앱에서 프로젝트의 폴더를 바꾸면 보관 폴더가 새로 생기고 이전 폴더도 남는다. 프로젝트 ID로는 어느 쪽인지 정할 수 없으므로 실행하지 않는다. 폴더 경로를 주면 그 폴더의 보관본만 읽는다.

인자가 틀리면 보관본을 읽기 전에 끝나고 종료 코드는 1이다. 오류는 표준 출력에 JSON으로 나온다. `--result` 파일에 쓰는지는 다음과 같다.

- 인자를 해석하지 못하면(모르는 인자, 값이 없는 인자, 중복 인자, `--project` 없음) 쓰지 않는다. 어느 파일이 결과 파일인지 믿을 수 없기 때문이다.
- `--result`가 `--transcript`와 같은 경로이면 쓰지 않는다. 앞서 만든 대화록을 오류로 덮어쓰지 않기 위해서다.
- `--result`나 `--transcript`가 문서 저장소의 `daily` 또는 `originals` 폴더 안을 가리키면 둘 다 쓰지 않는다. 하루 기록, 남겨 둔 판, 보관본을 출력 파일로 덮어쓰지 않기 위해서다. 경로는 위 `--transcript`와 같은 방법으로 풀어서 폴더와 비교한다. `--result`나 `--transcript`를 준 실행에서 문서 저장소의 위치를 확인하지 못하면(저장소 폴더나 `vault.json`이 없거나 읽히지 않음, 저장소 설정이 잘못됨) 이 비교를 할 수 없으므로 둘 다 쓰지 않는다. 오류는 표준 출력에만 나오고 종료 코드는 1이다. 기록 파일은 그대로 있는데 `vault.json`만 손상된 때에 `--result`가 가리키는 기록을 오류 JSON으로 바꾸지 않기 위해서다. 이때는 날짜 형식 같은 다른 인자 오류보다 이 오류가 먼저 나온다. 두 인자를 모두 주지 않은 실행은 이 확인을 하지 않는다.
- 그 밖의 오류(날짜 형식, 보관본 없음, 모델 호출 실패, 답 확인 실패 등)는 쓴다. 호출한 쪽이 지정한 결과 파일이고, 쓰지 않으면 이전 실행의 결과를 이번 것으로 읽을 수 있기 때문이다. 다른 `record` 명령도 오류를 결과 파일에 쓴다.

결과 JSON의 항목은 다음과 같다.

- `summary`: 사람이 글을 친 세션 수, 에이전트 실행 수, 말한 쪽별 블록 수, 대화록 글자 수, 말한 쪽별로 잘린 블록 수.
- `estimatedInputTokens`: 추정 입력 토큰. 글자 수를 3.3으로 나누고 호출 하나의 고정 입력 11,449토큰을 더했다. 3.3은 보관된 `codex exec` 62개에서 잰 3.66자당 1토큰을 한글이 많은 대화록에 맞게 낮춘 추정값이다. 11,449는 `gpt-6.1-terra`를 한 번 불러 잰 값이다.
- `sources`: 출처 번호별 보관본 파일 목록(`files`), 도구, 연 프로그램, 세션 ID.
- `record`: 하루 기록을 만들었을 때만 있다. 파일 경로, 판 번호, 모델, 사용량(`usage`), 확인 규칙이 바꾸거나 뺀 수(`checks`), 칸별 항목 수. 모델을 부르지 않은 `unchanged`이면 경로와 판 번호만, `busy`이면 경로만 있다.
- `outcome`: `dry_run`, `saved`(새 판을 남김), `unchanged`(같은 입력이라 부르지 않음), `busy`(다른 실행이 같은 날을 만드는 중이라 부르지 않음), `attention`(경고가 있음), `error`. 값은 하나만 나오며, 여럿에 해당하면 `error`, `busy`, `attention`, 나머지의 순서로 앞의 것이 나온다.
  - `error`(종료 코드 1): 실행이 끝까지 가지 못했다. `message`만 있다.
  - `busy`(종료 코드 2): 경고가 있어도 `busy`다. 이 실행은 기록을 만들지도 확인하지도 않았으므로 다시 실행해야 한다는 것이 먼저다. 경고는 `warnings`에 그대로 있다.
  - `attention`(종료 코드 2): 경고가 하나라도 있고 `busy`가 아닌 모든 실행. `--dry-run`이든, 새 판을 남겼든, 같은 입력이라 부르지 않았든 같다. 무엇을 했는지는 `record`로 가린다. `record`가 없으면 모델을 부르지 않은 것이고, `record.model`이 있으면 새 판을 남긴 것이고, 경로와 판 번호만 있으면 `unchanged`였던 것이다.
  - `dry_run`, `saved`, `unchanged`(종료 코드 0): 경고가 없을 때만 나온다.
- 남은 블록이 하나도 없는 날은 모델을 부르지 않는다. 결과는 경고와 `--dry-run`에 따라 다르다.

  | | `--dry-run` | `--dry-run` 없음 |
  | --- | --- | --- |
  | 경고 있음 | `attention` | `attention`. dry-run과 같은 결과이고 `record`는 없다 |
  | 경고 없음 | `dry_run` | `error`("이날의 대화가 없어…"), 종료 코드 1 |

  읽지 못한 파일에 그날의 대화가 있을 수 있어서, 경고가 있는 날을 대화가 없던 날의 오류와 구별한다.
- `warnings`: 읽지 못한 파일, 사람 판정 경고, 글이 빠졌을 수 있다는 경고. 경고는 출처 번호로 시작한다. 그날 남은 블록이 없는 세션의 경고는 보관본 파일 경로로 시작한다.

## 알려진 한계

- Claude Code에서 사람이 도구 실행을 거절하며 적은 이유는 도구 결과 안에 들어 있어 대화록에 남지 않는다.
- 질문 창에서 사람이 덧붙인 메모는 남지 않는다. 이 PC의 보관본에서 `toolUseResult.annotations`에는 선택지 미리보기(`preview`)만 있었고, 메모가 든 행이 없어 그 모양을 확인하지 못했다. 문자열이 아닌 답과, 질문 결과가 둘 이상인 행의 답도 남지 않는다. 이 PC의 보관본에는 없다.
- 8 MiB를 넘는 행과 JSON이 아닌 행은 읽지 않으므로 그 행에 든 사람 글과 시각을 잃는다. 경고는 나지만 글은 남지 않는다. 그 행이 자정 뒤 첫 행이면 뒤따르는 시각 없는 행은 전날로 간다. 그 행으로 파일이 끝나면 경고는 마지막으로 읽은 시각의 날부터 보관본의 수정 시각이 닿는 날까지 난다. 이 PC의 대화 보관본 392개에는 그런 행이 없다.
- 줄 끝 없이 끝나는 마지막 행은 경고 없이 빠진다. 쓰고 있는 세션에서는 정상이고, 다음 보관 때 행이 완성되어 들어온다. 세션이 끝난 뒤에도 그렇게 남은 파일이면 그 행의 글을 경고 없이 잃는다. 이 PC의 대화 보관본 392개에는 그렇게 끝나는 파일이 없다.
- 줄 끝 없이 끝나는 마지막 행이 8 MiB를 넘으면 경고가 난다. 줄을 읽는 공용 코드(`chat_history/transcript.rs`)가 상한을 넘은 행에서는 줄 끝을 만났는지 파일 끝에 닿았는지 알려 주지 않기 때문이다. 쓰고 있는 세션의 큰 행이 이렇게 보관되면 `attention`이 된다. 다음 보관 때 행이 완성되어도 8 MiB를 넘으므로 그 행은 읽지 못하고 경고는 계속 난다. 미완성이어서 난 경고인지 완성된 큰 행이어서 난 경고인지 구별하지 않는 것이며, 글을 잃었을 수 있다는 쪽으로 틀리는 것이라 고치지 않았다.
- 표시(`origin`, `turnOrigin`)가 없는 행에서 글 전체가 중단 표시와 같으면 앱의 글로 본다. 표시가 생기기 전 버전에서 사람이 그 글자 그대로만 쳤다면 경고 없이 빠진다. `[Request interrupted by user for tool use]`는 이 PC의 보관본에 없고, Claude Code가 도구 실행을 멈출 때 쓰는 문구로 알고 넣었다.
- 앱 알림은 사람 글 앞의 따로 된 블록일 때만 뺀다. 앱이 알림을 사람 글과 같은 블록이나 문자열에 넣거나 사람 글 뒤에 붙이면 그 알림이 `사람` 블록에 남는다. 거꾸로 사람이 알림 태그만으로 된 글을 치고 그 글이 다른 블록(이미지 포함) 앞에 놓이면 앱 알림으로 보고 뺀다. 이 PC의 보관본에는 둘 다 없다.
- `--transcript`와 `--result`가 같은 파일의 서로 다른 하드 링크이면 같은 파일인 줄 모른다. 경로만 비교하기 때문이다. 파일의 고유 번호를 읽으려면 표준 라이브러리 밖의 Windows API가 필요해 넣지 않았다. 두 출력 모두 임시 파일을 그 이름으로 옮겨 쓰므로, 대화록 쪽 이름에는 대화록이, 결과 쪽 이름에는 결과가 남고 두 이름은 더 이상 같은 파일이 아니다. 그 파일의 이전 내용은 그 파일의 다른 이름(세 번째 하드 링크)이 있으면 그 이름에 그대로 남고, 없으면 사라진다. 출력 이름이 `daily`나 `originals` 밖에서 기록이나 남겨 둔 판을 가리키는 하드 링크여도 기록은 바뀌지 않는다. `tests/daily-record.test.mjs`가 세 이름으로 확인한다.
- `--transcript`나 `--result`에 NTFS 스트림 이름(`day.md:note`)을 주면 쓰지 못하고 오류로 끝난다. Windows가 파일을 스트림 이름으로 옮기는 것을 받지 않기 때문이다(오류 87). 그 이름의 파일은 그대로다. 2026-11-24에 같은 `rename` 호출로 확인했다.
- 세션의 파일 하나를 읽지 못하면 그 세션의 사람 글은 모두 `다른 세션의 지시`가 되어 500자에서 잘린다.
- `origin`이 생기기 전 버전의 Claude Code 세션은 사람 글을 가리지 못한다. 경고와 함께 에이전트 실행으로 센다. 그런 세션을 새 버전에서 이어 쓴 파일은 사람이 연 세션으로 세지만, 표시 없는 앞쪽 글은 경고와 함께 빠진다. 이 PC의 보관본에는 그런 파일이 없다.
- Codex 하위 에이전트 세션에 사람이 직접 글을 쳐도 에이전트 실행으로 세고 경고를 낸다. 이 PC의 보관본에는 그런 세션이 없다.

- 하루 기록의 글은 확인하지 못한다. 프로그램이 확인하는 것은 답의 모양, 블록 번호, 글귀가 그 블록을 말한 쪽의 글에 있는지, 블록의 순서뿐이다. 요약, 결정, 이유 같은 글에 모델이 "사용자가 승인했다"라고 쓰면 그 문장은 그대로 남는다. 지시문으로 막고, `제안:`과 `확정:` 줄을 프로그램이 따로 쓰고, 값을 바꾼 결정에는 표시를 남길 뿐이다. 누가 제안하고 정했는지는 그 두 줄과 글귀로 읽어야 한다.
- 글귀가 사람의 글에 있다는 것은 사람이 그 말을 했다는 것까지만 보증한다. 그 말이 승인인지, 수정인지, 검토를 부탁한 것인지는 모델의 판단이다. "B안을 검토해 줘" 한 줄을 제안과 결정의 근거로 함께 들고 `human_decided`라고 답하면 그대로 남는다. 다이어리에 글귀가 함께 보이므로 읽는 사람이 가릴 수 있다. `human_approved`와 `human_changed`는 제안보다 뒤의 사람 글이 있어야 해서 이 경우에 남지 않는다.
- 글귀는 글자 그대로 옮겨야 센다. 모델이 낱말을 바꾸거나 줄이거나 두 군데를 이어 붙이면 실제로 사람이 정한 결정도 `unconfirmed`가 된다. 사람이 하지 않은 일을 했다고 적는 쪽보다 이쪽으로 틀리게 했다. 실제 모델에서 이런 일이 얼마나 생기는지는 재지 않았다. `checks.quotesNotFound`로 볼 수 있다.
- 질문 창에서 사람이 선택지 대신 직접 써넣은 답도 고른 답과 같이 다룬다. 결정의 근거는 되지만 사람의 제안으로는 세지 않는다. 글귀가 고른 답에도 있고 같은 블록의 질문 문구에도 있으면, 모델이 어느 쪽에서 옮겼는지는 가리지 못하고 센다. 사람이 고른 답에 그 글이 있기 때문이다.
- 대화록에서 8,000자에서 잘린 사람 글은 잘린 뒤쪽을 글귀로 쓸 수 없다. 모델도 그 부분을 읽지 못한다. 질문 창 블록도 같다. 고른 답은 통째로 따로 두지만, 글귀는 잘린 블록의 글에도 있어야 센다.
- 하루 기록 JSON은 프로그램이 만든 출력이다. 사용자가 최신 파일을 직접 고친 뒤 대화가 더 보관되어 다시 만들면, 고친 파일은 `<날짜>.r<판 번호>.json`으로 그대로 남고 최신 파일은 새 판이 된다. 고친 내용을 새 판에 합치지 않는다. "사용자가 고친 글은 자동 갱신이 덮어쓰지 않는다"는 원칙은 다이어리 표시를 붙이는 다음 단계에서 다이어리의 글에 적용한다. 그때까지 JSON을 직접 고치는 것은 지원하지 않는다.
- 최신 파일(`<날짜>.json`)이 지워지고 남겨 둔 판만 있으면 다음 실행은 1판부터 다시 만든다. 그 뒤 판을 남길 때 같은 번호의 파일이 이미 있고 내용이 다르면 오류로 멈춘다. 아무것도 덮어쓰지 않으며, 파일을 직접 정리해야 한다.
- 이 단계 이전에 만들어 둔 하루 기록 파일이 있으면 판 번호와 지문만 읽어 이어서 판을 쌓는다. 이전 모양의 파일을 새 모양으로 바꾸지는 않는다.
- 잠금 파일(`.<날짜>.lock`)은 날짜마다 하나씩 남고, 사용량 잠금 파일(`.usage.lock`)은 프로젝트마다 하나 남는다. 지우는 순간에 다른 실행이 잠금을 잡을 수 있어 지우지 않는다.
- 다른 실행이 `.usage.lock`을 쥔 채 멈춰 있으면 사용량 줄을 쓰려는 실행도 그동안 기다린다. 기다리는 시간에 상한을 두지 않았다. 그 프로세스가 끝나면 잠금이 풀린다.
- 실행 도중에 저장소 설정이 바뀌어도 그 실행은 처음 찾은 저장소를 끝까지 쓴다. 바뀐 뒤의 저장소는 이 실행에게 저장소가 아니므로, `--result`가 그 저장소의 `daily` 안을 가리키면 막지 않는다. 실행이 강제로 끝나면 `.<UUID>.tmp` 임시 파일이 남을 수 있다. 기록으로 읽지 않으며 지워도 된다.
- 하루 기록의 호출에서 CLI가 띄운 프로세스가 CLI보다 오래 살며 출력 파이프를 쥐고 있으면, 파이프를 읽던 스레드는 그 프로세스가 끝날 때까지 남는다. 호출은 CLI가 끝나고 2초 안에 돌아오고, 남은 스레드를 끝내지는 않는다. `record daily` 명령은 호출 한 번 뒤에 프로세스가 끝나므로 스레드도 함께 사라진다. 오래 켜 두는 앱이 이 호출을 되풀이하게 되면 그런 프로세스가 살아 있는 동안 스레드가 쌓일 수 있다. 채팅 경험 검토와 포트폴리오 작성은 출력을 읽지 않으므로 이 스레드가 없다.
- 프롬프트를 CLI의 입력으로 보내는 스레드는 모든 호출에 하나씩 있다. CLI나 CLI가 띄운 프로세스가 입력 파이프를 쥔 채 읽지 않으면 그 스레드가 프롬프트를 든 채 그 프로세스가 끝날 때까지 남는다. 이 단계 전에는 같은 경우에 호출이 돌아오지 않았다. 지금은 2초 안에 오류로 돌아온다.
- 대기 시간을 넘기면 직접 띄운 CLI만 끝낸다. CLI가 띄운 프로세스는 끝내지 않는다. Codex가 임시 폴더를 쥐고 있으면 그 폴더를 지우지 못하고 남긴다.
- `usage.jsonl`이 다른 날짜의 최신 판이나 남겨 둔 판과 하드 링크로 이어져 있으면, 사용량 줄을 덧붙일 때 그 판에도 붙어 그 판을 JSON으로 읽을 수 없게 된다. `usage.jsonl`은 덧붙여 쓰므로 하드 링크를 끊지 않는다. 하드 링크를 가리지 못하는 것은 위와 같은 이유이며, 문서 저장소 안에 일부러 하드 링크를 만든 경우다.
- 새 판을 내놓은 직후, 사용량 줄을 쓰기 전에 프로세스가 강제로 끝나면 그 호출의 `saved` 줄이 `usage.jsonl`에 없다. 다시 실행하면 `unchanged`여서 모델을 부르지 않고 줄도 쓰지 않는다. 빠진 줄을 되살리지 않는다. 그 호출의 사용량은 기록 파일의 `usage`에 있다. `usage.jsonl`은 정상으로 돌아온 실행의 호출만 모두 담는다.
- `--output-schema`가 이 스키마를 받는지, 모델이 글귀를 얼마나 정확히 옮기는지는 실제 호출로 확인하지 않았다. 이 단계의 테스트는 지어낸 답만 쓴다.
- 모델을 부르는 실행에서 `--result`를 문서 저장소 안의 다른 폴더(`daily`, `originals` 밖)로 지정하는 것은 막지 않는다.

## 검증

하루 기록의 자동 테스트(`crates/timeschedule-core/tests/daily_record_model.rs`)는 임시 폴더의 보관본과 지어낸 모델 답으로 확인 규칙, 저장, 사용량 기록을 본다. 실제 모델은 부르지 않는다. 제안만 한 사람, 제안보다 앞선 사람 글, 글귀가 맞지 않은 제안 근거, 잘린 블록의 `…`, 질문 창의 질문 문구, 첫 글자부터 `확정:` 줄인 요약, 모양이 다른 답과 펜스로 둘러싼 답 뒤의 기존 판, 같은 날의 동시 실행, 판을 남긴 직후 멈춘 실행, 버려진 답과 실패한 호출의 사용량, 쓰다 만 사용량 줄 뒤의 새 줄이 들어 있다. 다음도 들어 있다. 다음 질문의 `질문:`에서 잘린 질문 창 블록, 질문과 답처럼 보이는 줄이 든 직접 쓴 답, 대화록에서는 같게 보이지만 블록의 글·잘림 표시·고른 답이 다른 대화록의 지문, 다른 실행이 `.usage.lock`을 쥐고 있는 동안 기다리는 사용량 줄, 링크인 최신 판과 남겨 둔 판. 링크 테스트는 둘이다. 파일 링크 테스트는 파일 링크를 만들 권한이 있는 계정에서만 돌고, 2026-11-24에 이 PC에서는 건너뛰었다. 정션 테스트는 이 PC에서 돈다. 정션은 폴더를 가리키므로 링크 확인이 없어도 읽지 못해 오류로 끝나며, 이 테스트가 보는 것은 두 곳 모두 읽기 전에 링크인지 확인한다는 것(오류 글)까지다. 링크를 따라 읽은 내용이 최신 판과 같아 이전 판을 잃는 경로 자체는 이 PC에서 돌려 보지 못했다. 동시 실행 테스트는 두 실행을 각자의 스레드에서 돌리고 모든 대기에 20초 이내의 상한을 두어, 두 번째 실행이 잠금을 기다리게 바뀌면 멈추지 않고 실패한다.

`terra.rs`의 테스트는 Codex 대신 `cmd`와 `ping`을 띄운다(Windows에서만 돈다). `cmd`는 `ping`을 띄우고 바로 끝난다. 출력을 읽는 호출은 2초를 다 기다린 뒤 돌아오는지 본다. 파이프를 쥔 프로세스가 없으면 `cmd`가 끝나는 0.1초쯤에 돌아오므로, 2초를 채웠다는 것이 `ping`이 파이프를 물려받아 쥐고 있었다는 증거다. `ping`을 띄우지 않게 바꾸면 이 테스트는 실패한다(2026-11-24에 112 ms로 확인). 같은 프로그램을 출력을 읽지 않는 호출로 돌리면 2초를 기다리지 않는지도 본다. 대기 시간을 넘긴 호출이 멈추는지도 본다. 출력을 읽지 않는 호출에 읽는 스레드가 없다는 것은 코드의 구조로만 보장하고 테스트로 재지 않는다.

자동 테스트(`crates/timeschedule-core/tests/daily_record.rs`)는 임시 폴더에 만든 보관본으로 위 규칙을 확인한다. 실제 세션 파일로 자동 테스트하지 않는다. 명령은 두 곳에서 확인한다. `record_cli.rs`의 테스트는 틀린 인자를 주고 `--result`와 데이터 폴더에 무엇이 남는지 본다. 문서 저장소의 `vault.json`을 읽을 수 없게 한 뒤 `--result`로 기록 파일을 가리켜도 그 파일이 그대로인지도 본다. 한 번의 실행이 문서 저장소를 한 번만 찾는지는 테스트 빌드에만 있는 횟수 세기로 본다. 설정이 두 조회 사이에 바뀌는 경우를 실제로 만들어 돌리지는 않는다. `tests/daily-record.test.mjs`는 빌드한 실행 파일에 임시 홈 폴더를 주고 실제로 dry-run을 돌려, 대화록과 결과 파일이 생기고 데이터 폴더는 생기지 않는지 본다. 출력 파일을 `daily`나 `originals` 안으로 지정하면 거절하고 그 파일을 그대로 두는지, `vault.json`이 손상된 동안에는 어떤 출력도 쓰지 않는지, 출력 이름이 다른 파일의 하드 링크일 때 그 파일이 그대로인지, 경고만 있는 날을 `--dry-run` 없이 돌리면 `attention`으로 끝나는지도 본다.

`project.json`과 `index.jsonl`이 파일 링크일 때의 테스트는 파일 링크를 만들 권한이 있는 계정에서만 돈다. 2026-11-24에 이 PC의 계정에는 그 권한이 없어 건너뛰었다. 폴더 링크(정션) 테스트는 돌았다.

2026-11-24에 디버그 빌드로 이 PC의 실제 보관본(TimeSchedule, 활동 16일)에 `--dry-run`을 돌렸다. 저장소는 읽기만 했고 대화록 글은 파일에 쓰지 않았다.
