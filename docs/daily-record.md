# 하루 정리

[방향 문서](product-direction.md)의 "순서" 2번이다. 그날 채팅 원문을 모델이 읽고 하루 기록과 하루 요약을 만든다. 지금은 첫 단계인 **하루 대화록**까지 있다. 모델 호출, 저장, 다이어리 표시는 다음 단계에서 붙인다.

## 하루 대화록

한 프로젝트의 한국 시간 하루 동안 사람과 AI가 주고받은 글이다. [채팅 원문 보관](chat-originals.md)의 보관본만 읽는다. DB를 열지 않으므로 앱이 켜져 있어도 만들 수 있다.

### 고르는 파일

프로젝트의 `originals/<폴더>/index.jsonl`에서 대화 파일만 고른다. Codex 세션 파일과 Claude Code 본 세션 파일, Claude Code 하위 에이전트 기록(`subagents/`)이다. Claude Code 세션 옆의 도구 결과 파일은 읽지 않는다.

- 세션 시작 시각이 그날 끝 이후이거나, 보관할 때 원본의 수정 시각이 그날 시작 이전이면 열지 않는다.
- 연 파일에서는 행의 시각이 그날(한국 시간 자정 기준)인 행만 쓴다. 시각이 없는 행은 파일에서 바로 앞에 읽은 행의 시각을 따른다. 대화록에 넣지 않는 행의 시각도 센다. 여러 날에 걸친 세션은 날마다 나뉜다.
- 목록의 `file`은 프로젝트 폴더 안의 경로여야 한다. `..`이나 드라이브 문자가 든 경로, 프로젝트 폴더부터 보관본까지 링크(정션 포함)를 거치는 경로는 읽지 않고 경고로 남긴다. 다른 프로젝트의 보관본이 섞이지 않게 하기 위해서다.
- `originals`, 프로젝트 폴더, `project.json`, `index.jsonl`이 링크인지는 읽기 전에 본다. 프로젝트 ID로 찾을 때 링크인 폴더와 링크인 `project.json`은 열지 않고 건너뛴다. `originals`나 `index.jsonl`이 링크이면 오류로 끝난다. 하드 링크는 가리지 못한다.
- 한 행이 8 MiB를 넘으면 그 행은 읽지 않는다. 줄 끝까지 적혀 있는데 JSON이 아닌 행도 읽지 못한다. 둘 다 행 번호에는 센다. 그 행이 그날에 있거나 있을 수 있으면 경고를 낸다. 행의 시각을 읽지 못하므로, 바로 앞 행의 시각이 그날이면 그날의 행으로 본다. 앞 행의 시각이 그날 전이면, 다음에 시각이 적힌 행이 그날 시작 이후이거나 그런 행 없이 파일이 끝날 때 그날에 있을 수 있다고 본다. 빈 줄은 세지 않는다.
- 줄 끝 없이 끝나는 마지막 행은 읽지 않고 경고도 내지 않는다. 도구가 쓰고 있는 세션의 보관본은 그렇게 끝날 수 있다. 그 행이 8 MiB를 넘을 때는 경고가 난다("알려진 한계").

### 세션

말한 쪽은 파일이 아니라 세션 단위로 정한다.

- **Codex:** 목록의 세션 ID가 같은 파일은 한 세션이다. Codex가 세션 파일을 `archived_sessions/`로 옮기거나 한 세션을 두 번째 파일에 이어 쓰면 보관본이 둘이 된다. 2026-11-24에 이 PC의 보관본 367개 중 한 세션이 두 파일에 나뉘어 있었다. 한 파일이라도 그날 범위에 들면 그 세션의 파일을 모두 읽는다. 사람이 글을 쳤는지를 세션 전체에서 보기 위해서다.
- **Claude Code:** 파일 하나가 한 세션이다. 하위 에이전트 기록은 본 세션의 세션 ID를 갖고 있지만 따로 센다. 세션 ID는 보관 경로에서 읽는다. 본 세션 파일은 `claude/<폴더>/<세션 ID>.jsonl.zst`이고 하위 에이전트 기록은 `claude/<폴더>/<세션 ID>/subagents/` 아래에 있다. 목록의 `session`은 본 세션 파일에서 세션 ID가 적힌 첫 행의 값이라, 도구가 이어받은 세션의 행을 파일 앞에 복사해 두면 그 세션의 ID가 된다. 그래서 쓰지 않고, 경로의 ID와 다르면 경고를 낸다.
- 같은 글이 세션의 파일에 두 번 적혀 있으면 한 번만 센다. Codex는 항목 ID(`item.id`), Claude Code는 행의 `uuid`, Claude Code의 도구 결과는 `tool_use_id`로 가린다. 첫 사본이 비어 있으면 글이 있는 사본을 쓴다.
- 사본은 모두 사람 글이어야 한다. 대화록에 넣지 않는 행도 사본으로 센다. 다른 세션의 ID가 적힌 행, 세션 ID가 없는 행, `isMeta`인 행, 작업 알림 같은 행이 사람 글과 같은 ID를 갖고 있으면 그 글은 `다른 세션의 지시`가 되고 경고가 난다. 그런 행에 든 도구 결과도 같은 `tool_use_id`의 결과의 사본으로 센다. 질문 창에서 고른 답은 사본이 엇갈리면 블록을 만들지 않고 경고만 낸다. 다른 세션이 보낸 지시가 아니기 때문이다. 사본이 모두 고른 답이라고 해도 답의 글이 서로 다르면 엇갈린 것이다.
- 세션의 파일 가운데 하나라도 읽지 못하면 그 세션에는 `사람`이 없다. 읽지 못한 파일의 사본이 무엇이라고 하는지 알 수 없기 때문이다. 사람 표시가 있던 글은 `다른 세션의 지시`가 되고 경고가 난다. AI의 답은 `AI`로 남는다.
- 세션에 사람 글이 하나도 없으면 에이전트 실행이다. 두 도구에 같은 규칙을 쓴다. `codex exec`, Codex 하위 에이전트(첫 행의 `source`가 객체이거나 `exec`), Claude Code 하위 에이전트는 파일이 스스로 프로그램이 시작했다고 적은 세션이라 처음부터 에이전트 실행이다.
- 에이전트 실행은 그날 마지막 답만 남긴다. 마지막 답은 시각이 가장 늦은 답이고, 시각이 같으면 파일에서 뒤에 있는 답이다. Claude Code가 그 답을 여러 행에 나눠 적었으면(같은 `message.id`) 그날의 행을 시각 순서로 이어 첫 행의 자리에 둔다.

### 말한 쪽

| 표시 | 무엇인가 |
| --- | --- |
| 사람 | 사람이 친 글, 질문 창에서 고른 답(질문과 함께) |
| AI | 사람이 글을 친 세션에서 AI가 보여 준 답 |
| 에이전트 실행 | 아무도 글을 치지 않은 세션의 그날 마지막 답 |
| 검사 출력 | 실패한 명령의 종료 코드와 진단 줄 |
| 다른 세션의 지시 | 다른 세션이나 자동 실행이 보낸 글 |

다음 단계는 `사람` 블록을 사람이 그렇게 말했다는 근거로 쓴다. 그래서 `사람`은 파일에 적힌 표시가 모두 맞고 어긋나는 표시가 하나도 없을 때만 붙인다. 표시가 없거나 엇갈리면 `사람`이 아니다. 모델이 추측하지 않는다.

**Codex.** 화면에 보인 항목(`event_msg`의 `item_completed`)만 읽는다. 사용자 발화(`UserMessage`)가 `사람`이려면 다음이 모두 맞아야 한다.

1. 행의 `thread_id`가 이 세션의 ID다. 다른 세션의 ID가 적힌 행은 포크가 부모에게서 복사한 것이므로 버린다. `thread_id`가 없는 행도 버리고 경고를 낸다.
2. `client_id`가 있다. 없으면 `다른 세션의 지시`다.
3. 같은 항목 ID의 사본이 모두 위 둘에 맞는다. 하나라도 어긋나면 `다른 세션의 지시`로 두고 경고를 낸다.
4. 세션의 파일을 모두 읽었다.

세션의 ID와 누가 시작했는지는 파일의 첫 행(`session_meta`)에서만 읽는다. 포크는 둘째 행에 부모의 `session_meta`를 갖고 있다.

2026-11-24에 이 PC의 보관본으로 확인했다. 앱에서 사람이 연 세션의 발화 346개에는 모두 `client_id`가 있었다. `codex exec`, 하위 에이전트, 자동 실행이 쓴 발화 722개에는 하나도 없었다. CLI 0.164부터 0.169.1까지 같았다. 필드의 뜻을 Codex 문서로 확인한 것은 아니다. 포크 115개는 부모의 글을 `response_item` 행으로만 복사했고 `item_completed` 행으로는 복사하지 않았다. `thread_id`가 없는 항목과 같은 ID가 두 번 나온 항목은 없었다.

**Claude Code.** `user` 행의 글이 `사람`이려면 다음이 모두 맞아야 한다.

1. 행의 `sessionId`가 보관 경로에 적힌 이 세션의 ID다. 다른 세션의 ID가 적힌 행은 버린다. `sessionId`가 없는 행도 버리고 경고를 낸다.
2. 본 세션 파일의 행이고 `isSidechain`, `isMeta`, `isCompactSummary`가 아니다.
3. `origin.kind`가 `human`이다. `origin`이 없거나 `kind`를 읽을 수 없으면 `사람`이 아니다.
4. `turnOrigin`이 없거나 `human`이다.
5. 같은 `uuid`의 행이 모두 위 넷에 맞는다. 하나라도 어긋나면 `다른 세션의 지시`로 두고 경고를 낸다.
6. 세션의 파일을 읽었다.

- `turnOrigin`이 `host_synthetic`이면 `origin`이 무엇이든 `다른 세션의 지시`다.
- 그 밖의 `user` 행은 쓰지 않는다. 작업 알림, 슬래시 명령의 출력, 중단 표시(`[Request interrupted by user]`)가 여기에 든다. 표시가 없는 이런 행이 앱의 것인지는 글로 가린다. 슬래시 명령과 그 출력은 글의 시작(`<command-name>`, `<local-command-`)으로, 중단 표시는 글 전체가 `[Request interrupted by user]`나 `[Request interrupted by user for tool use]`와 같은지로 본다. 중단 표시로 시작하는 글은 사람이 쓸 수 있으므로 시작만으로는 앱의 글로 보지 않는다.
- 도구 결과(`tool_result`)는 사람 글이 아니다. 한 행에 도구 결과와 글(`text`)이 함께 있으면 글은 위 규칙으로 따로 본다.
- `AskUserQuestion`의 결과 행은 사람이 질문 창에서 고른 답을 갖고 있다. 블록의 글은 행의 `toolUseResult.answers`에서 만든다. 질문마다 `질문: …`과 `고른 답: …` 두 줄이고, 질문은 `toolUseResult.questions`의 순서다. 도구 결과의 글(`tool_result.content`)은 도구가 쓴 문구라서 쓰지 않는다. 고르지 않은 선택지를 인용할 수 있기 때문이다. 질문 문구는 AI가 쓴 것이고 `고른 답` 줄만 사람의 것이다.
- 고른 답은 다음이 모두 맞을 때만 `사람`이다. 본 세션 파일의 행이다. 그 행에 `AskUserQuestion` 결과가 하나뿐이다(`answers`가 어느 질문의 것인지 행에 적혀 있지 않다). 그 결과가 `is_error`가 아니다. `answers`에 비어 있지 않은 문자열 답이 하나 이상 있다. `origin`과 `turnOrigin`이 다른 쪽을 가리키지 않는다. 같은 `tool_use_id`의 결과가 모두 이에 맞고, 만들어진 블록의 글(질문과 고른 답)이 서로 같다. `isMeta`인 행이나 다른 세션의 ID가 적힌 행처럼 쓰지 않는 행에 든 결과도 센다. 하나라도 아니면 블록을 만들지 않는다. 사본이 엇갈린 경우에는 경고를 낸다.
- 앱은 사람 글 앞에 `<system-reminder>…</system-reminder>` 알림을 넣는다. 사람 글의 `text` 블록 앞에 따로 둔 `text` 블록이다. 그래서 `content`가 블록 목록일 때, 글 전체가 짝을 이룬 알림뿐인 `text` 블록을 앞에서부터 뺀다. 목록의 마지막 블록은 빼지 않는다. 마지막인지는 이미지 같은 다른 종류의 블록까지 세어 본다. 그래서 `[알림, 이미지]`에서는 알림이 빠져 사람 글이 남지 않고, 블록이 알림 하나뿐인 글은 사람이 쓴 것으로 남는다. 사람 글의 블록 안에 있는 태그와, `content`가 문자열 하나인 글의 태그는 사람이 쓴 것이므로 그대로 둔다.
- `다른 세션의 지시`는 문자열 하나가 알림으로 시작한다. 맨 앞에 짝을 이룬 알림만 뺀다. 가운데와 끝의 태그, 닫히지 않은 태그는 그대로 둔다.
- AI의 답 한 행에 `text` 블록이 여럿이면 한 블록으로 잇는다. 답 하나가 여러 행에 나뉘어 있으면(같은 `message.id`) 행마다 블록 하나다. 행마다 `uuid`, 행 번호, 시각이 따로 있어서, 다시 적힌 행을 한 번만 세고 자정을 넘긴 행을 제 날짜에 둘 수 있다. 에이전트 실행의 마지막 답만 그날의 행을 잇는다.

2026-11-24에 이 PC의 본 세션 12개(Claude Code 2.1.325~2.1.330)로 확인했다. `origin.kind`가 `human`인 행은 119개였다. 두 필드가 모두 없는 일반 행 20개는 모두 앱이 쓴 것이었다(슬래시 명령 11개, 그 출력 8개, 중단 표시 1개. 중단 표시의 글 전체는 `[Request interrupted by user]`였다). 도구 결과 행 3,393개에는 `origin`이 하나도 없었다. `AskUserQuestion` 결과 행은 4개였다. 모두 결과가 하나였고 `answers`는 질문 문구에서 답 문자열로 가는 표였으며(답 1~4개), 질문은 모두 `questions`에 있었다. 본 세션 12개 모두 목록의 `session`과 첫 행의 `sessionId`가 파일 이름과 같았다. 하위 에이전트 기록 13개의 대화 행 1,085개는 모두 경로의 세션 ID를 갖고 있었다. 한 파일에 같은 `uuid`가 두 번 나온 행과, 같은 `message.id`의 글이 두 행에 나뉜 답은 없었다. 같은 `tool_use_id`의 결과가 두 번 적힌 파일도 없었다. `origin.kind`가 `human`인 행 119개는 `content`가 문자열인 행 110개, `text` 블록 둘인 행 6개, 이미지 블록 뒤에 `text` 블록이 온 행 3개였다. 알림 태그가 든 행은 `text` 블록이 둘인 6개였고, 첫 블록은 짝을 이룬 알림뿐(알림 9개)이고 둘째 블록이 사람 글이었다. 사람 글의 뒤나 가운데에 든 알림은 없었고, `content`가 문자열인 110개에는 태그가 없었다. `host_synthetic` 행 34개는 문자열이 알림 1~3개로 시작했다.

**경고.** 사람 판정을 믿기 어렵거나 글이 빠졌을 수 있는 세션은 경고로 알린다. 그 세션의 파일에 그날 시각의 행이 하나라도 있으면, 그날 남은 블록이 없어도 경고는 남는다. 대화록에 넣지 않는 행도 센다. 그날 시각의 행이 없는 날에는 내지 않는다.

- 앱이나 터미널에서 사람이 연 것으로 보이는 Codex 세션(`source`가 `vscode`나 `cli`, `thread_source`가 `user`)에 발화는 있는데 `client_id`가 있는 발화가 없다. Codex가 이 필드를 없애면 사람 글이 0개로 나오기 때문이다.
- Claude Code 본 세션에 `origin`도 `turnOrigin`도 적힌 행이 하나도 없는데 일반 글이 있고, 사람 글로 센 글이 없다. 이 필드가 생기기 전 버전의 파일이다. 사람 글을 가릴 수 없으므로 에이전트 실행으로 센다.
- Claude Code 본 세션의 그날 행 가운데 `origin`도 `turnOrigin`도 없는 일반 글이 있다. 앱이 쓴 것으로 아는 글(슬래시 명령과 그 출력, 글 전체가 중단 표시인 글)은 세지 않는다. 중단 표시로 시작하고 다른 글이 이어지는 행은 센다. 같은 파일의 다른 행에 표시가 있어도 낸다. 이전 버전에서 시작한 세션을 새 버전에서 이어 쓰면 앞쪽 사람 글이 이렇게 빠진다. 위 경고가 난 세션에는 따로 내지 않는다.
- 프로그램이 시작한 세션에 사람 표시가 있는 글이 있다. 에이전트 실행으로 센다.
- Codex 파일에 `UserMessage` 항목이 하나도 없는데 그날 `event_msg`의 `user_message` 행이 있다. 예전 Codex는 사람 글을 이 형식으로만 적었을 수 있고, 이 형식에는 누가 쳤는지 표시가 없어 읽지 않는다. 지금 형식은 같은 글을 `user_message`와 `UserMessage` 항목에 함께 적으므로 경고가 나지 않는다. 이 PC의 보관본(CLI 0.164~0.169.1)에는 `user_message` 행이 없다.
- 같은 글의 사본끼리 사람 표시가 다르거나, 질문 창에서 고른 답의 사본끼리 답이 다르다. 세션 ID가 없는 행이 있다. 시각을 알 수 없는 글이 있다.
- 8 MiB를 넘거나 JSON이 아니어서 읽지 않은 행이 그날에 있거나 있을 수 있다.
- Claude Code 파일에서 목록의 세션 ID가 경로의 세션 ID와 다르다.
- 세션의 파일을 읽지 못했다. 파일마다 경고가 하나 나고, 사람 표시가 있던 글이 있으면 세션에도 하나 난다. 읽지 못한 파일에 그날의 행이 있는지 알 수 없으므로, 목록으로 보아 세션이 걸칠 수 있는 날마다 낸다.

### 남기는 것과 버리는 것

도구 출력, 추론, 같은 내용의 복사본(Codex의 `response_item`, 압축 요약, Claude Code의 API 요청 사본), 시스템이 넣은 글은 버린다. 사람과 AI의 글은 거르지 않는다.

실패한 명령은 종료 코드와 진단 줄을 세 줄까지만 남긴다. 줄을 고르는 규칙은 `chat_history/command.rs`에 있다. 따옴표, `=`, 주소, `token` 같은 낱말이 든 줄은 비밀값일 수 있으므로 뺀다. 출력을 통째로 옮기는 경우는 없다. TAP 형식의 테스트 출력에서는 실패한 테스트 줄(`not ok`)과 `# fail` 줄을 진단 줄로 본다. Claude Code의 종료 코드는 행의 `toolUseResult.exitCode`에서 읽는다. 행에 도구 결과가 하나일 때만이다. 거기서 읽지 못하고 결과가 `is_error`이면 결과 글의 `Exit code N`에서 읽는다. `is_error`가 아닌 결과의 글에서는 읽지 않는다.

블록 하나에 남기는 글자 수는 다음과 같다. 넘치면 자르고 끝에 `…`를 붙인다.

| 표시 | 상한 | 근거 |
| --- | --- | --- |
| 사람 | 8,000자 | 2026-11-24에 가장 긴 사람 글이 6,093자였다 |
| AI | 4,000자 | AI 답의 99%가 3,359자 이하였다 |
| 에이전트 실행 | 2,000자 | 실행의 지시문(합계 5.6M자)은 버리고 답만 남긴다 |
| 검사 출력 | 1,000자 | 진단 줄은 세 줄, 한 줄 400자까지다 |
| 다른 세션의 지시 | 500자 | 어떤 지시였는지만 남긴다 |

### 형식

블록은 시각 순서다. 블록마다 번호와 출처 번호(`S1`, `S2`, …)가 붙는다. 프로그램은 번호마다 보관본 파일과 압축을 푼 파일의 행 번호(1부터)를 갖는다.

```text
# 하루 대화록 · TimeSchedule · 2026-11-24

## 출처

S1 · claude · claude-desktop · 사람이 연 세션
S2 · codex · codex_exec · 에이전트 실행

## 대화

[1] 09:14 사람 · S1
…

[2] 09:20 에이전트 실행 · S2 (그날 마지막 답)
…
```

`[번호] 시:분 `으로 시작하는 줄은 블록의 머리말뿐이다. 글 안에 그런 모양으로 시작하는 줄이 있으면 앞에 `> `를 붙인다. AI가 대화록을 인용한 글을 실제 사람 블록으로 읽지 않게 하기 위해서다. 글의 줄 끝(`\r\n`, `\r` 등)은 모두 `\n`으로 바꾼다. 글의 앞과 뒤에서는 빈 줄(공백뿐인 줄)만 뺀다. 첫 줄의 들여쓰기와 마지막 줄 끝의 공백은 그대로 둔다. 말한 쪽이 누구든 같다. 사람 글은 쓴 그대로여야 하고, AI의 답도 코드로 시작하면 들여쓰기가 뜻을 갖기 때문에 규칙을 둘로 나누지 않았다. 질문 창에서 고른 답도 같은 방법으로 다듬어 `고른 답: ` 뒤에 붙인다. 프로젝트 제목과 출처 줄의 도구, 연 프로그램은 줄 끝을 빈칸으로 바꿔 한 줄로 쓴다. 제목이나 목록의 값에 든 줄이 머리말처럼 보이지 않게 하기 위해서다.

## 명령

```powershell
TimeSchedule.exe record daily --project C:\LSH\TimeSchedule --dry-run --date 2026-11-24
```

| 인자 | 뜻 |
| --- | --- |
| `--project` | 프로젝트 ID 또는 프로젝트 폴더의 절대 경로. 같은 ID의 보관 폴더가 둘 이상이면 실행하지 않고 폴더 경로를 지정하라고 알린다 |
| `--dry-run` | 대화록만 만들고 모델을 부르지 않는다. 지금은 반드시 붙인다 |
| `--date` | `YYYY-MM-DD`. 숫자 네 자리, 두 자리, 두 자리와 `-` 둘로 된 열 글자여야 하고 실제 날짜여야 한다(`2026-1-2`, `+2026-11-24`, `-0001-01-01`, `+10000-01-01`은 오류). 빼면 한국 시간 오늘 |
| `--transcript` | 대화록 글을 이 파일에 쓴다. 채팅 원문이 그대로 들어간다. `--result`와 같은 경로이면 실행하지 않고, 그 파일에 아무것도 쓰지 않는다. 경로의 대소문자와 상대 경로는 맞춰 본다. 파일 이름의 `:` 뒤는 NTFS 스트림 이름으로 보고 떼어 낸다(`day.md::$DATA`는 `day.md`). 경로에서 이미 있는 가장 가까운 상위 폴더까지를 링크(정션 포함)를 풀어 읽고 아직 없는 부분을 그 뒤에 붙여 비교하므로, 아직 없는 폴더 안의 파일을 정션을 거쳐 가리켜도 같은 경로로 본다. 비교는 아무것도 쓰기 전에 한 번만 하고 결과 파일을 쓸지도 그 답으로 정한다. 하드 링크는 가리지 못한다 |
| `--data-dir`, `--result` | 다른 `record` 명령과 같다 |

문서 저장소는 채팅 원문 보관과 같은 방법으로 찾는다. 명령은 보관본을 새로 만들지 않는다. 앱이 마지막으로 보관한 데까지 읽고, 결과의 `latestArchived`에 가장 늦은 보관 시각을 적는다. 데이터 폴더가 없어도 만들지 않는다. 그때는 기본 위치의 문서 저장소를 읽는다.

앱에서 프로젝트의 폴더를 바꾸면 보관 폴더가 새로 생기고 이전 폴더도 남는다. 프로젝트 ID로는 어느 쪽인지 정할 수 없으므로 실행하지 않는다. 폴더 경로를 주면 그 폴더의 보관본만 읽는다.

인자가 틀리면 보관본을 읽기 전에 끝나고 종료 코드는 1이다. 오류는 표준 출력에 JSON으로 나온다. `--result` 파일에 쓰는지는 다음과 같다.

- 인자를 해석하지 못하면(모르는 인자, 값이 없는 인자, 중복 인자, `--project` 없음) 쓰지 않는다. 어느 파일이 결과 파일인지 믿을 수 없기 때문이다.
- `--result`가 `--transcript`와 같은 경로이면 쓰지 않는다. 앞서 만든 대화록을 오류로 덮어쓰지 않기 위해서다.
- 그 밖의 오류(`--dry-run` 없음, 날짜 형식, 보관본 없음 등)는 쓴다. 호출한 쪽이 지정한 결과 파일이고, 쓰지 않으면 이전 실행의 결과를 이번 것으로 읽을 수 있기 때문이다. 다른 `record` 명령도 오류를 결과 파일에 쓴다.

결과 JSON의 항목은 다음과 같다.

- `summary`: 사람이 글을 친 세션 수, 에이전트 실행 수, 말한 쪽별 블록 수, 대화록 글자 수, 말한 쪽별로 잘린 블록 수.
- `estimatedInputTokens`: 추정 입력 토큰. 글자 수를 3.3으로 나누고 호출 하나의 고정 입력 11,449토큰을 더했다. 3.3은 보관된 `codex exec` 62개에서 잰 3.66자당 1토큰을 한글이 많은 대화록에 맞게 낮춘 추정값이다. 11,449는 `gpt-6.1-terra`를 한 번 불러 잰 값이다.
- `sources`: 출처 번호별 보관본 파일 목록(`files`), 도구, 연 프로그램, 세션 ID.
- `warnings`: 읽지 못한 파일, 사람 판정 경고, 글이 빠졌을 수 있다는 경고. 하나라도 있으면 `outcome`이 `attention`이고 종료 코드가 2다. 경고는 출처 번호로 시작한다. 그날 남은 블록이 없는 세션의 경고는 보관본 파일 경로로 시작한다.

## 알려진 한계

- Claude Code에서 사람이 도구 실행을 거절하며 적은 이유는 도구 결과 안에 들어 있어 대화록에 남지 않는다.
- 질문 창에서 사람이 덧붙인 메모는 남지 않는다. 이 PC의 보관본에서 `toolUseResult.annotations`에는 선택지 미리보기(`preview`)만 있었고, 메모가 든 행이 없어 그 모양을 확인하지 못했다. 문자열이 아닌 답과, 질문 결과가 둘 이상인 행의 답도 남지 않는다. 이 PC의 보관본에는 없다.
- 8 MiB를 넘는 행과 JSON이 아닌 행은 읽지 않으므로 그 행에 든 사람 글과 시각을 잃는다. 경고는 나지만 글은 남지 않는다. 그 행이 자정 뒤 첫 행이면 뒤따르는 시각 없는 행은 전날로 간다. 그 행으로 파일이 끝나면 경고는 마지막으로 읽은 시각의 날부터 보관본의 수정 시각이 닿는 날까지 난다. 이 PC의 대화 보관본 392개에는 그런 행이 없다.
- 줄 끝 없이 끝나는 마지막 행은 경고 없이 빠진다. 쓰고 있는 세션에서는 정상이고, 다음 보관 때 행이 완성되어 들어온다. 세션이 끝난 뒤에도 그렇게 남은 파일이면 그 행의 글을 경고 없이 잃는다. 이 PC의 대화 보관본 392개에는 그렇게 끝나는 파일이 없다.
- 줄 끝 없이 끝나는 마지막 행이 8 MiB를 넘으면 경고가 난다. 줄을 읽는 공용 코드(`chat_history/transcript.rs`)가 상한을 넘은 행에서는 줄 끝을 만났는지 파일 끝에 닿았는지 알려 주지 않기 때문이다. 쓰고 있는 세션의 큰 행이 이렇게 보관되면 `attention`이 된다. 다음 보관 때 행이 완성되어도 8 MiB를 넘으므로 그 행은 읽지 못하고 경고는 계속 난다. 미완성이어서 난 경고인지 완성된 큰 행이어서 난 경고인지 구별하지 않는 것이며, 글을 잃었을 수 있다는 쪽으로 틀리는 것이라 고치지 않았다.
- 표시(`origin`, `turnOrigin`)가 없는 행에서 글 전체가 중단 표시와 같으면 앱의 글로 본다. 표시가 생기기 전 버전에서 사람이 그 글자 그대로만 쳤다면 경고 없이 빠진다. `[Request interrupted by user for tool use]`는 이 PC의 보관본에 없고, Claude Code가 도구 실행을 멈출 때 쓰는 문구로 알고 넣었다.
- 앱 알림은 사람 글 앞의 따로 된 블록일 때만 뺀다. 앱이 알림을 사람 글과 같은 블록이나 문자열에 넣거나 사람 글 뒤에 붙이면 그 알림이 `사람` 블록에 남는다. 거꾸로 사람이 알림 태그만으로 된 글을 치고 그 글이 다른 블록(이미지 포함) 앞에 놓이면 앱 알림으로 보고 뺀다. 이 PC의 보관본에는 둘 다 없다.
- `--transcript`와 `--result`가 같은 파일의 서로 다른 하드 링크이면 같은 파일인 줄 모른다. 대화록을 쓴 뒤 결과 쪽 이름을 새 결과 파일로 바꾸므로, 대화록 쪽 이름에는 대화록이, 결과 쪽 이름에는 결과가 남고 두 이름은 더 이상 같은 파일이 아니다. 그 파일에 있던 이전 내용은 사라진다. 2026-11-24에 한 번 실행해 확인했다. 경로만 비교하기 때문이다. 파일의 고유 번호를 읽으려면 표준 라이브러리 밖의 Windows API가 필요해 넣지 않았다.
- 세션의 파일 하나를 읽지 못하면 그 세션의 사람 글은 모두 `다른 세션의 지시`가 되어 500자에서 잘린다.
- `origin`이 생기기 전 버전의 Claude Code 세션은 사람 글을 가리지 못한다. 경고와 함께 에이전트 실행으로 센다. 그런 세션을 새 버전에서 이어 쓴 파일은 사람이 연 세션으로 세지만, 표시 없는 앞쪽 글은 경고와 함께 빠진다. 이 PC의 보관본에는 그런 파일이 없다.
- Codex 하위 에이전트 세션에 사람이 직접 글을 쳐도 에이전트 실행으로 세고 경고를 낸다. 이 PC의 보관본에는 그런 세션이 없다.

## 검증

자동 테스트(`crates/timeschedule-core/tests/daily_record.rs`)는 임시 폴더에 만든 보관본으로 위 규칙을 확인한다. 실제 세션 파일로 자동 테스트하지 않는다. 명령은 두 곳에서 확인한다. `record_cli.rs`의 테스트는 틀린 인자를 주고 `--result`와 데이터 폴더에 무엇이 남는지 본다. `tests/daily-record.test.mjs`는 빌드한 실행 파일에 임시 홈 폴더를 주고 실제로 dry-run을 돌려, 대화록과 결과 파일이 생기고 데이터 폴더는 생기지 않는지 본다.

`project.json`과 `index.jsonl`이 파일 링크일 때의 테스트는 파일 링크를 만들 권한이 있는 계정에서만 돈다. 2026-11-24에 이 PC의 계정에는 그 권한이 없어 건너뛰었다. 폴더 링크(정션) 테스트는 돌았다.

2026-11-24에 디버그 빌드로 이 PC의 실제 보관본(TimeSchedule, 활동 16일)에 `--dry-run`을 돌렸다. 저장소는 읽기만 했고 대화록 글은 파일에 쓰지 않았다.

| 항목 | 값 |
| --- | --- |
| 날짜당 걸린 시간 | 0.3~2.1초 |
| 대화록 글자 수 | 중앙값 66.7K자, 가장 큰 날(11-16) 304.1K자, 16일 합계 1,228.8K자 |
| 추정 입력 토큰 | 가장 큰 날 103,614, 16일 합계 555,546 |
| 경고 | 0건 |
| 잘린 블록 | 사람 0개. 에이전트 실행이 가장 많다(11-16에 106개 중 25개, 11-22에 32개 중 14개) |

설계할 때 같은 보관본에서 같은 상한으로 어림한 합계는 1,318K자였다. 7% 차이는 그 어림이 블록 머리말을 넉넉히 잡았고, `client_id` 규칙으로 사람 글이 아닌 발화 10개가 빠진 데서 온다.
