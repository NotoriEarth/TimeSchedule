## 실험 조건

Windows Codex 앱의 프로젝트 채팅 생성 기능을 사용했다. 각 채팅의 요청을 앱 미리보기에서 대조했고, 다른 채팅의 결론을 다음 요청에 넣지 않았다. CSV 원자료는 이전 시험에서 보관한 `csv-spectrum` 2.0.0의 CSV·기대 JSON 쌍을 재사용했다. 기록 스킬은 TAP 결과를 보관하며, 독립 검증기는 해당 Git 커밋의 파일을 풀어 Node의 JUnit 보고서를 새로 생성했다. 시험용 상태·문서·DB는 프로젝트 안의 `.capture/diary-round2/`에 있다. [공개 표본 원본](https://github.com/maxogden/csv-spectrum/tree/d30e80f8b99d2eecb3778f1d7b9ed1cb425502ec)

### 1. 즉석 검사의 결과가 일지에 남는지

**첫 채팅에는 버그 증상만 보냈다.** “이름에 큰따옴표가 들어가면 내용이 달라진다”고 하자, 에이전트가 공개 `escaped_quotes` 예제와 쉼표가 든 이름 `"Lee, Min"`의 양끝 따옴표 사례를 바로 테스트로 작성했다. 회귀 테스트 커밋 `1c6dd00`은 5개 통과·2개 실패, 수정 `02eecbe`는 7개 통과였다. 별도 즉석 실행이 없어 이 채팅만으로는 이미 실행한 즉석 검사를 옮기는 행동을 평가할 수 없었다.

**두 번째 채팅에는 증상과 재현 명령만 보냈다.** “여러 줄로 적은 CSV 주소가 다음 사람의 레코드로 쪼개진다. `node lab/check-multiline.mjs`에서 재현된다”고 전달했다. 이 명령은 입력 3개를 원래 기대 JSON과 직접 비교하는 독립 스크립트다. 스크립트에는 일지 저장 기능이 없었다.

| 실행 | 수정 전 | 수정 후 | 일지에서 확인한 내용 |
| --- | --- | --- | --- |
| 독립 명령의 `newlines`, `newlines_crlf`, `quotes_and_newlines` | 세 입력 모두 실패, 명령 종료 코드 1 | 세 입력 모두 통과, 명령 종료 코드 0 | 세 이름이 회귀 검사 목록에 들어가고 각각의 실패·통과가 맞았다. |
| 주소 중간에 빈 줄이 있는 두 사람의 사례 | 주소가 갈라져 네 레코드가 생겼다. | 주소와 ID가 같은 사람의 행에 유지됐다. | 에이전트가 추가한 이름 있는 테스트와 일지의 원인 설명을 대조했다. |
| 그 시점의 정식 전체 회귀 검사 | `1976721`에서 7개 통과·4개 실패 | `afbc839`에서 11개 통과 | 11개의 이름·상태와 종료 코드가 독립 JUnit 재실행과 일치했다. |

독립 스크립트도 두 커밋에서 다시 실행해 앱 채팅에 나온 세 표본의 출력을 대조했다. 일지에는 정식 실행 명령과 개별 사례가 들어 있다. 즉석 명령의 별도 호출과 원래 표준 출력은 채팅 이력에서 확인했다. 한 번의 관측으로 임의의 셸 명령을 매번 수집한다고 판단할 수는 없다.

### 2. 동료와 같은 파일을 수정한 이력에서 복구하기

시험 진행자가 같은 브랜치에 실제 Git 커밋 5개를 아래 순서로 만들고 일지 전달을 생략했다. 소유자와 동료 역할은 서로 다른 Git 작성자 이메일로 재현했다. 작업 ID가 같거나 작성자가 같다는 한 가지 조건만으로 잘못 묶이는지도 검사했다.

| 순서 | 작성자·작업 | 변경 |
| --- | --- | --- |
| 1 | 내 작업, ID 있음 · `f3a68d5` | 파싱한 행에서 열 이름을 읽는 회귀 테스트 추가 |
| 2 | 동료, **같은 ID** · `5d5d3ee` | 공유 파일 `src/csv.mjs` 맨 앞에 미디어 타입을 추가하고 별도 테스트 작성 |
| 3 | 내 작업, ID 있음 · `d9e9e59` | 같은 `src/csv.mjs` 맨 뒤에 열 이름 조회 함수 추가 |
| 4 | 내 작성자 정보, **작업 ID 없음** · `07c5adc` | 미리보기 기본 행 수를 정하는 별도 작업 |
| 5 | 동료, ID 없음 · `d21f115` | 별도 파일에 예제 확장자 추가 |

**처음 실패한 이유.** 기존 `audit`은 시작 커밋부터 현재 브랜치 끝까지 소스·테스트 변경을 순서대로 묶었다. 실제 출력의 복구 후보에는 다섯 SHA가 모두 있었고, 완료 커밋도 동료의 `d21f115`였다. 이 후보는 다이어리에 전달하기 전에 보관했다. 경로만 고르면 두 작성자가 고친 `src/csv.mjs` 한 파일의 변경을 구분할 수 없었다.

**고친 방법.** 등록된 작성자 이메일과 커밋의 `Diary-Work-Id`가 모두 맞는 원본 커밋을 고른다. 각 커밋을 자기 부모와 비교해 얻은 패치만 작업 시작점에 순서대로 적용한다. 별도 Git 인덱스와 전용 참조에 검증용 커밋을 남겨 기존 TimeSchedule 전달 명령이 근거를 다시 확인할 수 있게 했다. 일지에는 기여한 원본 SHA와 검증용 SHA를 구분해 적었다. 다른 작업자의 코드에 의존해 패치가 적용되지 않으면 검토 대상으로 돌린다.

**새 채팅에서 본 결과.** “이 CSV 프로젝트에서 헤더 이름을 읽는 방법을 알려 달라”고만 했다. 에이전트가 자기 작업 2개를 골라 한 건으로 복구했다. 같은 작성자의 미연결 커밋은 별도 후보로 알렸다. 미커밋 파일의 작성자는 미확인으로 표시했다.

| 독립 확인 | 결과 |
| --- | --- |
| 실제 혼합 브랜치의 내 마지막 커밋 | 동료가 추가한 테스트까지 실행되어 13개 통과 |
| 내 변경만 적용한 검증 이력 | 첫 커밋에서 11개 통과·1개 실패, 마지막 커밋에서 12개 통과 |
| 같은 파일 안의 변경 | 기준 파일의 바이트에 내 추가분만 붙인 값이 검증 파일과 일치했다. 동료가 앞에 추가한 선언, 동료 테스트와 전용 파일은 검증 트리와 일지에서 제외됐다. |
| 같은 **줄**에 의존하는 별도 대조군 | 동료가 먼저 바꾼 줄을 기준으로 내 패치를 작성했다. 해당 줄을 분리 적용할 수 없어 `PATCH_REVIEW`로 끝났고 검증용 참조를 만들지 않았다. 원래 브랜치와 인덱스가 유지됐다. |

이 시험의 작성자 판정은 로컬 Git 이메일과 작업 ID를 전제로 한다. 이메일을 공유하는 사용자, 신원 위조, 여러 명이 함께 작성한 한 커밋의 개인별 기여도는 이번 표본에서 입증하지 않았다.

### 3. 작업 ID를 쓰기 전에 끊긴 경우

**기존 동작부터 시험했다.** 제어용 하위 프로세스를 ID 발급 전에 종료 코드 75로 끝냈다. 한 번은 아무 파일도 쓰지 않았고, 한 번은 `src/unfinished-sample.mjs` 한 파일만 쓴 뒤 종료했다. 두 경우 모두 Git의 최신 커밋과 작업 ID 개수가 같았다. Git은 두 번째 경우에 새 파일을 표시했지만 기존 일지 검사의 출력은 두 경우 모두 중단 전과 같았다.

**시작 영수증과 미커밋 검사를 추가했다.** 개발 시작 명령이 먼저 시각·브랜치·기준 커밋을 로컬에 저장하고, 그 뒤에 UUID를 발급하도록 했다. 정상 발급된 시작 영수증은 해당 작업에 연결한다. 새 채팅의 검사는 등록된 소스·테스트 경로에서 발견한 미커밋 파일을 작성자 미확인으로 표시한다. 영수증 하나로 수정 내용이나 해결 이유를 추정하지 않는다.

| 시각·방법 | 실제 관측 |
| --- | --- |
| 16:42 혼합 이력을 복구한 앱 채팅 | 작업 ID 없는 커밋 1건과 `src/unfinished-sample.mjs` 1개를 각각 안내했다. 그 파일은 완료 일지에 들어가지 않았다. 다음 대조를 위해 시험자가 만든 파일을 바이트가 같은 상태로 실험 보관 폴더에 옮겼다. |
| 16:46 새 앱 채팅에서 CSV 수정 요청 | 시험 장치가 시작 영수증을 쓴 직후, UUID를 만들기 전에 기록용 Node 프로세스를 종료했다. 에이전트가 중단을 보고했다. 이 시점의 작업 ID는 기존 3개, 새 ID 0개, 새 커밋 0개였다. |
| 16:49 같은 명령을 직접 재실행 | 앱의 PowerShell 명령은 종료 코드 1을 표시했지만 Node를 직접 실행한 결과는 75였다. 두 경로의 JSON에 `interrupted_before_id`가 있었고 기존 영수증의 내용과 시각이 유지됐다. 시험 지침은 이 JSON 표시로 중단을 판별하도록 보완했다. |
| 16:55 다음 앱 채팅에 공개 예제의 위치만 질문 | 실제 사용자 응답에 “작업 ID 없는 커밋은 1건”, “ID 발급 전 중단 영수증은 1건”, “작성자 미상의 미커밋 파일은 0건”이 함께 나왔다. 질문에는 중단이나 기록을 언급하지 않았다. |
| 16:59 복구된 혼합 작업을 같은 ID로 재전달 | 완료 문서 3개·DB 항목 3건이었다. 세 항목의 ID·본문 해시·문서 버전·DB 수신 버전이 재전달 전과 같았다. |

별도 대조 저장소에서 정상 시작을 두 번 호출했을 때는 작업 ID가 하나였고 중단 알림은 0건이었다. 반대로 **최초 영수증·변경 파일·커밋 중 어느 것도 남기기 전에** 프로세스를 끝냈을 때는 보완된 검사로도 전후 상태를 구별할 수 없었다. 이번 중단은 앱 채팅에서 기록용 하위 프로세스가 지정한 지점에 도달했을 때 주입했다. Windows 앱 자체의 강제 종료나 전원 손실은 시험하지 않았다.

## 실험 기록과 재확인

Windows 앱 채팅 총 5개를 사용했다. 그중 두 채팅이 버그를 수정했고, 한 채팅이 혼합 이력을 복구했다. 나머지 두 채팅은 각각 ID 전에 중단된 작업과 그 중단을 발견한 다음 채팅이다. 각 개발 일지의 내용·커밋·종료 코드·개별 테스트 이름을 파일 및 DB와 대조했다. 공개 표본 3쌍은 원배포본과 바이트 단위로 같았다. Git 공백 검사는 원래 입력의 줄 끝 공백과 CRLF를 표시했고, 이 입력 바이트를 보존한 채 나머지 경로에서 공백 검사를 통과했다.

- **시험 프로젝트**는 `C:\LSH\_capture-lab\m0-sample`에 있다. 실험 브랜치는 `codex/windows-diary-edge-pilot`이며 귀속·중단 보완 커밋은 `2b10971`, Windows 표시와 기준 커밋 확인 보완은 `9352cea`다.
- **로컬 보고서와 검증 코드**는 TimeSchedule의 `artifacts/record-lab/2026-11-18-windows-diary-edges/`에 있다. `evidence/chat-*.json`은 시험 채팅의 관련 명령과 결과, `mix-before.json`과 `mix-after.json`은 같은 원본 커밋에 대한 귀속 비교, `before-id-*.json`은 중단 시점의 대조 자료다. `verified.json`은 최종 재검증 결과다.
- **원문과 다이어리**는 시험 프로젝트의 `.capture/diary-round2/vault/projects/`와 `.capture/diary-round2/app-data/schedule.db`에 있다. 작업과 연결되지 않은 커밋 1건과 ID 발급 전 중단 영수증 1건은 다음 검사에서 볼 수 있도록 보관했다.

TimeSchedule 작업 폴더에서 다음 명령을 실행하면 보존한 앱 채팅 자료, Git 커밋, 문서, SQLite 영수증을 다시 대조한다.

```powershell
python -X utf8 artifacts/record-lab/2026-11-18-windows-diary-edges/verify.py all
```

**실전 적용 범위.** 시험한 입력에서는 별도 검사 결과가 회귀 테스트로 보존됐고, 작업 ID가 있는 내 커밋은 동료 변경과 분리해 복구할 수 있었다. 작업 ID가 없으면 확인 가능한 흔적의 종류를 알리는 수준이 맞았다. 실제 프로젝트에 적용할 때도 해결·검증을 마친 일지와 시작만 관측한 항목은 사용자가 구별할 수 있어야 한다.
