# 후속 커밋 직후 Windows Codex 채팅을 끊고 같은 개발 일지를 복구한 기록

2026-11-18, 실제 TimeSchedule 프로젝트에서 첫 일지를 저장하고 같은 작업에 개발 커밋을 하나 더 만들었다. 커밋 직후 채팅을 끊었다. 새 채팅은 일지를 언급하지 않은 요청만 받고 누락된 커밋을 찾아 첫 문제와 해결을 보존하면서 추가 수정의 이유와 테스트 결과를 덧붙였다. `TimeScheduleData`의 원문은 2판이 됐고 네이티브 다이어리에는 같은 항목 한 건이 남았다.

## 어떤 입력에서 실패했는가

| 재현한 상황 | 관찰한 실패 | 수정과 재검사 |
| --- | --- | --- |
| 첫 커밋의 설명을 저장한 뒤 같은 작업에 개발 커밋을 추가하고 설명 경로 없이 `finish <작업 ID>`를 실행했다. | 커밋이 바뀌어도 도구가 저장된 설명을 읽어 완료로 처리했다. SHA가 없는 구형 설명도 재사용할 수 있었다. | `1012a3f`에서 설명과 그 설명이 쓰인 작성자의 마지막 개발 커밋 SHA를 함께 저장한다. 후속 개발 커밋에는 `audit`이 `missing`을 반환한다. 같은 검사는 수정 전 8개 중 6개, 수정 후 8개 모두 통과했다. |
| 첫 수정 위에서 예전 설명 JSON을 다른 이름으로 복사해 이번에는 `finish`에 그 경로를 직접 지정했다. | 경로를 지정한 입력은 전부 새 설명으로 취급했다. 추가 변경 이유가 한 줄도 없어도 일지가 완료됐다. | `fad3f92`에서 요약과 상세 문단을 같은 작업의 이전 기록과 비교한다. 파일명·제목·검사 목록·공백만 바꾸거나 이전 판들의 문단만 다시 내면 후속 이유를 요청한다. 기존 설명에 새 근거를 덧붙이면 같은 항목을 갱신한다. |

두 번째 실패는 별도 임시 체크아웃에서도 재현했다. 같은 복사본으로 `1012a3f`에서는 거절을 기대한 검사가 실패했고 `fad3f92`에서는 통과했다. 회귀 검사에는 같은 커밋에 같은 설명을 다시 보내는 정상 경로도 포함했다. [회귀 검사](../tests/development-diary.test.mjs)

## Windows Codex에서 채팅을 끊은 시점

1. PR #32의 당시 끝 커밋 `db7ce00`에서 로컬 시험 브랜치를 열었다. 이전 프로젝트 시험 일지를 보존하기 위해 새 작업 ID를 받았다. Windows Codex 앱의 프로젝트 연결 기능으로 연 첫 채팅이 `1012a3f`를 커밋하고 첫 일지를 저장했다.
2. 같은 채팅에서 복사본 문제를 수정했다. `fad3f92`의 본문에 첫 수정으로 놓친 경로, 바꾼 이유, 테스트 결과를 적고 같은 작업 ID를 붙였다. Git이 성공한 직후 진행 중이던 채팅을 앱의 보관 기능으로 중단했다. 앱에서 해당 턴이 `inProgress`에서 `interrupted`로 바뀌었고, 커밋 다음에 실행된 명령은 0개였다.
3. 이때 `audit`은 `fad3f92`를 `missing`으로 표시했다. 별도로 새 설명 없이 `finish`를 실행하자 마지막 개발 커밋에 새 설명이 필요하다는 메시지와 종료 코드 1을 받았다. 문서와 DB 본문의 SHA-256은 첫 저장 직후와 같았다.
4. 같은 프로젝트에 대화 이력이 없는 새 채팅을 열고 아래 한 문장만 보냈다. 채팅이 직접 `audit`을 실행해 작업 ID와 누락된 커밋을 찾았다. 기존 일지, 커밋 본문과 diff, 로컬에 남은 검사 결과를 확인하고 완료 커밋에서 회귀 검사를 다시 실행해 같은 ID로 저장했다.

> 현재 체크아웃된 브랜치의 개발 작업을 이어받아서, 이미 커밋된 변경에 남은 마무리를 진행해줘. 원격 PR 갱신은 내가 맡을게.

## 실제 원문과 다이어리에서 확인한 값

| 이 작업에서 센 값 | 시작 전 | 첫 저장 후 | 채팅 중단 직후 | 새 채팅 복구 후 | 한 번 더 `retry`한 후 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `record.md`와 `metadata.json` 쌍 | 0 | 1 | 1 | 1 | 1 |
| 같은 출처의 다이어리 항목 | 0 | 1 | 1 | 1 | 1 |
| 보관된 문서 수정본 | 0 | 1 | 1 | 2 | 2 |

복구한 원문과 실제 SQLite 다이어리 본문에서 첫 요약 문단이 그대로 보존됐고, 복사한 설명을 새 입력으로 오인한 이유와 해결 과정이 추가됐다. Git에서 두 시점의 소스를 따로 꺼내 같은 회귀 검사를 실행했다. 첫 수정은 **6/8 → 8/8**, 후속 수정은 **8/10 → 10/10**이었다. 실패한 검사 이름과 종료 코드까지 일지와 일치했다. 기존 대표 `artifacts/TimeSchedule.exe`를 지정한 전체 Node 테스트는 **81개 통과, 건너뜀 0개**였다.

대표 앱의 `record status`와 실제 DB에서 받은 다이어리 항목 ID도 같았다. `retry`가 `unchanged: true`를 반환한 뒤 문서와 DB 본문의 SHA-256, 수정본 수, 항목 ID를 다시 대조했다. 모두 복구 직후와 같았고 최종 `audit`에서 누락은 0건이었다.

앱에서는 11월 18일 TimeSchedule 프로젝트의 **개발 일지 복구 시 설명을 작성자의 마지막 개발 커밋에 연결**을 열어 두 수정의 이유와 결과를 읽을 수 있다. 이번 시험에서 이유를 복원할 수 있었던 근거는 커밋 본문과 검사 기록이다. 문단 비교로 예전 설명의 재제출은 찾을 수 있지만 새 문장의 사실성은 커밋과 실행 결과를 대조해 확인해야 한다. [개발 일지 복구 절차](../.agents/skills/development-diary/SKILL.md)
