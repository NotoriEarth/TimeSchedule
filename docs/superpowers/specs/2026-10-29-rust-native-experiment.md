# Rust 네이티브 전환 실험 설계

> 진행 갱신: 사용자가 시제품 이후 “전체앱을 한번 이식해달라”고 명시적으로 요청했다. 현재는 별도 Iced 실행 파일로 전체 구현을 진행한다. 아래 초기 설계의 시제품 선행 수동 승인 조건은 구현 착수의 차단 조건에서 제외하되, 실제 IME·바탕화면 검증과 사용자 머지 승인은 계속 필요하다. 현재 승인 범위·담당·검증 기록은 `SOFTWARE_FACTORY.rust-native.md`를 따른다.

## 목적과 현재 기준

초기 요청은 다이어리 머지 이후 “Rust로 모두 바꾼다면?”을 검증할 별도 브랜치와 계획 작성이었다. 이후 시제품을 거쳐 전체 앱 이식 요청으로 범위가 확대되었다. 현재 범위는 기존 PC 기능을 별도 Rust 실행 파일로 구현하는 것이다.

- 기준 브랜치: `main`, 머지 커밋 `a8f47a1fcbf2bcc6dcd499ba1c545f897d5c0ee5` (PR #1).
- 실험 브랜치: `codex/rust-native-experiment`.
- 현재 앱: Rust/Tauri 2 + Svelte/TypeScript + SQLite. 제품 실행에 Python은 없다.
- 이미 Rust인 기능: SQLite 저장·마이그레이션·검색, Git 수집, Windows 바탕화면 연결과 창 관리의 상당 부분.
- 전환 대상: Svelte/DOM/CSS 화면, TypeScript의 날짜·초안·편집 상태, Tauri의 창·트레이·이벤트 연결. 두 WebView 화면을 Rust GUI로 대체한다.
- “전체 Rust”는 앱의 UI와 로직을 Rust로 작성하고 네이티브 실행 시 Tauri/WebView/JS 런타임을 요구하지 않는다는 뜻이다. SQLite의 C 구현, OS API, GPU 드라이버까지 Rust로 재작성하지 않는다.

## 예상 효과와 한계

WebView 프로세스와 웹 렌더러를 제거하면 상주 메모리와 프로세스 수가 줄 가능성이 있다. 그러나 Rust GUI도 글꼴·텍스트 편집 버퍼·GPU 리소스를 사용하므로 감소량은 측정 전에는 알 수 없다. 이미 Rust인 저장 코드를 다시 쓰는 것만으로 큰 절감이 생긴다고 보지 않는다. Rust로 작성한 웹 UI를 WebAssembly로 WebView 안에서 실행하는 방식은 이번 비교의 목표가 아니다.

유지보수 측면에서는 공통 Rust 코어와 명확한 UI 경계가 유리하다. 반면 현재 웹 편집기를 네이티브로 옮기면 한글 IME, 텍스트 선택·실행 취소, 접근성, 팝업, 여러 창과 바탕화면 자식 창을 직접 검증해야 한다. 향후 모바일·태블릿 지원은 코어 재사용 가능성을 열어두되 화면 코드까지 자동으로 재사용된다고 약속하지 않는다. 현재 자유 노트는 일반 텍스트이며 Notion급 블록 편집기는 이 실험의 범위가 아니다.

## 후보 비교와 선택 방식

| 후보 | 이번 실험에서의 역할 | 확인할 점 |
| --- | --- | --- |
| 현재 Tauri/Svelte | 기능·성능 비교 기준으로 유지 | 같은 데이터와 화면 조건으로 측정 |
| Iced 0.14 계열 | 우선 시제품 후보. Rust 상태/메시지 기반 화면과 멀티라인 편집기로 현재 다이어리 재현 | 한글 조합·커서, 독립 스크롤, 창 수명, GPU 렌더러와 WorkerW 자식 창의 호환성 |
| egui/eframe | Iced가 입력·바탕화면·성능 기준을 통과하지 못할 경우 작은 동일 시제품으로 비교 | 폼/다이어리 스타일, 한글 편집, 유휴 redraw, 렌더러별 메모리 |
| Slint | 예비 대안. 선언형 화면을 허용할 경우 재검토 | `.slint` 언어를 쓰므로 문자 그대로 Rust 소스만인 구조는 아님. 배포 전 라이선스 선택과 실제 편집 동작 검토 |
| Windows API 직접 UI | 위젯 플랫폼 계층에 한정해 검토 | 상세 다이어리 전체를 직접 그리면 편집기·접근성·다른 OS 확장 비용이 커짐 |

Iced를 확정 채택한 것은 아니다. 공식 FAQ는 0.14부터 IME와 reactive rendering을 지원한다고 설명하지만 CJK 편집의 경계 사례가 남을 수 있다고 명시한다. 따라서 한글 노트 편집을 첫 번째 통과 조건으로 둔다. eframe은 wgpu/glow 선택을 제공하므로 예비 시제품에서는 사용한 렌더러를 반드시 기록한다. 특정 렌더러가 무조건 가볍다고 단정하지 않는다.

참고한 공식 자료(2026-10-29): [Iced FAQ](https://book.iced.rs/faq.html), [Iced 0.14 text_editor](https://docs.rs/iced/0.14.0/iced/widget/fn.text_editor.html), [Iced daemon](https://docs.rs/iced/0.14.0/iced/daemon/index.html), [eframe 문서](https://docs.rs/eframe/latest/eframe/), [Slint FAQ](https://slint.dev/faqs), [Tauri 구조](https://v2.tauri.app/concept/architecture/). 구현 시 사용할 릴리스와 feature를 Cargo.lock에 고정하고 해당 버전 예제를 기준으로 작업한다.

## 보존해야 할 기능

1. 반투명 바탕화면 달력, 위치 이동/잠금/복구, 트레이, 상세 창 닫기·재열기. Explorer 소유 창의 스타일·프로시저를 변경하거나 재시작하지 않는다.
2. 상세 창이 주 화면. 월간 일요일 앞 선택 영역은 다음 월요일~다음 일요일, 월간 복귀는 원래 월 유지.
3. 주간은 4열×2행: 주간 정보·월·화·수 / 목·금·토·일. 800×620 이상에서 7일을 한눈에 보고 날짜별 독립 스크롤. 날짜/추가 버튼 고정.
4. 일정·기록·메모·할 일·프로젝트 CRUD, 펼침/접힘과 출처 링크. 긴 본문은 필요할 때 읽는다.
5. 편집창 바깥 클릭: 변경 없으면 닫기, 변경 있으면 별도 중앙 확인 팝업. 계속 편집/Esc는 내용과 스크롤을 보존하고 명시적 버리기만 닫는다. 저장 실패·저장 중·비동기 초안 도착으로 작성 중 내용이 사라지지 않는다.
6. 한국어 제목/본문 검색, 220ms 입력 대기, 최대 50개 결과, 최신 요청만 표시. 200개 단위 기록 조회.
7. 수동 Git 최근 500개 수집, 원문·중복 식별자·사용자 수정 보존. 근거 초안은 최대 100개 자료의 로컬 정리이며 기존 기록을 덮어쓰지 않는다.
8. SQLite schema v2와 기존 ID/날짜/본문/설정 호환. 앱의 새 기능·동기화 서버·AI 연동은 추가하지 않는다.

## 목표 구조

`timeschedule-core`는 저장/검색/Git/날짜/근거 초안을 소유한다. `timeschedule-desktop`은 Windows HWND·바탕화면·트레이·설정 경로를 소유한다. `timeschedule-native`는 Rust GUI 상태와 화면을 소유한다. 기존 `src-tauri`는 비교 기간 동안 같은 코어를 호출하는 어댑터로 남는다.

주의할 실제 결합: `diary.rs`의 `tauri::Url`을 독립 `url::Url`로 바꾸고, `open_source_url`의 ShellExecuteW는 플랫폼 계층으로 옮긴다. `desktop.rs`의 인자는 현재 `tauri::WebviewWindow`이므로 파일 이름만 옮겨서는 독립하지 않는다. UI 스레드와 창 수명을 보장하는 HWND 어댑터가 필요하다. `commands.rs`의 Tauri State/Emitter/spawn_blocking은 코어에 옮기지 않는다.

검색·Git·DB 작업은 UI 렌더 루프에서 실행하지 않는다. 작업 요청에 ID를 부여하고 화면/프로젝트/편집 세대가 바뀐 결과는 버린다. 폴링으로 매 프레임 DB를 읽거나 고정 60fps로 상주하지 않는다.

## 데이터 및 비교 환경

- 네이티브 실험판 기본 데이터 경로는 기존 앱과 분리한다. `TIMESCHEDULE_DATA_DIR`도 지원하며, 비교에는 각각 별도 복제 DB를 사용한다.
- 기본 사용자 DB를 자동으로 열거나 변환하지 않는다. 호환성 테스트는 합성 v1/v2 DB와 명시적으로 준비한 복사본에서 한다.
- 열린 SQLite DB를 파일 하나만 복사하지 않는다. 앱 완전 종료 뒤 복사하거나 SQLite backup API로 일관된 스냅샷을 만든다.
- 기준 EXE·커밋·SHA256을 보존한다. 기존 실행 파일과 사용자 앱 프로세스를 덮어쓰거나 강제 종료하지 않는다.
- 실험판의 실행 파일 이름·데이터 경로·트레이 표시는 구분한다. 같은 데이터 폴더의 중복 실행은 데이터 폴더별 잠금으로 막는다.

## 측정과 채택 기준

아래 숫자는 **실험용 제안 기준**이며 성능을 달성했다는 주장이 아니다. 채택 판단 시 측정 결과와 사용자 체감을 함께 검토한다.

- 메모리: 같은 기능 상태에서 전체 자식 프로세스를 포함한 private working set 중앙값이 기준판 대비 30% 이상 감소하는 것을 목표로 한다. 상세+위젯, 위젯만 두 상태 모두 측정한다.
- 응답성: 검색어 입력부터 결과 표시까지 p95 300ms 이내를 목표로 하되 220ms 입력 대기를 포함한다. 1~2글자 검색의 전체 스캔은 3글자 이상 검색과 별도로 보고한다.
- 시작: 새 프로세스 실행→첫 사용 가능한 화면의 p95가 `max(기준판 p95 × 1.1, 기준판 p95 + 100ms)`를 넘지 않는 것을 목표로 한다. 재부팅하지 않은 실행을 cold boot라고 부르지 않는다.
- 유휴 CPU: 프로세스 트리 CPU 시간 증가량으로 측정하고, 1코어=100% 기준으로 명시한다. 중앙값이 기준보다 0.5%p 이상 증가하면 조사한다.
- 실제 한글 입력·편집·미저장 보호·DB 호환·바탕화면 동작이 하나라도 실패하면 메모리가 줄어도 채택하지 않는다.
- 총 working set 합계는 공유 페이지 중복을 포함하며 private commit은 상주 RAM이 아니다. GPU 메모리는 별도 관찰 항목으로 기록한다.

현재 다이어리 버전의 새 기준 측정부터 시작한다. README의 과거 메모리 수치는 다른 기능 상태의 참고 기록으로만 사용한다. 시제품 측정은 시제품끼리의 비교이며 기능이 빠진 시제품의 수치를 최종 절감률로 발표하지 않는다.

## 중단·전환·완료 조건

우선 시제품에서 한글 입력 또는 바탕화면 연결이 실패하면 전체 이식을 진행하지 않고 원인·대안·최소 비교 결과를 기록한다. egui 대안도 통과하지 못하면 기존 Tauri를 유지하는 결론도 유효하다. 통과 시 코어 분리→상세 화면→위젯·트레이→동등 기능 성능 비교 순서로 진행한다. 최종 결과는 별도 EXE, 호환성/성능 보고서, PR로 전달하고 사용자가 테스트 후 승인하기 전에는 이 실험 브랜치를 머지하지 않는다.
