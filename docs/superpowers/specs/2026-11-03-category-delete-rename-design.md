# 카테고리 삭제·이름 변경 설계

상태: 2026-11-03 사용자가 **1번 시안 — 수정 화면에서 삭제**를 선택했다. 연결된 기록의 이동 대상을 직접 고른 뒤 카테고리만 삭제하고, 같은 수정 화면에서 이름·색상을 변경한다. 제품 코드는 아직 변경하지 않았으며 실행 순서는 [구현 계획](../plans/2026-11-03-category-delete-rename.md)에 정리한다.

## 목적과 확정 요구

- 사용하지 않는 카테고리를 정리한다. 연결된 기록이 있으면 사용자가 이동할 카테고리를 직접 고른다.
- 기록 원문·제목·날짜·프로젝트 연결·출처·짧은 표시 이름·원본 ID는 보존한다.
- 이름 변경을 찾기 쉽게 만들고 저장 후 위젯·다이어리에 함께 반영한다.
- 사용자는 실제 데이터를 건드리지 않는 두 화면 시안 중 1번을 선택했다.

## 현재 구조

`category_ui.rs`는 이름 클릭으로 수정 폼을 여는 `Edit`와 같은 ID에 저장하는 경로를 이미 갖고 있다. 삭제 액션과 저장소 삭제 API는 없다. 이름 변경은 기존 기능의 진입점을 명확하게 하는 작업이다.

`calendar.rs`의 `entry_display.category_id`는 카테고리를 참조한다. 사용자 분류는 기록형이며 기본 일정 ID는 기록 저장 대상으로 허용하지 않는다. 일정·기록 기본 ID는 날짜 조회에서 항상 사용되므로 삭제로 없어져서는 안 된다. 이름을 바꾸어도 기본 ID는 유지된다.

## 검토한 방식

| 방식 | 차이 | 선택 |
|---|---|---|
| 연결 기록을 선택한 분류로 옮기고 카테고리 삭제 | 기록 보존과 분류 정리를 한 번에 수행 | 사용자 선택 |
| 빈 카테고리만 삭제 | 구현은 단순하지만 먼저 기록을 따로 옮겨야 함 | 미선택 |
| 숨김·복원 | 보관 상태와 별도 표시 규칙이 필요 | 미선택 |

선택된 **1번: 수정 화면에서 삭제**는 각 행의 명시적인 `수정` 버튼으로 이름·색상 폼을 열고, 폼 하단에서 `카테고리 삭제`와 `변경 저장`을 떨어뜨려 배치한다. 삭제 진입 시 그 자리의 확인 화면으로 전환하며, 취소하면 기존 수정 초안으로 돌아온다. 목록 행에는 삭제 버튼을 추가하지 않는다.

**2번: 목록에서 바로 삭제**는 각 행에 `수정`·`삭제`를 모두 표시하는 미선택 대안으로만 보관한다. 두 시안의 삭제 확인 절차는 같다.

## 삭제 동작

1. 삭제 진입 시 현재 날짜 범위와 무관하게 연결된 전체 기록 수를 조회한다. 이때까지 저장소를 변경하지 않는다.
2. 기록이 있으면 삭제할 카테고리명·전체 건수·이동 대상 선택을 표시한다. 이동 대상은 자동 확정하지 않으며 사용자가 선택해야 `이동 후 삭제`를 누를 수 있다.
3. 삭제 대상 자신과 일정형 기본 카테고리는 이동 후보에서 제외한다. 기본 기록과 다른 사용자 기록 카테고리를 현재 이름으로 표시한다. 후보가 하나만 남아도 대상 이름을 명시하고 사용자의 선택을 받는다.
4. 기록이 없으면 이동 선택 없이 `카테고리 삭제`를 확인한다. 확인 전에 기록이 추가되면 삭제를 거절하고 최신 건수와 이동 선택을 다시 보여준다.
5. 최종 적용은 연결 변경·카테고리 삭제·남은 순번 정리를 한 트랜잭션으로 처리한다. 중간 실패는 전부 되돌린다. `entry_display` 행을 지우지 않고 카테고리 ID만 바꿔 짧은 표시 이름을 보존한다.
6. 확인 중 원본 분류·이동 대상·연결된 기록 집합이 바뀌면 조용히 다른 대상에 적용하지 않고 최신 내용을 다시 확인한다. 확인 때 읽은 분류 정보와 정렬된 기록 ID를 최종 트랜잭션 안에서 비교한다. 카테고리별 연결 조회 인덱스와 기존 DB 이전은 구현 계획에 포함한다.
7. 취소·Esc는 저장하지 않고 기존 수정 초안을 유지한다. 처리 중에는 중복 실행을 막는다. 성공 후 위젯·다이어리·열린 상세의 공통 조회를 갱신하고 이동 건수와 대상을 알린다.

선택된 시안의 기본 동작대로 일정·기록 카테고리는 삭제를 막고 이름·색상 변경은 허용한다. 이는 현재 저장 구조가 필요로 하는 보호이며 별도 삭제 허용을 요청받은 것은 아니다. 보호 여부는 이름 문자열이 아닌 고정 ID로 판단한다. 기록까지 함께 삭제하거나 숨김/휴지통/되돌리기를 추가하는 기능은 이번 범위에 포함하지 않는다.

## 이름 변경

- 이름을 클릭하는 기존 동작과 함께 눈에 보이는 `수정` 버튼을 둔다. 입력명은 `이름`, 완료 동작은 `변경 저장`으로 구분한다.
- 같은 카테고리 ID에 이름·색상을 저장한다. 카테고리별 순서, 연결된 기록, 프로젝트명, 기록 제목은 바꾸지 않는다.
- 현재의 빈 이름·중복 이름·최대 32자 검증을 재사용하고 오류 시 입력을 유지한다. 다른 창에서 선택한 카테고리가 변경되거나 삭제된 경우 최신 상태를 확인하도록 하며 사라진 ID를 조용히 재생성하지 않는다.
- 새 입력은 `새로 작성`과 `카테고리 추가`로 구분해, 이름 입력 뒤 추가 버튼이 내용을 지웠던 오류가 반복되지 않게 한다.

## 구현 경계와 경량화

기존 Rust/Iced·SQLite·worker·공통 refresh 경로를 사용한다. 확인창을 열 때 영향 범위를 조회하고 최종 적용 때 검증한다. 새 주기 조회·상주 프로세스·AI 호출은 추가하지 않는다. 전체 본문을 읽지 않고 카테고리 ID와 연결 정보로 집계·이동한다. 카테고리별 조회 인덱스가 필요하면 기존 DB를 보존하는 이전 절차와 함께 추가한다.

편집 중인 기록이 이동되더라도 원문 초안을 덮어쓰지 않는다. 기존 `EntryEdit` 비교와 삭제된 분류 선택 처리까지 확인해, 다시 저장할 때 최신 분류를 선택하거나 충돌 안내를 받을 수 있게 한다. MCP 일정 계약과 개발 기록 전달 ID·영수증은 유지한다.

## 구현 시 검증할 동작

- 빈 분류 삭제, 기록 있는 분류의 이동 대상 필수 선택, 기본 분류 보호, 같은 분류/일정형 대상 거절.
- 날짜·프로젝트가 다른 기록을 함께 이동해도 원문·ID·출처·별칭을 보존하고 양쪽 화면이 같은 분류를 표시.
- 취소·중복 클릭·저장 실패·확인 중 외부 변경·대상 삭제·오래된 편집 폼 처리와 원자적 롤백.
- 실제 모달의 `수정`·`변경 저장`·`삭제`·대상 선택·확정 클릭부터 저장소까지 검증. 저장 API만 직접 호출하는 테스트로 버튼 연결을 대신하지 않는다.
- 작은 창·긴 이름·명암 테마에서 버튼과 안내가 잘리지 않는지 확인. 실제 사용자 조작 확인과 자동 검증을 구분한다.

## 이번 설계 작업의 범위

화면 시안은 합성 카테고리와 브라우저 안의 임시 상태만 사용한다. 실제 앱·DB·버전·EXE는 변경하지 않는다. 문서/시안 작업이므로 자동 개발 기록의 prepare/sync를 실행하지 않는다.
