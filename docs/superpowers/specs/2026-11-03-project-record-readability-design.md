# 2단계 · 프로젝트 기록 표시와 다이어리·위젯 연동 설계

상태: **계획 검토용. 제품 구현·버전 변경·배포 전.**

기준: `1a8342a6b36c3b6c3f81cc4b6df2ffcf8a841f3b`, 네이티브 0.10.1.

## 사용자 의도와 확정한 선택

- `기록 1`만으로는 어느 프로젝트에서 무슨 일을 했는지 알기 어렵다. 달력에서 먼저 구별하고, 누르면 상세 내용을 읽고 수정한다.
- 사용자가 선택한 표현: **프로젝트명 위 / 작업명 아래의 두 줄**. 앱 다이어리와 위젯 모두 이 계층을 사용한다.
- 공간이 부족한 위젯에 대한 추가 선택: **프로젝트명만 표시하고 누르면 작은 토글로 작업명을 두 번째 줄에 펼친다.** 기본 두 줄 표시와 함께 쓰는 축약 방식이다.
- 가독성을 우선한다. 내용에 맞춰 글자를 계속 줄이거나 작은 칸에 본문까지 넣지 않는다.
- 같은 기록을 어느 화면에서 수정해도 양쪽에 반영한다. 이번 요청은 계획 작성이며 실행 승인은 아직 받지 않았다.

## 화면 제안

```text
3 화
15:00  개발 회의
┌────────────────┐
│ 타임스케줄      │  프로젝트 표시 이름
│ 연결 도우미 추가│  짧은 작업명
└────────────────┘
┌────────────────┐
│ 견적앱          │
│ 계산 오류 수정  │
└────────────────┘
+ 기록 2개 더
```

위 예의 상자는 범위를 설명하기 위한 것이다. 기본 시각안은 얇은 왼쪽 구분선이며 선택한 항목에만 옅은 배경을 준다. 공간이 작은 날짜 칸에는 아래 축약 표시를 사용한다.

```text
▸ 타임스케줄          →  ▾ 타임스케줄
                         연결 도우미 추가  → 상세
```

**구현 제안:** 펼침 내용은 행 바로 아래의 작은 팝오버로 표시한다. 날짜 칸 높이나 전체 달력 배치를 바꾸지 않는다. 사용자가 선택한 것은 프로젝트명→작업명 토글이며, 팝오버로 배치하는 방식은 달력 흔들림을 막기 위한 제안이다.

### 두 줄의 읽기 순서

- 윗줄: 프로젝트명. 짧은 표시 이름이 있으면 그것을 사용하고 없으면 원래 프로젝트명. 프로젝트 연결이 없거나 삭제된 기록은 `프로젝트 없음`.
- 아랫줄: 작업명. 별도로 입력한 달력용 제목이 있으면 그것을 사용하고 없으면 원래 기록 제목.
- 기본 제안은 프로젝트 12px/행높이 16px, 작업명 14px/행높이 19px, 줄 간격 2px, 위아래 여백 각각 4px(총 45px). 실제 글꼴 메트릭이 더 크면 높이도 늘린다. Windows 배율·위젯의 사용자 글꼴/글자 크기를 적용하며 공간 때문에 자동 축소하지 않는다.
- 작업명이 주 정보다. 프로젝트명을 과도하게 흐리게 하지 않고, 작업명은 더 큰 글씨로 표현한다. 색만으로 프로젝트를 구별하지 않는다.
- 프로젝트별 구분 색은 기존 팔레트와 고정 ID로 일관되게 정한다. 같은 이름·같은 색일 때도 실제 프로젝트 ID는 합치지 않는다. 상세에서 전체 프로젝트명/저장소로 구분한다.
- 이름과 작업명은 각각 한 줄이다. 한글·영문·숫자·이모지 혼합 폭을 **실제 렌더링 글꼴로 측정**한다.

### 긴 제목·작은 칸·많은 기록

- 원래 프로젝트명/기록 제목/본문은 보존한다. `달력 표시 이름`과 `달력용 작업명`을 선택적으로 편집하고 비우면 원래 제목으로 돌아간다. 자동 AI 요약은 하지 않는다.
- 짧은 이름은 입력 글자 수뿐 아니라 실제 미리보기에서 길이를 확인한다. 권장 길이는 프로젝트 2~6자, 작업명 6~12자지만 저장 제한과 실제 화면 폭은 구분한다.
- 임의 길이의 제목을 모든 창 크기에서 전부 보여준다고 보장하지 않는다. 공간이 부족하면 글자 중간을 잘라 가리지 않고 문자 묶음을 보존하는 `…`로 줄인다. 전체 내용은 클릭/키보드로 항상 접근한다. 호버만으로 접근하게 만들지 않는다.
- 날짜 행과 필요한 `더 보기` 행의 공간을 먼저 확보한다. 완전한 두 줄 기록이 들어가면 두 줄, 들어가지 않으면 프로젝트명만 표시하는 축약 행(기본 22px, 글꼴 실측에 따라 증가)을 쓴다. 같은 날짜 안에서는 표시 방식을 통일한다. 글자 폭만 부족한 경우에는 별칭/생략을 쓰며 자동으로 행 모드를 바꾸지 않는다.
- 축약 행은 `▸ 프로젝트명`이며 행 전체가 토글이다. 누르면 `▾`와 함께 작업명이 작은 펼침창에 나타난다. 펼침창의 작업명/상세 동작을 누르면 전체 기록 상세로 이동한다. 다시 누르기·바깥 클릭·Esc로 닫고, 한 창에서는 하나만 열린다. 키보드로 열고 작업명/상세에 접근할 수 있다.
- 팝오버는 별도 OS 창이나 프로세스가 아닌 기존 Iced overlay다. 글꼴을 유지하고 긴 작업명은 줄바꿈한다. 기본 너비 240 논리 px, 창 안쪽 폭에서 양쪽 8px를 뺀 값 이하로 제한한다. 아래 공간이 부족하면 위로, 옆으로 넘치면 창 안으로 보정한다. 위치·범위·폰트가 바뀌거나 기록이 삭제되면 닫는다. 본문은 이 단계에서 읽지 않는다.
- 날짜 칸 높이를 새로 강제하거나 선택한 주 수를 자동 변경하지 않는다. 기본/축약 전환은 실제 사용 가능한 높이로 결정하며, 640×480·960×640 등 보통 창에서도 주 수·배율에 따라 축약될 수 있다. 팝오버는 기존 다른 행 위에 떠서 이웃 날짜나 달력의 스크롤 위치를 밀지 않는다.
- 일정과 기록이 함께 있으면 일정 한 줄과 기록 한 항목을 먼저 배치한다. 두 줄이 안 들어가면 축약 기록으로 시도한다. 그것도 함께 들어가지 않으면 축약 기록을 우선하고 숨겨진 일정은 개수 진입점에 포함한다. 나머지는 기존 일정 순서와 기록의 `updated_at DESC, id` 순서다. 두 종류의 숨긴 개수는 각각 정확하게 표시하고 같은 날짜 상세로 접근한다.
- `+ 기록 N개 더`는 실제로 숨겨진 기록 수다. 축약 행조차 들어가지 않는 극소 높이에서만 `기록 N개`를 사용한다. 반쪽 행이나 날짜 칸 내부 스크롤은 만들지 않는다.
- 같은 프로젝트의 여러 기록은 별도 ID 항목으로 유지한다. 축약 상태에서 같은 이름이 반복될 수 있으며 토글로 작업명을 구별한다. 이번 단계에서 프로젝트별 그룹/새 집계 저장 구조는 추가하지 않는다.
- 달력의 미리보기 상한은 날짜당 4개. 개수는 전체를 세고, 더 보기는 날짜별 50개씩 계속 읽는다. 200개 목록 한도 때문에 특정 날짜가 비어 보이거나 개수가 틀리는 문제를 함께 막는다.
- 앱과 위젯은 같은 표시 규칙을 쓰지만 화면 크기가 달라 보이는 항목 수는 달라도 된다. 위젯 범위와 앱 월간/주간 범위는 각각 계산한다. 앱의 프로젝트 필터를 위젯에 몰래 전파하지 않는다.

### 클릭·상세·수정

- 두 줄 기록은 한 번 누르면 해당 **기록 ID의 읽기 전용 상세**가 열린다. 축약 기록은 먼저 작업명을 펼치고 작업명/상세를 누르면 진입한다. 어느 경로도 일정 생성이나 날짜 더블클릭 동작이 함께 실행되면 안 된다.
- 앱에서는 기존 날짜 상세 영역, 위젯에서는 기존 빠른 창을 재사용한다. 좁은 앱 창은 현재처럼 상세를 아래로 배치한다. 같은 공통 상세 컴포넌트를 사용한다.
- 상세 순서: 전체 프로젝트명 → 원래 기록 제목 → 날짜·기록 종류 → 본문 → 출처 링크. 근거 원문은 별도 펼치기 항목으로 둔다. 상태는 저장된 근거가 있을 때만 표시하며 본문에서 임의 추론하지 않는다.
- 본문은 원문 그대로 줄바꿈/긴 URL을 안전하게 표시하는 읽기 화면으로 시작한다. 이번에 별도 웹뷰나 고급 Markdown 편집기를 추가하지 않는다.
- `수정`을 누르면 기존 공통 편집기를 사용한다. 원래 제목·프로젝트·날짜·본문·출처 및 달력용 작업명을 수정할 수 있고 저장/취소가 명확하다. 프로젝트 표시 이름은 프로젝트 편집에서 변경하며 해당 프로젝트의 모든 기록에 반영된다.
- 저장이 성공한 뒤 다이어리·위젯·열린 상세의 머리말/본문 캐시를 갱신한다. 날짜를 옮기면 옛 날짜에서 제거되고 새 날짜에 표시된다. 실패하면 초안을 유지한다.
- 동시에 편집 가능한 초안은 기존처럼 하나다. 다른 화면에서 편집을 요청하면 현재 편집 창으로 안내한다. 자동 기록 수신 등으로 원본이 바뀌었다면 오래된 초안으로 덮어쓰지 않고 충돌을 알린다.

## 저장 구조와 경량화

- `diary_entries`가 기록 원본이다. 위젯용 일정이나 복제 기록을 만들지 않는다. 기존 `Entry.id`, `Project.id`, `source_ref`, 수신 영수증을 유지한다.
- 표시용 메타데이터를 별도 두 테이블에 저장하는 안을 권장한다: `project_display(project_id PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE, short_name)` 및 `entry_display(entry_id PRIMARY KEY REFERENCES diary_entries(id) ON DELETE CASCADE, short_title)`.
- 빈 별칭은 행 삭제/원래 이름 사용. 프로젝트 별칭은 최대 24 Unicode scalar, 작업 별칭은 최대 80, 둘 다 한 줄·제어문자 금지. 표시는 별도로 grapheme 단위를 지킨다.
- 별칭 편집은 `project_record_receipts.managed_snapshot`에 포함시키지 않는다. 외부 전달이 별칭을 지우지 않는다. 실제 본문/제목/프로젝트 편집은 기존 사용자 수정 충돌 보호를 유지한다.
- 스키마 3→4는 트랜잭션으로 테이블만 추가한다. 기존 행/본문/검색 인덱스와 영수증을 다시 쓰지 않는다. 원본 기록 편집+표시명 저장은 하나의 트랜잭션으로 처리한다.
- 오래된 EXE는 새 스키마를 거절할 수 있으므로 구현 때 첫 마이그레이션 전 일관된 SQLite 백업을 준비하고 실패 복구를 검증한다. 사용자 데이터 폴더 이동이나 과거 EXE로의 자동 되돌리기는 하지 않는다.
- 달력용 범위 쿼리는 본문·출처 원문을 읽지 않고 날짜별 정확한 개수와 최대 4개 머리말만 반환한다. 일별 SQL 루프를 돌리지 않는다. 상세 본문은 클릭 시 읽는다.
- 기존 저장 성공/기록 수신/범위 변경 경로로 새로고침한다. 매초 전체 DB를 훑는 타이머, 새 상주 프로세스, 모델 호출을 추가하지 않는다. 일반 일정 MCP의 도구와 응답은 유지한다.

## 대안과 이번 범위

| 대안 | 장단점 | 결정 |
|---|---|---|
| 프로젝트+작업 한 줄 | 촘촘하지만 서로의 공간을 빼앗음 | 선택하지 않음 |
| 프로젝트 위·작업 아래 두 줄 | 읽기 순서가 명확하고 정보량은 감소 | **사용자 선택** |
| 날짜마다 프로젝트별 그룹 카드 | 같은 프로젝트 반복은 줄지만 높이가 변하고 작은 위젯에 불리함 | 보류 |

이번 범위는 기존 기록의 식별·표시·상세·공통 수정이다. 다음 3단계의 기록 반영 승인, 4단계의 여러 저장소 자동 수집, 5단계의 Space 전송/기존 검증 오류 수정, 6단계의 개인 서버는 포함하지 않는다. 앱 내 수정은 이번에 Space 원격 본문을 자동 변경하지 않는다.

## 완료 기준

- 동일 날짜에 서로 다른 프로젝트 3개가 있어도 두 줄로 구별되고 전체 제목은 상세에서 읽힌다.
- 두 줄 또는 프로젝트명 토글로 소속을 식별할 수 있다. 주 수와 배율에 따른 축약 전환을 검증하며, 축약 행조차 못 넣는 극소 높이의 집계 예외는 클릭해서 전부 읽을 수 있다.
- 앱→위젯, 위젯→앱의 제목·날짜·본문·프로젝트·별칭 수정 왕복이 같은 ID에서 반영된다.
- 미저장 초안, 자동 수신, 저장 실패, 삭제된 프로젝트, 200개 초과 기록을 잃거나 조용히 덮어쓰지 않는다.
- 두 테마, 한글/영문/이모지, 100/150/200% 배율, 작은/보통/큰 위젯에서 텍스트·더 보기·클릭 영역이 겹치지 않는다. 상태 전환으로 달력 배치가 흔들리지 않는다.
- 축약 토글을 열고 닫아도 날짜 칸 높이·이웃 위치·스크롤 오프셋이 동일하다. 펼침창은 창 경계 안에 있고 다른 행을 실수로 선택하지 않으며, 키보드·Esc와 상세 진입을 확인한다.
- 초기 목록 로딩에서 본문을 읽지 않고, 기존 유휴 작업/프로세스 수를 늘리지 않는다. 같은 fixture의 스크롤·렌더링 검사와 자원 비교를 수행하되 수치를 측정 전 보장하지 않는다.
- 사용자에게 실제 Iced 시안과 EXE를 제공하고 화면 확인을 받은 뒤에만 머지한다. 계획 문서 승인은 실제 앱 테스트 승인을 대신하지 않는다.

## 계획 검토 결과

- 독립 검토에서 여러 주를 표시할 때 45px 두 줄이 보통 창에도 들어가지 않는 문제가 지적됐다. 사용자의 프로젝트명 토글 선택을 반영해 실제 높이에 따른 두 줄/축약/집계로 정리했고 재검토에서 해당 모순 해소를 확인했다.
- 날짜 목록의 50개 페이지를 읽는 중 수신/편집으로 정렬이 바뀌면 기존 세대의 offset 응답을 버리고 첫 페이지부터 다시 읽는다. 본문을 미리 가져오거나 모든 기록을 메모리에 복사하지 않는다.
- 대화용 시안은 가상 기록을 사용하는 브라우저 모형이다. 두 테마·좁은 폭, 토글 시 날짜 위치 유지, 별칭 변경의 두 화면 반영, 더 보기와 상세 선택을 확인했다. 실제 Iced·Windows 입력·배율·자원 사용은 구현 후 검증 항목이며 지금 통과했다고 주장하지 않는다.
