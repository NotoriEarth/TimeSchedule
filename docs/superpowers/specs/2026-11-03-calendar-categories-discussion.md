# 날짜 항목 분류와 프로젝트 기록 재정리

상태: **설계 협의 중. 기존 2단계 문서의 분류·입력·우선순위보다 이 문서의 최신 사용자 요구가 우선한다. 제품 구현 전이다.**

## 사용자에게서 확정된 요구

- 분류는 DB의 원본 종류가 아니라 위젯·다이어리의 날짜에 표시할 항목 종류다.
- 기본 분류는 **일정(기존 할 일 포함)**과 **프로젝트 기록(개발 기록·Git 커밋·트러블슈팅 포함)**이다.
- 사용자가 분류를 추가할 수 있어야 한다.
- 일정 입력은 제목 바로 아래 내용을 입력할 수 있게 구성한다.
- Google Calendar를 참고할 범위는 추가 응답으로 **제목·내용·날짜/시간·종일·완료의 기본 입력**을 선택했다. 반복 일정·알림까지 포함하는 선택은 하지 않았다. Google 계정 연결/동기화를 요청한 것으로 해석하지 않는다.
- 기본 두 줄 시안으로 구현한다. 프로젝트명 토글 시안은 보관 대안이다.
- 일정이 프로젝트 기록보다 먼저 표시된다. 완료된 일정은 이전에 선택한 `완료 N개` 접기를 유지한다.
- 현재 프로젝트에 어떤 내용이 어떻게 적히는지 먼저 설명하고 구조를 정리한다. 이 변경을 반영한 실행 계획은 아래 제안이 정리된 후 다시 작성한다.

## 현재 코드에서 확인한 사실

### 일정과 할 일

`CalendarEvent`에는 제목, 날짜, 시작/종료 시각, 종일, 본문(`notes`), 색상, 완료 여부가 있다. `Task`에는 제목, 선택 날짜, 완료 여부가 있고 본문은 없다. UI도 `Kind::Event`와 `Kind::Task`를 구분하며 본문 편집기는 Task에 표시하지 않는다. 일정 본문은 현재 제목 바로 아래가 아니라 날짜/시간/색상/완료 항목 뒤에 있다.

일정은 현재 하루의 시작/종료 시각으로 저장한다. 여러 날짜에 걸친 일정, 시간대, 반복, 알림과 같은 Google Calendar의 모든 동작이 이미 지원된다는 의미는 아니다. 날짜 없는 기존 할 일을 날짜 칸으로 강제로 옮기지 않는다.

근거: `crates/timeschedule-core/src/storage.rs::CalendarEvent`, `Task`; `apps/timeschedule-native/src/editor.rs::Kind`, `Form`; `views.rs::editor_view`.

### 프로젝트 자체

프로젝트 원본은 ID, 이름, 설명, 로컬 Git 저장소 경로, 수정 시각을 보관한다. 프로젝트 화면은 프로젝트 선택 목록, 설명/저장소 경로, Git 커밋 수집·근거 요약·포트폴리오 초안 버튼, 선택한 날짜 범위의 기록 목록 순이다. 전체 영구 이력을 항상 한 번에 보여주는 화면은 아니다.

### 프로젝트에 연결된 기록

각 기록은 별도의 ID와 프로젝트 ID, 날짜, 종류, 제목, 본문, 출처 링크, 수집 참조, 수집 원문, 수정 시각을 보관한다. `diary_entries`의 현재 종류는 자유 노트·개발 기록·트러블슈팅·Git 커밋·근거 요약·포트폴리오 초안 6종이다. 이것들은 앞으로 날짜 칸에 표시할 최상위 분류 6개라는 뜻이 아니다.

현재 프로젝트 목록은 날짜 → 종류/제목이며, 제목을 펼치면 본문·출처·수집 원문·수정 버튼을 보여준다. 정렬은 날짜 내림차순, 수정 시각 내림차순, ID이며 목록은 200개 단위다. 일정·할 일은 현재 프로젝트 ID를 갖지 않는다.

- **Git 커밋 수집:** 커밋 하나를 `commit` 기록 하나로 저장한다. 첫 줄을 제목, 전체 커밋 메시지를 본문/수집 원문, 저장소+커밋 해시를 중복 방지 근거로 사용하며 가능한 경우 커밋 URL을 붙인다. 같은 저장소 루트+해시를 다시 수집하면 기존 항목을 갱신하지 않고 건너뛴다.
- **개발 작업 자동 전달:** 전달받은 작업 제목·종류·날짜와 상세 원문을 저장한다. schema 2 본문 뒤에는 작업 상태와 Space 연결 상태가 붙고, 요약은 수집 원문 필드에 보관된다. 같은 workId의 더 높은 revision이고 기존 관리 원본에 사용자 편집이 없을 때 같은 기록 ID를 갱신한다. 동일 입력은 unchanged, 오래된 revision은 stale, 사용자 수정·삭제는 conflict로 보존한다. 저장소 경로에 일치하는 프로젝트가 없으면 생성하며, 하나면 연결하고 여러 개면 오류로 수신을 중단해 프로젝트 연결 정리를 요구한다.
- **현재 한계:** 작업 단위 자동 전달과 커밋 단위 수집은 별도 경로다. 관련 Git 커밋이 작업 기록의 하위 근거로 자동 연결되거나 같은 작업으로 의미상 병합되는 구조는 아니다. 사용자 DB의 실제 중복 유무는 이번 조사에서 읽지 않았다.

근거: `diary.rs::Project`, `Entry`, `list_entries`, `store_commits`; `project_records.rs::apply_project_record`; `views.rs::projects`, `entry_card`; `docs/project-records.md`.

## 제안 · 분류와 프로젝트를 분리

| 개념 | 예시 | 의미 |
|---|---|---|
| 날짜 항목의 분류 | 일정 / 프로젝트 기록 / 사용자가 추가한 학습 | 날짜 칸에 어떤 종류의 내용을 넣었는가 |
| 소속 프로젝트 | TimeSchedule / 견적 관리 | 어느 프로젝트에 관한 내용인가 |
| 프로젝트 기록의 세부 종류 | 개발 / 트러블슈팅 | 그 프로젝트에서 어떤 성격의 작업인가 |
| 근거·입력 경로 | 직접 입력 / Git 커밋 / 개발 작업 전달 / Space 링크 | 어떤 자료로 작성됐는가 |

Git 커밋은 사용자에게 개발 기록의 일부로 보여주되 해시·원문은 근거로 보존하는 안을 권장한다. 기존 커밋을 임의로 같은 작업에 합치거나 본문을 지우지 않는다. 자유 노트·근거 요약·포트폴리오 초안의 기존 데이터도 보존하고, 새 분류로 옮기는 정책을 구현 설계에서 명시한다.

## 제안 · 입력과 표시

### 일정

- 공통 입력 순서: 제목 → 내용(여러 줄, 선택) → 날짜/시간·종일 → 완료.
- 기존 할 일도 같은 일정 목록과 편집 흐름에서 사용한다. 날짜가 없는 항목은 미배정 목록에 남기고 날짜를 지정하면 해당 날짜에 표시한다.
- 달력 칸에는 시간/종일과 제목을 우선 표시하고, 전체 내용은 항목을 열었을 때 제목 아래에서 읽고 수정한다. 달력의 모든 칸에 긴 본문을 펼쳐 높이를 늘리지 않는다.
- 일정·할 일을 실제 하나의 저장 원본으로 이관할지, 기존 ID를 보존하는 공통 모델로 먼저 묶을지는 구현 설계에서 결정한다. 단순히 메뉴 이름만 바꾸고 할 일 본문 입력이 안 되는 상태를 통합 완료로 간주하지 않는다.
- 기존 일정 MCP의 ID·편집 충돌 보호·왕복 결과를 보존해야 한다. 날짜 없는 항목·일정 범위·기존 할 일 이관·검색도 재검증 대상이다.

### 프로젝트 기록

- 프로젝트 선택 → 세부 종류(개발/트러블슈팅) → 작업 제목 → 내용 → 작업 날짜 → 관련 자료.
- 날짜 칸의 기본 두 줄은 프로젝트명 / 짧은 작업명이다. 종류·커밋 해시·긴 본문은 상세에 둔다.
- 프로젝트 화면은 프로젝트 소개 아래 날짜별 작업 기록을 읽는 구조를 권장한다. 작업 기록 상세에는 변경 내용, 문제/원인/해결(해당될 때), 검증/남은 일, 관련 커밋·자료를 보여준다. 근거 없는 필수 문단이나 AI 재요약은 만들지 않는다.
- 한 작업에 커밋 여러 개를 연결하는 것은 권장 방향이다. 기존 개별 커밋을 자동 추정해 묶는 기능은 별도 설계 없이 추가하지 않는다.

### 사용자 분류

- 일정/프로젝트 기록과 같은 수준에서 `분류 추가`를 제공한다. 이름·색상·표시 순서·표시 여부를 변경하는 구성을 제안한다.
- 분류 이름을 안정된 ID와 분리해 이름 변경이 기존 항목 연결을 깨뜨리지 않게 한다. 분류 숨김/보관은 항목 삭제를 뜻하지 않는다.
- 경량 구현 대안: (A) 기록형 공통 입력에 이름/색만 추가, (B) 일정형 또는 기록형 공통 입력을 선택한 뒤 이름/색을 지정. **B를 제안**한다. 운동 같은 계획과 학습 일지 같은 기록을 기존 입력 두 종류로 처리할 수 있다. 사용자 정의 필드·수식·범용 폼 제작기는 만들지 않는다.
- 새 분류의 기본 위치는 기존 분류 뒤로 두고 순서를 조정할 수 있게 하는 안이다. 사용자 설정 전에는 일정이 프로젝트 기록보다 우선한다. 앱·위젯은 같은 분류 설정을 사용한다.

## 남은 설계 결정

- 사용자 분류를 이름/색만 바꿀지, 일정형/기록형 입력도 고를지.
- 기존 자유 노트·근거 요약·포트폴리오 초안의 새 분류 연결 정책.
- 일정 통합 저장 방식과 날짜 미지정/여러 날짜 일정의 정확한 범위, 기존 MCP·Tauri와의 호환.

위 내용은 현재 구조 설명과 제품 제안이며 확정된 구현 인터페이스가 아니다. 기존 두 줄 표시 실행 계획에 분류 테이블·일정 통합을 끼워 넣어 바로 실행하지 않는다. 설계가 정리되면 데이터 보존 → 입력 통합/분류 관리 → 공통 표시·상세/편집 → 검증 순으로 계획을 다시 나눈다.

## 참고

Google Calendar의 이벤트 모델은 제목(`summary`), 설명(`description`), 시작/종료 날짜 또는 시각을 구분한다. 완료 체크는 TimeSchedule의 기존 기능을 유지하는 요구다. [Google Calendar 공식 이벤트 문서](https://developers.google.com/workspace/calendar/api/v3/reference/events). 이번에 선택한 기본 입력 범위를 Google Calendar 전체 기능 동등성이나 동기화로 표현하지 않는다.

이 작업은 코드 읽기·분류 설계 문서만 변경한다. 버전·EXE·사용자 데이터·개발 기록 prepare/sync는 변경하거나 실행하지 않는다.
