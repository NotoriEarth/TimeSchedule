# 0.8.0 자동 기록 검증

2026-10-31 Windows 환경에서 확인했다. 사용자 테스트 및 PR #8 병합 승인은 별도다.

## 자동 검증

- `cargo test --workspace --locked --offline`: 코어 33개, 플랫폼 12개, 네이티브 65개, 총 110개 통과. 기존 자식 프로세스 fixture와 수동 렌더 미리보기 각 1개는 의도적으로 제외된다.
- `cargo fmt --all -- --check`: 통과.
- `node --test tests/*.test.mjs`: 12개 통과. PR 없는 기록, 동일 내용 생략, Space 성공 후 다이어리 재시도, queued/충돌 구분, 불확실한 생성 복구, 한계 문단 보존, 실제 도구 읽기 검증, 동시 프로세스 잠금을 포함한다.
- Tauri 테스트: 3개 및 실제 Windows 창 통합 1개 통과. 공통 코어의 serde_json 의존성 추가를 Tauri lockfile에도 반영했다.
- 디버그 EXE의 `record enqueue/status`를 격리 DB에서 실행했다. 반복 전달 후 항목은 1개이며 entry ID와 Space URL이 유지됐다. 사용자 DB에는 이 시험 데이터를 넣지 않았다.

## 실제 Space 전달

[이번 개발 기록](https://chatgpt.com/space/page_fdbfca54dc988191a30560abf42934d6)을 기존 포트폴리오 아래에 만들었다. 로그인된 Codex 0.163.0, GPT-6 Luna medium과 실제 Pages 도구를 사용했다.

첫 시도에서 모델이 문장 끝 `3d3fab6이다.`를 `3d3fab6.`으로 바꿨다. 실제 전체 본문 비교가 이를 차단했고 다이어리에 전달하지 않았다. 실제 create/read 결과에서 같은 페이지 ID를 보존하고, 계산한 원문 차이를 제공해 복구한 후 본문과 부모 링크 검증이 통과했다. 모델의 “저장 완료” 선언만으로 성공 처리하지 않았다. 첫 저장·복구 확인에는 총 3회 모델 실행이 필요했다.

그다음 EXE 경로가 없는 실패를 의도적으로 발생시켰고 `space_saved` 상태가 보존됐다. 실제 EXE로 해당 원문 요약과 검증된 URL을 격리 DB에 저장·재전달했을 때 하나의 항목으로 유지됐다.

기존 `timeschedule` 자동화의 ID·오전 9시 주기·대상 채팅을 유지하고 같은 전달 절차로 갱신했다. 예약 시각의 실제 실행까지 시험한 것은 아니다. heartbeat 자체의 모델은 변경하지 않았으며 기록용 하위 CLI만 Luna medium을 명시한다.

최종 검증 결과를 같은 페이지의 revision 2로 갱신하는 추가 실행은 원문 검증을 한 번에 통과했다. 최종 EXE로 실제 사용자 다이어리에 저장해 `complete` 수신 결과를 확인했다. 바로 재실행했을 때 `skipped: true`였으며 모델 호출 누계는 4회에서 증가하지 않았다.

## 사용자 확인 순서

1. `artifacts/TimeSchedule.exe`를 실행하고 앱 설정 또는 Windows 파일 속성에서 0.8.0을 확인한다.
2. 다이어리의 2026-10-31 또는 TimeSchedule 프로젝트에서 “Space 중심 개발 기록과 다이어리 자동 연결”을 찾는다.
3. 기록을 펼쳐 요약을 읽고 출처 링크로 Space 상세 기록이 열리는지 확인한다.
4. 기존 일정·메모·편집 내용이 유지되는지 확인한다. 미저장 편집 중 도착한 외부 기록은 저장·닫기 후 안전한 시점에 반영한다.

실제 한글 입력·링크 클릭·사용자 데이터의 육안 확인은 사용자 테스트 범위다. 링크는 기존 HTTPS 검증과 Windows `ShellExecuteW` 경로를 재사용한다.

## 실행 중 앱과 독립 검토

0.8.0 테스트 전용 앱을 격리된 DB로 실행했다. 창 생성과 0.8.0 제목을 확인하고 CLI로 기록을 전달했을 때 처음에는 `queued`가 반환됐다. 앱의 주기 처리 후 수신 결과가 `saved`로 바뀌었고 로그에 기록 1개·프로젝트 1개로 새 목록을 조회한 사실이 남았다. 화면 캡처는 선택·재선택 후 두 번 시간 초과가 발생하여 클릭·시각 배치는 확인했다고 주장하지 않는다. 해당 테스트 프로세스만 종료했으며 사용자 앱은 사용자 종료 확인 후 교체했다.

GPT-6 Astra의 독립 전체 변경 리뷰에서 두 문제를 발견해 수정했다. 수신 결과 파일 쓰기가 실패하기 전에 DB가 커밋되면 화면의 오래된 본문으로 덮어쓸 수 있었으므로 실패와 재전달 뒤에도 캐시를 비우고 재조회한다. 오래된 PID 잠금을 두 프로세스가 동시에 복구하는 경쟁은 OS가 소유하는 Windows named pipe 잠금으로 없앴다. 두 재현 테스트가 실패하는 것을 확인한 뒤 수정해 전체 테스트를 다시 통과시켰다. 남겨둔 사소한 리뷰 지적은 없다.

## 구현 판단과 한계

- 같은 작업의 독립 브랜치를 이어 사용했다. 다른 작업과 작업 공간을 공유하게 되면 새 격리가 필요하다.
- 사용자의 Space 우선·선택적 PR 재사용 정정을 구현 방향으로 반영했다. PR 병합 승인으로 해석하지 않았다.
- 큐 이름은 엄격히 검증한 UUID와 revision을 사용한다. 내용 해시 대신 불변 원문과 수신 결과를 비교한다.
- 검증 스크립트는 Git Bash의 다른 `link.exe`를 피하기 위해 기존 PowerShell toolchain을 사용했다. 다른 환경에는 해당 컴파일러 설정이 필요하다.
- 수신 결과는 당시 전달의 확인이다. 이후 사용자가 편집·삭제한 현재 내용을 인증하지 않으며 코어는 이를 자동 복원하지 않는다.
- 생성 결과가 불확실하면 보수적으로 기존 페이지만 확인한다. 일부 CLI 실패 뒤 수동 확인이 필요할 수 있다.
- Space와 로컬 DB 사이에 분산 트랜잭션은 없다. 검증 직후의 별도 사용자 편집까지 동시에 고정할 수는 없다.
- Windows가 지원 대상이다. 비 Windows 테스트용 loopback 잠금은 포트 충돌 시 안전하게 실행을 거부할 수 있다.
- 의미 없는 코드 형식 변경은 추가하지 않았다. 머지는 사용자 테스트 이후 별도 승인 단계다.
