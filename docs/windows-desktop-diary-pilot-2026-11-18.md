# Windows Codex 앱에서 버그 수정과 개발 일지 복구 시험

2026년 11월 18일 한국 시각에 Windows Codex 앱의 독립 프로젝트 `m0-sample`에서 시험했다. 한 사람이 순서대로 작업하는 Git 브랜치 한 개에서 에이전트가 기록을 따로 부탁받지 않아도 일지를 남기는지, 전달을 한 번 건너뛰면 다음 채팅이 찾아서 복구하는지 살폈다.

**개발 작업 2건을 앱 채팅 3개로 시험했다.** 첫 작업은 자동으로 저장됐다. 두 번째 작업은 전달을 생략했고, 다음 채팅이 일반적인 프로젝트 질문을 처리하면서 복구했다. 두 일지의 정식 회귀 테스트 이름·결과·종료 코드가 Git 커밋 독립 재실행과 일치했다. 일지 목록에서 빠진 즉석 검사 2건도 확인해 보완 방법을 시험했다.

## 첫 채팅에서 기록을 언급하지 않고 버그 고치기

> CSV에서 큰따옴표 안에 들어간 쉼표까지 열 구분자로 처리돼요. 이 버그를 고쳐 주세요.

에이전트는 시작 검사를 실행하고 작업 ID를 받았다. 공개 `comma_in_quotes` 표본의 도시 값 `"Anytown, WW"`가 갈라져 다음 열인 우편번호까지 밀렸다. 모든 쉼표를 먼저 자르면 바깥 따옴표를 나중에 제거해도 원래 열 경계를 찾을 수 없었다. 에이전트는 헤더와 데이터 행이 공유하는 함수가 따옴표 안인지 추적하도록 고쳤다. 일지에는 이 선택 이유와 기대한 우편번호 `08123`이 남았다.

| 대상 커밋 | 독립 재실행 결과 | 일지와 대조 |
| --- | --- | --- |
| 회귀 테스트 `6bed0e9` | 3개 통과, `comma_in_quotes` 1개 실패, 종료 코드 1 | 결과 4개의 이름·상태 일치 |
| 수정 `28fb0cf` | `simple`, `simple_crlf`, `utf8`, `comma_in_quotes` 통과, 종료 코드 0 | 결과 4개의 이름·상태 일치 |

앱 채팅의 명령 이력에서 `diary.mjs test`의 종료 코드 1과 0, 에이전트가 실행한 `diary.mjs finish`의 종료 코드 0을 확인했다. 진행자가 일지를 작성하거나 전달할 필요가 없었다. 두 커밋은 문서 한 개와 다이어리 한 건으로 저장됐고 상태는 `local_complete`였다.

## 두 번째 채팅에서 기록 한 건을 의도적으로 빠뜨리기

> UTF-8 BOM이 붙은 CSV를 열면 첫 번째 열 이름에 보이지 않는 문자가 들어갑니다. 고쳐 주세요.

두 작업 사이에 사용 예제의 위치만 적은 문서 커밋 `f34a487`을 넣었다. 두 번째 작업을 시작할 때 시험 폴더의 표시가 `delivery: paused`를 반환하게 했다. 에이전트는 테스트와 커밋을 수행하고 지침대로 `finish`를 건너뛰었다. 이 시점에 두 번째 작업의 테스트 영수증과 커밋은 있었고, 전달 입력과 `state.json`은 없었다. 문서와 DB에는 첫 작업 한 건만 있었다.

오류 원인은 파일 시작의 BOM이 첫 헤더의 일부가 된 데 있었다. 첫 글자가 따옴표인지 보는 코드도 영향을 받았다. 에이전트는 입력 시작에서 BOM 한 글자만 제거했다. 이름에 쉼표가 든 헤더가 한 열로 유지되고, 데이터 값 내부의 U+FEFF가 보존되는지 같은 회귀 테스트에서 확인했다.

| 대상 커밋 | 독립 재실행 결과 |
| --- | --- |
| 회귀 테스트 `dfce100` | 기존 4개 통과, `ignores a UTF-8 BOM only at the start of the CSV` 실패, 종료 코드 1 |
| 수정 `8f03493` | 기존 4개와 새 테스트 1개 통과, 종료 코드 0 |

두 개발 채팅만 지정해 SpecStory를 한 번씩 내보냈다. 수집기는 내보낸 명령 출력에서 작업 ID와 시작 커밋을 읽고, 당시 완료 답변의 커밋이 일치할 때 원래 답변을 발췌했다. 시험자가 복구할 작업의 번호를 본문에 적거나 새로운 요약을 작성할 필요가 없었다. 원문과 발췌는 시험 PC에만 보관했다.

## 세 번째 채팅에서 복구 요청 없이 복구하기

> 이 프로젝트에서 어떤 CSV 입력을 다루는지 짧게 알려 주세요.

전달 중지 표시를 해제한 뒤 같은 프로젝트에 새 앱 채팅을 열었다. 이때 진행자는 복구 명령을 실행하지 않았다. 에이전트가 첫 검사에서 `8f03493` 한 건을 찾았다. 해당 작업의 원래 완료 답변 발췌를 읽고 커밋과 테스트 파일을 확인한 뒤, 원래 작업 ID로 `recover`를 실행했다. 복구한 일지에는 파일 맨 앞의 BOM을 지우기로 한 이유와 데이터 안의 U+FEFF를 보존한 범위가 남았다. 원문 파일과 SQLite 본문에 표시한 수정 전·후 테스트 5개의 이름과 결과가 독립 JUnit 재실행과 일치했다.

| 한국 시각과 관측 시점 | 확인된 누락 | 원문 파일 | SQLite 다이어리 |
| --- | --- | --- | --- |
| 14:52 첫 버그의 자동 저장 후 | 0건 | 1개 | 1건 |
| 14:58 두 번째 버그까지 커밋하고 전달 생략 | BOM 작업 1건 | 1개 | 1건 |
| 15:02 새 채팅의 첫 검사 | 같은 BOM 작업 1건, 전달 대기 0건 | 1개 | 1건 |
| 15:03 새 채팅의 복구 및 재검사 | 0건, 전달 대기 0건 | 2개 | 2건 |
| 15:05 진행자가 두 작업을 같은 ID로 각각 재전달 | 0건, 전달 대기 0건 | 2개 | 2건 |

복구 전후 첫 일지의 항목 ID와 본문 해시가 같았다. 재전달 전후 두 항목의 ID, 본문 해시, 파일 수정 버전, DB 수신 버전이 모두 같았다. 사이에 넣은 문서 전용 커밋은 누락으로 표시되지 않았다. 누락을 찾은 경로는 새 채팅의 프로젝트 지침이었다. 시험 폴더에 있던 종전 관측 훅은 이 기록과 복구를 실행하지 않았다.

## 다시 확인할 수 있는 자료

이 PC에서 독립 Git 프로젝트는 `C:\LSH\_capture-lab\m0-sample`의 `codex/windows-diary-pilot` 브랜치다. `.agents/skills/development-diary/SKILL.md`에서 기록·복구 지침을, `.capture/diary-live/vault/projects/`에서 두 원문을, `.capture/diary-live/app-data/schedule.db`에서 다이어리를 볼 수 있다. 기존 TimeSchedule의 실제 문서 저장소와 다이어리는 사용하지 않았다.

시험 당시의 복원 코드, 원본 없는 집계와 이 보고서 사본은 TimeSchedule 작업 폴더의 `artifacts/record-lab/2026-11-18-windows-diary/`에 있다. `evidence/normal.json`, `omitted.json`, `recovered.json`, `retried.json`에 단계별 커밋과 검사 결과가 남는다. `scope-probe.json`에는 즉석 검사와 전체 공개 표본을 다시 실행한 결과가 있다. 원문 대화는 이 폴더의 로컬 자료로만 유지한다.

```powershell
# TimeSchedule 작업 폴더에서 두 일지와 네 커밋을 다시 대조
python -X utf8 artifacts/record-lab/2026-11-18-windows-diary/verify.py retried

# 별도 복사본에서 이름 있는 BOM 검사 2개와 공개 표본 6쌍 재실행
python -X utf8 artifacts/record-lab/2026-11-18-windows-diary/scope_probe.py
```

**도입 판단.** 이 구성으로 프로젝트 한 곳에서 시범 운영할 수 있다. 첫 실전 표본에서는 일지에서 읽은 테스트 범위가 실제 출력과 같은지, 누락 후보를 다른 사람의 작업과 구별할 수 있는지 확인하는 것이 우선이다. 이번 시험에서는 작업 시작 ID와 테스트 근거가 남은 상태에서 전달 한 건을 의도적으로 누락시켰다. 시작 표시까지 없는 작업, 여러 사람이 섞인 브랜치, 강제 종료, 실시간 SpecStory 수집, 장기간의 자연 발생 누락률은 검증 범위 밖이다.
