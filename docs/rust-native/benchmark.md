# Tauri · Rust 네이티브 비교 벤치마크

2026-10-29 정식 20회 측정 완료. **기본 월간 상세창과 위젯을 연 유휴 상태에서 Rust 네이티브의 전용 상주 메모리는 약90% 낮았지만, 유휴 CPU 사용량은 높았다.** 이번 결과로 모든 화면의 속도나 전체 기능의 동등성을 판단하지 않는다.

## 결과

| 합성 자료 | Tauri 전용 상주 RAM | Rust 전용 상주 RAM | 감소율 | Tauri CPU | Rust CPU |
|---|---:|---:|---:|---:|---:|
| 소형: 일정1천·기록2천 | 141.24MiB | 12.96MiB | 90.82% | 0.01294% | 0.03993% |
| 대형: 일정1만·기록2만 | 146.02MiB | 15.16MiB | 89.62% | 0.01316% | 0.13385% |

RAM은 앱과 자식 프로세스의 **private working set** 합계다. 각 실행의 유효 표본 중앙값을 구한 뒤5회 중앙값을 표시했다. CPU는 실제 표본 간격으로 가중한 실행별 평균의5회 중앙값이며, 위 표는12논리 프로세서 전체 용량 기준이다. 한 논리 코어100% 기준으로는 소형0.1553→0.4792%, 대형0.1579→1.6062%다. 네이티브 유휴 CPU 중앙값은 각각3.09배·10.17배로, 절대 사용량은 낮지만 메모리와 같은 방향으로 개선되지는 않았다. 원인을 규명하는 프로파일링은 하지 않았다.

| 자료 / 앱 | RAM 실행별 중앙값 범위(MiB) | CPU 실행별 가중평균 범위(한 코어 기준 %) | working set 합계 중앙값(MiB) | private commit 중앙값(MiB) |
|---|---:|---:|---:|---:|
| 소형 / Tauri | 139.52–145.08 | 0.1294–0.9476 | 486.68 | 250.14 |
| 소형 / Rust | 12.92–13.02 | 0.4016–0.6345 | 29.90 | 14.05 |
| 대형 / Tauri | 139.34–149.03 | 0.1295–0.2200 | 491.54 | 286.70 |
| 대형 / Rust | 15.09–15.18 | 1.5535–1.7091 | 32.08 | 16.61 |

소형 Tauri의 높은 CPU 실행도 제외하지 않았다. 범위가 겹치므로 모든 개별 실행에서 Rust CPU가 높았다는 뜻은 아니다. working set 합계는 프로세스 간 공유 페이지를 중복 계산하므로 절감률의 대표 지표로 사용하지 않았다. private commit은 실제 RAM 상주량이 아니다. 이전 빈 DB에서 보고한 네이티브27.23MiB도 일반 working set 순간값으로, 이번 전용 상주 RAM과 지표·자료·집계 방식이 다르다.

실행 파일은 Tauri7,805,440bytes, Rust5,545,984bytes로29.0% 작다. WebView 런타임 설치 용량을 포함한 총 설치 크기 비교는 아니다.

## 증거와 유효 표본

[전체 집계와 실행별 요약](benchmark-results.json), [2,400개 표본 CSV](benchmark-samples.csv)를 저장소에 포함했다. 상세 프로세스 원본·실행별 DB·프로필은 로컬 `.test-data/benchmark/runs/comparison-final`에 보존한다.

- 소형 Tauri: RAM598/600, CPU596/600; 소형 Rust: 각각600/600.
- 대형 Tauri: RAM599/600, CPU598/600; 대형 Rust: 각각600/600.
- 총 RAM2,397/2,400, CPU2,394/2,400 유효. `small-p1-tauri`, `small-p4-tauri`, `large-p4-tauri`의59번째 표본에서 자식 프로세스가 수집 중 종료되어 해당 합계를 제외했다. 그 다음 표본은 이전 CPU 기준점이 없어 CPU만 추가 제외했다. 누락을0으로 바꾸지 않았다.
- 실제 간격 평균1.0057초, 범위0.6109–6.6280초. 수집 자체 평균0.6855초, 최대6.2634초로 관측 도구 비용이 있다. 정확한1초 타이머나 정밀 시작시간 벤치마크가 아니다.
- 20회 모두 완료했고 실행 파일과 원본 fixture 해시는 전후 동일했다. 실행을 소유한 프로세스만 정리했으며 종료 오류는 없었다.

fixture 무결성·외래키·FTS·한국어 검색·장문·재현성·기존 파일 덮어쓰기 거부 테스트와 측정기의 PID/시작시각/경로·누락 카운터·CPU 단위·프로세스 정리 테스트를 통과했다. 고정된 측정기와 fixture는 독립 검토 후 실행했다.

## 프로토콜

- 소형: 일정 1,000개, 기록 2,000개, 프로젝트 10개. 대형: 일정 10,000개, 기록 20,000개, 프로젝트 50개.
- 고정 날짜 2026-10-29 기준 합성 자료에 한국어·링크·100,000자 본문을 넣는다. 결정적 ID·본문·논리 데이터 해시를 검증한다. 사용자 자료는 넣지 않는다.
- 매번 동일 fixture의 독립 DB 복사본으로 시작한다. 데이터셋별로 두 후보를 번갈아 5회씩 실행한다.
- 각 실행에서 60초 안정화 후 1초 간격 목표로 120회 표본을 수집한다. 실제 표본 간격과 누락/제외 사유를 함께 남긴다.
- 앱과 자식 프로세스의 private working set, working set 합계, private commit, CPU 사용을 구분한다. shared working set 중복과 commit/실제 상주 RAM 차이를 명시한다.
- 기본 월간 시작 상태의 유휴 사용량을 우선 비교한다. 실제 화면 크기·표시 상태와 시작 관측 기준을 기록한다. 창 생성 시간과 화면 사용 가능 시간을 같은 것으로 취급하지 않는다.
- 위젯만 남긴 상태, 검색·긴 노트 편집, 닫기/재열기는 지원되는 UI 도구로 실제 조작·확인한 경우에만 결과에 포함한다.

## 해석의 범위

사전 실행에서 확인한 환경은 Windows 10 Pro 19045, Ryzen 5 5600X(6코어·12논리 프로세서), 약32GiB RAM, WebView2 156.0.4314.50이다. 두 상세창은 외곽1176×859 / 내용1160×820,96DPI이며 표시·비최소화 상태였다. 바탕화면 위젯은 Tauri900×560, native500×620으로 다르다. 정식 실행별 상태는 raw summary에 다시 기록한다.

| fixture | 일정 / 기록 / 프로젝트 | 할 일 / 메모 | DB 크기 | 논리 데이터 SHA256 |
|---|---|---|---|---|
| small | 1000 / 2000 / 10 | 100 / 20 | 9,560,064 bytes | 3F194DC2376D5A6A61B362B0CF0CAC6BA9A6745B7A2C058F8119F7E87E7FCD33 |
| large | 10000 / 20000 / 50 | 1000 / 100 | 68,509,696 bytes | 69941896E3C1B064503550050631E091F988B3FAC86367041E311880795FC4CE |

자료는2026-04-30~2027-04-29에 분산되어 있으며 장문 기록은2026-10-29에 있다. 본문을 펼치거나 편집하지 않은 기본 월간 상태이므로 장문 편집 부하 결과로 해석하지 않는다. WebView 프로필은 프로세스 범위 `WEBVIEW2_USER_DATA_FOLDER`로 격리하고 관측한 브라우저 프로세스의 경로를 검증했다. 이 오버라이드는 [Microsoft 공식 API 문서](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl?view=webview2-1.0.3967.48)에 설명되어 있다.

사용자가 작업 중인 실제 PC에서 측정했으므로 다른 프로그램의 활동과 캐시·OS 메모리 정책이 영향을 줄 수 있다. 실행 전후에만 읽은 전체 시스템 CPU는0–40%였고, 측정 중 배경 부하를 연속 추적하지 않았다. 같은 자료를 썼다는 사실만으로 화면 배치·기능·렌더링 부하까지 같다고 주장하지 않는다. GPU 메모리, 입력 지연, 장시간 누수, 모든 UI 동작은 별도 검증이다.

실행은 데이터셋별 AB,BA,AB,BA,AB 순서(A=Tauri,B=Rust), 총20회였다. 매 실행 새 WebView 프로필을 사용했지만 OS 캐시는 초기화하지 않았다. 매우 짧게 생겼다가 표본 사이에 종료되는 자식 프로세스는 놓칠 수 있다. 첫 창 핸들 관측은 약1초 폴링과 수집 비용을 포함하며 콘텐츠 준비 완료 신호가 아니므로 시작 속도 우열은 발표하지 않는다.
