# SpecStory로 개발 일지를 복구한 Windows 격리 실험

2026년 11월 18일, 한국 시각. 원격이 없는 작은 CSV 프로젝트에서 개발 에이전트에게 기록을 언급하지 않고 버그 수정을 맡겼다. 이후 새 세션이 작업을 복원하는지, 관련 커밋 두 개가 다이어리 한 건으로 들어가는지, 다른 작업을 일부러 빠뜨렸을 때 다음 세션에서 발견하는지 시험했다.

| 질문 | 관측 결과 |
| --- | --- |
| 대화가 끝난 뒤 무엇을 복원했나 | 새 Codex 세션이 줄바꿈 문제, 재현, 수정 이유, 최종 테스트 결과를 복원했다. 검증 근거를 요청한 요약은 수정 전 실패 수도 맞혔으나 검증 범위 한 문장을 틀렸다. |
| 커밋 두 개가 일지 한 건이 됐나 | 한 작업 ID에 시작·완료 커밋과 변경 파일 두 개를 연결했다. 원문 파일과 실제 SQLite 다이어리 항목이 각각 한 건이었고, 재전달 뒤에도 같았다. |
| 기록을 빼먹으면 알 수 있나 | 다음 Codex 세션의 프로젝트 지침과 Claude Code의 실제 `SessionStart` 훅이 같은 개발 커밋 한 건을 알렸다. 보완 뒤 두 경로에서 누락이 0건이 됐다. 문서 전용 커밋은 경고에 들어가지 않았다. |

## 시험 환경과 재사용한 자료

Windows 10 빌드 19045에서 Node 24.16.0, Git 2.52.0.windows.1, TimeSchedule.exe 0.18.0을 사용했다. 개발·요약·다음 작업은 데스크톱 앱에 포함된 `codex-cli 0.169.0-alpha.11.1`의 독립 `exec` 세션에서 `gpt-6-luna`와 낮은 추론 설정으로 실행했다. 실제 시작 훅 시험에는 Claude Code 2.1.325와 `claude-haiku-5-5`를 썼다.

- **CSV 입력과 정답**은 `csv-spectrum` 2.0.0의 CSV·JSON 12쌍을 그대로 사용했다. npm 배포 파일의 SHA-512를 레지스트리 값과 대조했고, 다시 실행할 때도 시험 저장소의 입력·정답이 배포본과 바이트 단위로 같은지 확인했다. [공개 CSV 표본](https://github.com/maxogden/csv-spectrum/tree/d30e80f8b99d2eecb3778f1d7b9ed1cb425502ec)
- **수집기**는 SpecStory 2.17.0 Windows x86-64 공식 ZIP을 시험 폴더에만 풀었다. ZIP의 SHA-256은 `5029141c5f91ad16f2fd5c12ed225444a1cc1d010c9dd0aad751b8079687c128`이었다. 제작자의 `TestGenerateAgentSession_ThreadItemStream`에서 메시지 순서·예상 문구·도구 개수를 가져와 배포 EXE의 대조군으로 썼다. 세션 ID와 작업 경로만 실험값으로 바꿨다. [공식 배포본](https://github.com/specstoryai/getspecstory/releases/tag/v2.17.0) · [제작자의 Codex 테스트](https://github.com/specstoryai/getspecstory/blob/v2.17.0/specstory-cli/pkg/providers/codexcli/agent_session_test.go#L315)
- **요약 지침**은 `specstory-session-summary` 1.0의 고정 커밋을 두 요약 세션에 동일하게 제공했다. **다이어리 전달**은 시험 프로젝트 안에 복사한 TimeSchedule의 기존 명령과 대표 EXE를 사용했다. 저장 명령이 자기 저장소의 Git 근거를 검사하기 때문에 이 배치가 필요했다. [공식 스킬 원문](https://github.com/specstoryai/agent-skills/blob/9454d3f2b9ac5397d735ae3bbdcfa6dc83392036/skills/specstory-session-summary/SKILL.md) · [TimeSchedule 전달 절차](project-records.md)

개발 저장소, 요약용 폴더, 원문 보관 폴더, 전달 상태, 앱 데이터 폴더를 분리했다. SpecStory에는 시험 세션 하나만 넣은 입력 폴더와 `--no-cloud-sync`를 지정했다. 원본 JSONL은 로컬에 보관했다. 요약 모델에는 공개 CSV 과제의 발화와 테스트 출력을 발췌해 전달했다. TimeSchedule의 Space 설정은 꺼짐이었고, 실제 사용자 다이어리 대신 시험용 `schedule.db`를 사용했다.

## 1. 기록 요청 없이 버그를 수정하고 다시 읽기

개발 세션에는 다음 요청만 전달했다.

> CSV의 따옴표 안 줄바꿈이 다음 행으로 잘못 파싱됩니다. 포함된 공개 csv-spectrum의 LF와 CRLF 예제로 먼저 실패를 재현하고, 원본 줄바꿈을 보존하도록 고쳐 주세요. 회귀 테스트와 구현을 이 로컬 브랜치에 두 커밋으로 나눠 주세요. node --test를 실행하고 확인한 결과를 알려주세요.

기존 파서는 입력을 물리적인 줄로 먼저 쪼갰다. 이때 인용 필드 중간의 LF나 CRLF도 행 경계가 됐다. 에이전트는 공개 입력의 바이트와 기대 JSON을 확인하고 두 예제를 회귀 테스트에 추가했다. 두 테스트가 실패하는 것을 본 뒤, 인용 상태를 유지하면서 레코드 경계를 찾고 인용 밖의 줄바꿈에서만 레코드를 끝내도록 수정했다. 개발 답변을 받은 뒤 시험 담당자가 세 커밋의 트리를 각각 다른 폴더에 복원해 `node --test`를 다시 실행했다.

| 시험 프로젝트 커밋 | 기대한 역할 | 독립 재실행 |
| --- | --- | --- |
| `148556e` | 시작점과 기존 테스트 | 4개 통과, 종료 코드 0 |
| `54fa9d8` | LF·CRLF 회귀 테스트 추가 | 4개 통과, 2개 실패, 종료 코드 1 |
| `703b07f` | 인용 필드 안 줄바꿈 유지 | 6개 통과, 0개 실패, 종료 코드 0 |

**검증 범위를 넓히니 다른 결과가 나왔다.** 구현 커밋에서 공개 입력과 기대 JSON 12쌍 전체를 직접 비교하니 11쌍이 일치했다. `location_coordinates`의 기대 JSON은 단일 객체였고, CSV와 기대 JSON의 전화번호 값도 달랐다. 기대 객체를 단일 행으로 감싸도 전화번호·좌표 필드가 일치하지 않았다. 시작점에서도 같은 두 필드가 달랐다. 이 표본을 고치거나 통과로 집계하지 않았다. 줄바꿈 회귀 검사 6/6과 전체 표본 일치 11/12는 서로 다른 결과다.

### SpecStory가 읽은 범위

공식 EXE로 세션 ID를 지정해 `sync codex`를 실행했다. 같은 입력에서 다시 내보내도 각 폴더에 Markdown이 한 개였고, 결과 본문의 SHA-256도 첫 실행과 같았다. 아래 사용자·에이전트 수는 Markdown 표제 개수다.

| 입력 | 내보낸 내용 | 추가 확인 |
| --- | --- | --- |
| 제작자 테스트를 옮긴 입력 6개 이벤트 | Markdown 507바이트, 사용자 표제 1개 | 예상 발화 3개가 모두 있었고, 두 이벤트로 표현된 같은 명령은 1회만 렌더링됐다. |
| 이번 Windows CLI 개발 세션 80개 이벤트 | 24,471바이트, 사용자 표제 1개, 도구 블록 10개 | 실제 요청, 실패 2건과 수정 후 통과 출력, 두 커밋의 단축 해시가 남았다. |
| 이전 Windows 데스크톱 앱 시험 세션 102개 이벤트 | 4,396바이트, 에이전트 표제 14개, 도구 블록 5개 | 당시 `Stop` 훅의 마지막 응답과 일치했다. 사용자 표제는 0개였다. |

데스크톱 자료는 같은 PC에서 이전에 만든 합성 시험 세션의 실제 JSONL이었다. 당시 요청은 앱에 연결된 도구를 통해 전달됐다. 원본의 사용자 역할 메시지는 환경 정보 한 건이었고, 일반 사용자 요청 이벤트는 관측되지 않았다. 이를 SpecStory가 사용자 발화를 버렸다는 근거로 삼을 수 없다. 앱 입력창에 직접 타이핑한 새 대화와 실행 중 실시간 `watch`는 후속 시험 범위다. [기존 앱 표본의 관측 조건](https://github.com/NotoriEarth/TimeSchedule/blob/a333456b59cfc3eb012f31cbc20df2ebf049892a/docs/project-capture-support.md)

### 같은 발췌로 두 가지 요약 비교

새 읽기 전용 Codex 세션 두 개에 똑같은 3,754바이트 발췌와 수정하지 않은 공식 스킬을 제공했다. 발췌에는 사용자 요청, 개발자 역할을 맡은 에이전트의 설명, 테스트 이름과 결과 행, 마지막 응답이 들어 있었다. 전체 도구 입력, 경로 목록과 코드 본문은 뺐다. 두 세션 모두 스킬과 발췌를 실제로 읽은 것이 도구 결과에 남았다. 별도 시험 담당자가 실행한 12쌍 비교 결과는 제공하지 않았다.

| 질문 방식 | 맞게 복원한 내용 | 빠뜨리거나 잘못 쓴 내용 |
| --- | --- | --- |
| 공식 스킬 형식으로 최근 세션 한 건 요약 | LF·CRLF 재현, 레코드 단위 스캔을 선택한 이유, 최종 6개 통과, 두 커밋 | 수정 전 실패 개수를 생략했다. 발췌에 없는 변경 파일명은 추측하지 않았다. |
| 같은 스킬에 실패 과정·전후 수치·미검증 범위를 요청 | 수정 전 4개 통과·2개 실패, 수정 후 6개 통과·0개 실패, 줄바꿈 보존 이유 | 두 회귀 예제 외에는 검증 결과가 없다고 썼다. 같은 발췌에 `simple`, `simple_crlf`, `comma_in_quotes`, `escaped_quotes`의 통과 행이 있었다. |

공식 스킬에 적힌 사용자 표제 검색식은 이번 Markdown과 일치한 줄이 0개였다. 스킬은 `_**User**_`를 찾고 SpecStory 2.17.0의 Markdown v2.1.0은 `_**User (시각)**_` 형태를 썼다. 이번 세션은 앞뒤 문맥을 읽어 복원했다. 긴 세션 중간에 여러 요청이 있는 경우에도 같은 결과가 나올지는 확인이 필요하다.

## 2. 두 커밋을 일지 한 건으로 저장

작업 A에 고정 UUID 하나를 부여하고 `gitChanges`에 `148556e..703b07f`와 `tests/csv.test.mjs`, `src/csv.mjs`를 전달했다. 일지 본문은 개발 세션의 확인 문단과 시험 담당자가 독립 재현한 수치로 구성했다. 요약 모델이 잘못 쓴 검증 한계는 이 본문에서 제외했다.

시험용 `prepare`와 `sync` 후 `local_complete`를 확인했다. `record.md`가 전달 본문과 바이트 단위로 같았고, 별도로 연 SQLite의 `diary_entries` 행에는 같은 본문이 있었다. `project_record_receipts`와 조인해 작업 ID에 대응하는 항목도 확인했다. 같은 입력을 다시 보내니 문서 1개, DB 항목 1개였고 항목 ID, 본문 해시, 문서 수정 버전이 유지됐다.

## 3. 빠진 기록을 다음 세션에서 찾아 복구

작업 A 다음에 README만 수정한 대조 커밋 `ba83886`을 만들었다. 이어서 공개 `quotes_and_newlines` 예제를 회귀 검사에 추가한 개발 커밋 `95bc143`을 만들고 7개 통과를 확인했다. 이 두 번째 개발 작업 B의 기록 전달을 의도적으로 생략했다.

시험용 검사기는 등록한 시작점 이후 선형 브랜치에서 개발 커밋 후보를 찾고, 저장된 `metadata.json`의 저장소·커밋 범위·선택 경로로 이미 기록한 변경을 확인했다. 빠뜨릴 커밋을 적어 둔 시험 정답은 검사기에 입력하지 않았다.

| 시점 | 대상 개발 커밋 / 기록에서 찾은 커밋 | 누락 | 원문 문서 / DB 항목 |
| --- | --- | --- | --- |
| 작업 A 저장·재전달 | 2 / 2 | 0건 | 1 / 1 |
| 문서 커밋과 작업 B 커밋 후 | 3 / 2 | B만 1건 | 1 / 1 |
| B 보완 후 | 3 / 3 | 0건 | 2 / 2 |
| B에 같은 작업 ID로 재전달 후 | 3 / 3 | 0건 | 2 / 2 |

두 가지 시작 방식을 복구 전후에 실제로 실행했다.

- **Codex 프로젝트 지침**에는 새 작업을 시작할 때 시험 검사기를 실행하도록 했다. 복구 전후 각각 독립된 세션에 같은 질문인 “이 프로젝트의 기존 테스트가 어떤 CSV 입력을 다루는지 짧게 알려주세요. 파일은 수정하지 마세요.”를 전달했다. 두 세션 모두 검사기를 호출했다. 복구 전에는 `95bc143`만 지목했다. 복구 후에는 해당 경고가 사라졌고, 응답에는 누락 항목이 없다는 안내가 한 줄 남았다.
- **Claude Code의 실제 `SessionStart` 훅**은 시험 실행에만 `--settings`로 연결했다. 검사 결과에 누락이 있을 때만 시작 문맥에 제목과 짧은 SHA를 넣었다. 같은 인사 요청에서 복구 전에는 `95bc143`이 사용자 응답에 나왔고, 복구 후에는 일반 인사만 나왔다. 훅 내부 검사 시간은 두 호출에서 각각 1,665ms와 1,680ms였다. 이 두 값은 이 작은 저장소에서의 관측이다.

## 실패한 시도와 바꾼 방법

| 시도 | 관측 | 바꾼 방법과 확인 결과 |
| --- | --- | --- |
| 공개 CSV 저장소에서 커밋 고정 ZIP 다운로드 | 해당 URL이 HTTP 404를 반환했다. | 공식 npm 배포 파일의 `gitHead`가 같은 커밋임을 확인하고 SHA-512 일치 후 입력·정답을 추출했다. |
| 앱 번들 Codex에 자동 승인 검토와 샌드박스 모드를 동시에 명시 | 두 옵션이 충돌해 종료 코드 2로 세션 시작 전 종료됐다. | 작업 폴더 쓰기 모드를 포함한 자동 검토 옵션을 단독 사용해 개발 세션과 두 커밋을 얻었다. |
| 개발 세션이 일반적인 Node 프로젝트처럼 `package.json`과 Git 상태 조회 | 패키지 파일이 없었고 Windows의 Git 소유권 검사도 걸렸다. | 실제 `node --test` 진입점을 사용하고 해당 시험 경로에만 명령 단위 Git 예외를 지정했다. |
| 새 요약 세션에 읽기 전용과 승인 요청 금지를 함께 지정 | 두 모델 호출은 종료 코드 0이었지만 파일 읽기 명령이 정책에 거절돼 요약이 생기지 않았다. | 읽기 전용을 유지하고 읽기 요청을 자동 검토하도록 바꿨다. 스킬·발췌 읽기 결과와 실제 요약 본문을 확인했다. |

## 결과를 다시 확인하는 방법

실험한 PC의 TimeSchedule 작업 폴더에서 아래 명령을 실행하면 보존된 시험 저장소와 SQLite DB를 다시 검사한다. `RESULTS.json`은 검증기가 만드는 원문 없는 집계이고, `evidence/`에는 커밋별 재실행 결과와 최초 실패를 포함한 로컬 자료가 있다. 이 폴더는 원격 Git에서 제외했다.

```powershell
Set-Location -LiteralPath 'artifacts/record-lab/2026-11-18-specstory'
node tools/verify-results.mjs
node tools/diary-pilot.mjs audit
git -C project log -5 --oneline
```

세 커밋의 CSV 테스트를 다시 돌리려면 같은 폴더에서 `node tools/replay.mjs`를 실행한다. 커밋의 파일을 시험 폴더에 각각 복원하므로 현재 작업 브랜치를 전환할 필요가 없다. 초기 전달과 복구 단계는 이미 끝난 시험 상태를 보호하기 위해 별도로 구분했다.

**도입 판단.** CLI 작업에서는 SpecStory를 누락 복원 자료로 쓰고, 커밋·테스트 출력으로 확인한 사실을 작업별 일지에 넣는 구성을 실제 프로젝트 한 곳에서 시범 운영할 근거가 생겼다. 모델이 생성한 미검증 범위 역시 테스트 이름과 대조해야 한다. 다음 실사용 표본은 Windows 앱 입력창에서 직접 시작한 작업, 여러 세션에 걸친 작업, 다른 작업자가 섞인 브랜치다. 이 실험에서 확인한 누락은 의도적으로 만든 한 건이며, 여러 주에 걸친 자연 누락률이나 매번 요약 스킬이 자발적으로 실행될 확률은 측정하지 않았다.
