# TimeSchedule 방향

기준일: 2026-11-23 · 기준 시간대: Asia/Seoul

이 문서는 사용자가 2026-11-23 대화에서 말한 목표를 한 곳에 적은 것이다. 구현 계획이나 완료 보고가 아니다. "정한 것"은 사용자가 직접 말한 내용이다. "출발값으로 정한 것"은 작성자가 제안한 값을 사용자가 같은 날 받아들인 것이며, 실제로 써 본 뒤 바꿀 수 있다. 사용 흐름과 "정한 것"은 대화를 옮겨 적은 것이라 틀린 곳이 있으면 고친다.

이전 요구사항 문서 둘과 실제 구현이 서로 다른 방향을 가리키고 있어서 기준을 다시 적는다. 방향 판단은 이 문서를 따른다. 이전 문서는 맨 아래 "이전 문서"에 정리했다.

## 만들려는 것

개발하는 동안 쌓이는 AI 채팅 원문을 프로젝트별로 모으고, 그것을 날마다 개발 기록으로 정리해 두었다가, 프로젝트가 끝나면 포트폴리오용 프로젝트 기록으로 한 번 종합한다. 나중에 AI와 함께 실제 포트폴리오를 만들 때 AI가 이 기록과 원문을 찾아 구체적인 내용을 가져올 수 있어야 한다.

일정, 다이어리, 바탕화면 위젯은 지금처럼 함께 쓴다.

## 사용 흐름

1. **프로젝트 등록.** GitHub에 저장소를 만들고 그 링크로 프로젝트를 시작한다.
2. **원문 수집.** Codex와 Claude Code로 개발하면 CLI에서 하든 앱에서 하든 채팅 원문이 그 프로젝트에 모인다. 개발 흐름을 끊지 않는다.
3. **하루 정리.** 에이전트가 그날의 원문을 읽고 하루 기록과 하루 요약을 만든다.
4. **완료 시 종합.** 프로젝트가 끝나면 상위 모델이 프로젝트 전체를 포트폴리오용 프로젝트 기록으로 한 번 정리한다.
5. **나중에 조회.** 실제 포트폴리오를 만들 때 AI가 CLI로 기록과 원문을 찾아, 기억나지 않는 부분의 구체적인 내용을 가져온다.
6. **수정할 때 참고.** 나중에 고칠 일이 생기면 그 당시의 기록과 원문을 보고 고친다.

## MVP 뒤: 학습 영역과 학습

프로젝트에서 한 일을 아래 16개 영역으로 나눠 면접에서 깊이 있게 다룰 수 있게 정리한다. 프로젝트를 하면서 그 내용을 top-down으로 학습한다.

요구사항·도메인 설계, 시스템 아키텍처, 프로그래밍 기초·코드 품질, 데이터베이스, 백엔드·API, 동시성·비동기 처리, 테스트·품질 보증, 디버깅·문제 해결, 보안·개인정보 보호, 운영체제·네트워크, 인프라·배포·CI/CD, 모니터링·장애 복구, 성능·확장성, 프론트엔드·UX, 협업·문서화·형상 관리, AI 에이전트·하네스.

- 영역 분류는 하루 기록에 붙이는 꼬리표다. 원문과 하루 기록이 남아 있으면 나중에 전체를 다시 읽혀 붙일 수 있다. 그래서 MVP에 넣지 않는다.
- 학습은 하루 기록의 결정이나 문제 하나를 골라 실제 코드로 설명을 듣고, 본인 말로 적어 그 기록에 붙이는 방식으로 한다. 설명은 기존 pstack `teach`로 할 수 있다. 본인 설명을 받고 저장하는 단계는 새 스킬이 필요하다.
- 각 항목에 "본인이 설명할 수 있음" 여부를 표시한다.

## 지키는 원칙

- 이유가 원문에 없으면 "이유 기록 없음"으로 둔다. 모델이 추측으로 채우지 않는다.
- 근거가 없는 학습 영역은 비워 둔다. 수치가 없으면 개선량을 만들지 않는다.
- 사용자가 고친 글은 자동 갱신이 덮어쓰지 않는다.
- 새 화면, 메뉴, 입력 요소는 위치와 이름과 용도를 먼저 확인받고 만든다.
- 모델을 호출하는 기능은 첫 호출부터 사용량을 기록한다.
- 승인 없이 유료 API로 바꾸지 않는다.

## 현재 구현과의 차이

2026-11-23에 코드와 실제 DB 건수로 확인한 상태다. DB는 건수만 셌고 내용은 읽지 않았다.

| 흐름 | 현재 | 차이 |
| --- | --- | --- |
| 프로젝트 등록 | 이름, 설명, 로컬 저장소 경로 하나 | GitHub 링크와 완료 상태가 없다 |
| 원문 수집 | 0.33.0부터 세션 파일 전체를 문서 저장소에 압축해 보관한다([채팅 원문 보관](chat-originals.md)). 다이어리에는 세션마다 앞 40KB와 뒤 48KB 발췌를 넣는다 | 발췌는 Claude Code 중 CLI 세션만 읽는다. 하루 정리(0.34.0)는 보관본을 읽으므로 데스크톱 앱 세션도 들어간다. 발췌 메모는 포트폴리오가 쓰고 있어 순서 4번까지 그대로 둔다 |
| 하루 정리 | 0.34.0부터 `record daily`가 하루 대화록으로 모델을 한 번 불러 하루 기록(개발 내역, 트러블슈팅, 개선 방향, 결정)을 만들고, 앱이 다이어리에 보여 준다([하루 정리](daily-record.md)). 결정은 제안·확정의 근거를 원문 글귀로 확인한다. 에이전트 개발 기록과 세션별 경험 검토는 그대로 있다 | 명령으로만 실행한다. 자동 실행과 화면 버튼은 비용과 품질을 본 뒤 정한다 |
| 하루 요약 | 하루 기록의 요약 문장(근거 블록 포함)으로 만든다 | 따로 짧은 요약 화면은 없다 |
| 완료 시 종합 | 확인한 경험으로 Markdown 포트폴리오를 만든다 | 완료 시점과 모델 선택이 없다 |
| 조회 | `record` 명령은 넣기, 상태 확인, 수집 실행만 한다 | 읽기와 검색이 없다 |
| 모델 | 기본 `gpt-6.1-terra`를 Codex CLI로 호출한다. 하루 정리는 `--model`로 바꿀 수 있고, 호출마다 Codex가 보고한 토큰 수를 `usage.jsonl`에 남긴다 | 채팅 경험 검토와 포트폴리오 작성은 모델이 고정이고 사용량을 남기지 않는다 |

수집되지 않는 것: 코드 작업이 아닌 일반 채팅(claude.ai, ChatGPT 대화)은 로컬에 파일이 없다.

## 순서

1. **원문 보존.** 0.33.0에서 했다. 수집할 때 세션 파일을 문서 저장소의 `originals`에 압축해 보관한다([채팅 원문 보관](chat-originals.md)). 이 문서의 이전 판은 Codex 세션 파일이 11월 16일부터만 남아 있다고 적었는데 틀렸다. Codex는 그 이전 파일을 `.jsonl.zst`로 압축해 두었고 6월 파일까지 남아 있다.
2. **하루 정리와 하루 요약.** 0.34.0에서 했다([하루 정리](daily-record.md)). 결정 항목을 처음부터 포함하고, 에이전트가 결정을 내릴 때 `결정:` 형식으로 채팅에 적도록 작업 지침에 규칙을 두었다. 2026-11-24에 실제 하루(11월 20일)로 두 번 만들어 보았다. 한 번에 입력 약 3만 토큰, 45초 안팎이었다.
3. **읽기용 CLI.** 프로젝트와 날짜로 기록 목록, 본문, 검색 결과, 원문 위치를 돌려준다.
4. **프로젝트 링크와 완료 상태, 완료 시 종합.**
5. **모델 선택과 사용량 기록.**
6. **UI와 설정 메뉴 정리.**
7. **MVP 뒤: 학습 영역 분류와 학습 스킬.**

이 순서와 별개로 먼저 정리할 것:

| 대상 | 처리 | 이유 |
| --- | --- | --- |
| Space 게시 | 없앤다 | 사용자 결정. 꺼져 있고, 기록 41건 중 7건만 Space까지 갔다. 전달 상태의 대부분이 여기서 나온다 |
| Git 커밋 가져오기 | 0.33.1에서 네이티브 앱의 버튼과 처리 코드를 없앴다. 코어의 함수는 예전 Tauri 앱이 써서 남겼다(2026-11-24 사용자 결정) | 실제 데이터 0건 |
| 규칙 기반 경험 추출기 | 순서 2번(하루 정리)에서 채팅 검토 경로를 다시 짤 때 함께 없앤다(2026-11-24 사용자 결정) | 앱은 호출하지 않는다. 다만 테스트 5개가 이 추출기로 시험용 후보를 만들어 저장·내보내기 동작을 검사하고 있어, 없애려면 그 테스트를 다시 써야 한다 |

| 일정, 위젯, 검색, 앱 수신함, MCP | 손대지 않는다 | 쓰고 있거나 쓸 계획이다 |

## 출발값으로 정한 것

작성자가 제안한 값을 사용자가 2026-11-23에 받아들였다. 확정이 아니라 출발값이다. "다시 볼 때"에 적은 시점에 실제 결과를 보고 바꿀 수 있다.

| 질문 | 정한 출발값 | 다시 볼 때 |
| --- | --- | --- |
| 프로젝트 문서를 개발 중에도 계속 갱신하는가, 완료 때 한 번 종합하는가 | 개발 중에는 하루 기록과 하루 요약만 쌓고 완료 때 한 번 종합한다. 원하면 중간에도 요청해서 종합할 수 있게 한다 | 하루 기록만으로 프로젝트 상태를 파악하기 어렵다고 느낄 때. v0.2는 계속 갱신으로 정했었다 |
| 하루 정리를 언제 실행하는가 | 처음에는 버튼이나 명령으로 실행한다 | 비용과 품질을 본 뒤 자동 실행을 정한다 |
| 기존 에이전트 개발 기록 경로를 하루 정리로 바꾸는가 | 하루 정리가 돌 때까지 유지하고 그 뒤에 정한다 | 하루 정리가 실제로 돌기 시작한 뒤 |
| GitHub 링크와 로컬 경로를 어떻게 잇는가 | 링크는 프로젝트의 이름표로 저장하고, 수집은 지금처럼 로컬 경로로 맞춘다. 수집은 세션 파일에 적힌 로컬 작업 경로로 프로젝트를 찾는다 | 링크에서 다른 동작이 필요해질 때 |
| 원문을 얼마나, 얼마 동안 보관하는가 | 등록한 프로젝트의 세션만 압축해 보관한다. 기간은 정하지 않고 지우지 않는다 | 용량을 본 뒤 기간을 정한다. 2026-11-24에 TimeSchedule의 세션 파일은 3주치 445개, 351MB였고 보관본은 127MB였다 |
| API를 쓰는가, 어떤 모델을 쓰는가 | CLI로 시작한다 | 실제 비용을 본 뒤 API와 모델을 정한다 |

v0.2와 달라진 점은 둘이다. v0.2는 프로젝트 문서 하나를 개발 중에 계속 보완하는 것을 중심에 두었고, 이 문서는 하루 기록을 쌓다가 완료 때 종합하는 흐름을 적었다. 사용자는 완료 때 종합하는 쪽을 출발값으로 정했다. 그리고 v0.2에 없던 학습 영역 정리와 학습이 추가되었다.

11월 19일과 20일에 만든 0.21부터 0.31까지의 기능(채팅 경험 검토와 포트폴리오 생성)은 두 문서의 순서와 다르게 완료 시 종합에 해당하는 부분을 먼저 만든 것이다. 이 문서의 4번에서 다시 쓴다.
