# Claude 구현·Codex Astra 검토·Rust 학습 운영 지침

작성일: 2026-11-17. 연결 문서: [구현·검증 계획](superpowers/plans/2026-11-17-project-document-implementation.md), [요구사항](TimeSchedule_Product_Requirements_v0.2_2026-11-17.md).

상태: 운영 절차와 설정 설계. 이번 변경은 문서이며 Claude 설정 변경, Superpowers 설치, 승인 제어 프로그램/훅 구현, 제품 구현을 수행하지 않는다. 아래 추천 배분과 학습 시간은 실측 결과가 아니다.

## 1. 역할과 단계 배분

모델은 추론 담당이고, Claude Code/Codex는 파일·명령·권한·대화를 관리하는 실행 환경(하네스)이다. Superpowers는 그 환경에서 따르는 작업 절차다. 스킬 이름만 지정해도 특정 모델이나 권한 경계가 자동으로 설정되는 것은 아니다.

Claude Fable 5.2 high를 설계·모호한 문제·데이터 무결성 작업의 첫 후보로, Opus를 계약이 명확한 구현의 첫 후보로 추천한다. 이는 이 저장소에서 검증한 성능 순위가 아니다. 공식 문서는 Fable을 Claude Code의 가장 강력한 계열로 소개하므로 “Opus가 항상 상위 모델”이라는 전제도 두지 않는다. 실제 수정량·실패·지연·사용량으로 배분을 교정한다. [공식 모델 설정](https://code.claude.com/docs/en/model-config)

| 실행 단위 | 첫 담당 추천 | 산출물·사용자 확인 | Rust 학습 주제 |
| --- | --- | --- | --- |

각 단위의 독립 검토는 **Codex Astra**가 맡는다. 설계와 구현을 둘이 나눌 때는 설계 계약을 먼저 고정한다. 구현 모델이 바뀔 때 작업 요약·현재 SHA·허용 범위를 넘긴다. UI 작업이라도 원인 불명 회귀가 생기면 Fable의 진단 범위를 별도 명시한다. 두 모델을 항상 중복 실행하지 않는다.

개발에 사용하는 모델과 제품의 문서 생성 모델은 별개다. 이 배분은 제품의 최종 생성 모델을 확정하지 않는다. Fable/Opus/CLI 사용이 구독에 무조건 포함되거나 무료라고 간주하지 않는다.

## 2. 멈추는 단위와 승인

전체 M1은 크므로 계획의 작업 2·3·4를 별도 하위 계획으로 만든다. 각 계획은 구현 범위, 허용 경로, 필요한 테스트, 완료 산출물, 금지한 다음 단계, 실제 모델, 실행/재시도 상한을 명시한다. 큰 작업은 독립적으로 시험 가능한 결과 기준으로 더 나눈다.

1. **설계 확인:** Claude가 읽기 중심으로 현재 상태와 이번 범위를 제시한다. 사용자가 해당 범위 구현을 승인하기 전 제품 파일을 수정하지 않는다.
2. **승인 범위 구현:** 필요한 테스트·수정·커밋·푸시·PR 준비까지 진행한다. 기존 AGENTS.md의 승인된 Git 절차를 매 명령마다 재확인하지 않는다. 다음 범위를 미리 구현하지 않는다.
3. **검토 고정:** BASE/HEAD SHA와 변경 경로를 고정해 Astra에 읽기 전용 검토를 맡긴다. 검토 중 같은 대상을 수정하지 않는다. 테스트 실행이 필요하면 격리된 검증 경로와 권한을 명시한다.
4. **지적 처리:** 범위 안 수정까지 사전 승인받은 실행이면 그 범위에서 수정·필요한 테스트·새 SHA 재검토를 수행한다. 범위 확대·새 의사결정은 사용자에게 제시하고 멈춘다. 반복 횟수/비용 상한을 넘으면 결과를 보고한다. 별도 검토 전용 명령은 기본적으로 결과 보고에서 종료한다.
5. **사용자 확인:** 확인한 동작·미확인 동작·Astra 결과·수정 후 SHA·실행 파일(앱 변경 시)·시험 방법·짧은 개념 설명을 전달한다. 제품 동작이 없는 M0는 지원표와 설계 결과로 확인한다.
6. **다음 범위:** 사용자가 다음 작업을 명시적으로 승인한 뒤 시작한다. Astra 통과, 테스트 통과, 체크박스 완료는 사용자 승인이나 머지 승인이 아니다.

예: “작업 2의 연결/스키마 구현과 그 범위의 검토 수정까지 진행. 작업 3 수집은 시작하지 말 것.” 다음 승인은 “작업 2 결과 확인. 작업 3 시험 프로젝트 수집·저장 구현 승인.”처럼 대상을 분명히 한다. 이후 수정이 있으면 새 변경에 대한 사용자 테스트·머지 승인을 다시 받는다.

## 3. Superpowers에서 브레이크를 거는 방법

현재 Codex에 설치된 Superpowers 7.0.1의 `executing-plans`와 `subagent-driven-development`에는 **“Do not pause to check in with your human partner between tasks”**라는 연속 실행 규칙이 있다. 따라서 전체 계획을 실행 입력으로 넘기고 “중간에 알아서 물어봐”라고만 하면 사용자 의도와 충돌한다. 직접 지정한 사용자 승인 경계를 우선하며, 실행 대상 자체를 승인된 하위 계획 하나로 제한한다.

확인한 로컬 출처:

- `C:/Users/ycg03/.codex/plugins/cache/openai-curated-remote/superpowers/7.0.1/skills/executing-plans/SKILL.md`
- `C:/Users/ycg03/.codex/plugins/cache/openai-curated-remote/superpowers/7.0.1/skills/subagent-driven-development/SKILL.md`
- 같은 경로의 `using-superpowers/SKILL.md`: 명시적 사용자 지시가 스킬보다 우선한다.

권장 스킬 적용은 다음과 같다.

| 시점 | 스킬 | 적용 경계 |
| --- | --- | --- |
| 새로운 설계 쟁점 | brainstorming | 확정 요구를 다시 묻지 않고 남은 쟁점만 설명 |

## 4. 실제 도구 실행을 막는 장치

추천 시작점은 **계획 모드 + 한 번에 한 하위 계획 + 결과 보고 후 종료**다. 실수로 구현을 시작하는 문제가 반복되면 아래 제어기를 별도 작업으로 구현·검증한다. 문서 규칙을 설정했다고 “우회 불가능”이라고 표시하지 않는다.

- 계획/검토 세션은 `plan` 또는 읽기 전용 권한으로 실행한다. 계획 모드의 계획 파일 등 예외와 실제 권한을 확인하고, 임의 명령 실행을 포괄 허용하지 않는다. [Claude 권한 문서](https://code.claude.com/docs/en/permissions)
- 구현 세션은 승인한 작업 트리·경로·도구만 허용한다. 승인 제어기는 `locked → authorized → submitted → locked` 전환을 관리하고 사용자 승인만 다음 실행을 연다. 승인에는 단계 ID, 세션/작업 트리, 시작 SHA, 허용 경로·동작, 실행/시간 상한을 연결한다.
- `PreToolUse`는 도구 실행 직전에 잠금 상태와 허용 범위를 검사해 `permissionDecision: deny`를 반환할 수 있다. 단, Edit/Write만 막으면 Bash/PowerShell/Node, MCP, 하위 에이전트 경유 변경이 남는다. 잠긴 동안은 확인된 읽기 동작만 허용하고 알 수 없는 도구를 거절한다. 명령 문자열 정규식 몇 개로 임의 쉘의 안전성을 보장하지 않는다.
- 승인 상태·훅 코드·설정을 구현 에이전트가 수정할 수 있으면 스스로 잠금을 풀 수 있다. 실제 강제력이 필요하면 보호된 설정/외부 제어기와 OS 권한·격리를 함께 사용한다. 사용자와 같은 권한으로 무제한 쉘을 제공하는 구성은 강한 경계가 아니다.
- 훅 오류·누락·시간 초과에서도 허용되지 않도록 설치 버전의 동작과 제어기를 시험한다. 시작 시 훅이 로드됐는지 확인하고, 단계 종료 시 실행 프로세스와 남은 하위/백그라운드 작업을 정리·확인한다. 새 도구 호출 차단만으로 이미 시작된 프로세스가 멈추지는 않는다.
- `Stop` 훅의 `decision: block`은 **Claude의 종료를 막아 계속 작업하게 하는 동작**이다. 사용자 승인 대기 브레이크로 쓰지 않는다. [공식 훅 문서](https://code.claude.com/docs/en/hooks)

실제 제어기 인수 시험: 승인 전 수정 거절, 정상 승인 범위만 허용, 다음 단계 거절, 쉘·MCP·자식 작업 우회 거절, 승인 파일 변조 거절, 훅 실패 시 차단, 재시작 후 잠금 유지, 만료 승인 거절, 기존 백그라운드 작업 잔존 확인. 이 시험을 통과하기 전에는 “강제 브레이크 설치 완료”라고 보고하지 않는다.

## 5. Claude → Codex Astra 전달

현재 Claude의 Codex 플러그인 1.0.6은 연결 경로가 있다는 근거이며 Astra 실행 성공의 근거는 아니다. 확인한 `task` 경로는 `--model`을 지원한다. 리뷰 명령의 기본 모델이 Astra라고 추정하거나, 지원하지 않는 옵션을 임의로 붙이지 않는다. 초기 연동 점검에서 실제 모델 선택과 결과의 모델 식별을 확인한다. 자동 연동이 불가능하면 같은 전달 문서를 Codex 앱의 Astra 선택 채팅에 넣는다. 임의 모델 대체·유료 API 전환은 하지 않는다.

각 하위 계획의 인계 자료에는 다음을 넣는다.

- 단계 ID와 승인 범위, 요구사항/하위 계획의 경로.
- 저장소·브랜치·BASE/HEAD 전체 SHA·이번 변경 경로. 사용자 기존 미커밋 변경은 제외.
- 무엇이 달라졌고 왜 필요한지, 설계 선택·대안·남은 한계.
- 테스트 명령·종료 결과·증거 위치·미검증 동작, EXE가 있으면 해당 빌드의 SHA.
- 실제 구현/검토 모델·설정·실행 ID, 관측된 사용량과 확인 불가 항목.

원본 대화 전체·인증정보·개인 기록을 전송하지 않는다. 검토에 필요한 코드와 허용된 근거만 전달한다.

```text
Codex Astra로 다음 변경을 읽기 전용 검토하라.
대상: [저장소], BASE=[전체 SHA], HEAD=[전체 SHA], 범위=[경로].
요구사항=[경로], 승인 하위 계획=[경로], 인계 자료=[경로].
실제 모델 식별자를 확인하고 Astra가 아니거나 대상 SHA가 달라지면 알리고 중단하라.
요구 누락, 근거 보존, 중복/재시작, 사용자 편집 충돌, CLI/API 전환,
전송 범위, 비용 관측, Rust 오류·동시성·저장 경계를 중심으로 검토하라.
지적마다 심각도, 파일/줄, 발생 조건, 사용자 영향, 확인 방법을 적어라.
사실과 추정·미검증을 구분하라. 코드 수정, 다음 단계 실행, 머지는 하지 마라.
지적이 없더라도 확인하지 못한 범위를 남겨라.
```

검토 결과를 Claude가 전달할 때 원문과 별도의 한국어 설명을 함께 보관한다. 쉬운 말로 정리하면서 심각도·조건·불확실성을 지우지 않는다. Claude가 수정한 뒤에는 새 HEAD를 다시 검토한다. 이전 검토 통과를 새 코드에 재사용하지 않는다.

## 6. Rust를 배우는 범위

목표는 “이 앱의 데이터가 어디로 이동하고, 어디서 실패하며, 왜 이 Rust 코드가 필요한지 설명할 수 있음”이다. 언어 전체를 먼저 익히거나 AI가 만든 코드를 모두 직접 다시 작성할 필요는 없다. 소유권·참조·오류 전파·동시성은 반복해서 접해야 하며 익숙해지는 시간은 기존 프로그래밍 경험에 따라 다르다. 단계마다 15~30분은 제안하는 학습 시간 배분이지 숙련 기간 보장이 아니다.

설명은 사용자 동작 → 실행 흐름 → 실제 코드 한 함수 → 새 개념 1~3개 → 실패 예 → 확인 질문 순으로 만든다. 문법부터 길게 설명하지 않는다. UI/저장/모델 호출의 전체 그림을 먼저 이해하고 해당 코드가 들어가는 위치를 표시한다. Rust 메모리 안전성과 디스크 영속성은 별개다. [Rust 공식 소유권 설명](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)

현재 코드 예시: `crates/timeschedule-core/src/storage.rs`의 `Storage::connection`은 다음과 같다. 이 예시는 새 기능이 아니라 현재 구현을 설명한다.

```rust
pub(crate) fn connection(&self) -> Result<MutexGuard<'_, Connection>, String> {
    self.connection
        .lock()
        .map_err(|_| "Database access was interrupted. Please restart the application.".into())
}
```

- `&self`: Storage 자체를 넘겨 없애지 않고 잠시 참조한다.
- `Mutex`: 이 연결을 사용하는 코드들이 동시에 접근하지 않도록 잠근다. 경쟁 시 기다릴 수 있으므로 UI 응답성까지 자동 보장하지 않는다.
- `MutexGuard`: 잠금을 보유하는 값이다. 정상적으로 범위를 벗어나 해제될 때 잠금도 풀린다. `'_`는 이 가드가 빌린 데이터보다 오래 살아서는 안 된다는 수명 관계를 표현한다.
- `Result<성공, 실패>`: 연결 잠금에 성공하면 가드, 실패하면 오류 문자열을 돌려준다. `map_err`는 실패 내용을 앱의 오류 표현으로 바꾼다.
- 호출부의 `let connection = self.connection()?;`에서 `?`는 성공값을 꺼내고 실패 시 현재 함수에서 오류를 반환한다. 자동 재시도가 아니다.

이 잠금이 파일 손상이나 저장 중 전원 차단까지 해결하지는 않는다. SQLite 트랜잭션·파일 저장 절차·백업 복구는 별도로 검증해야 한다. 확인 질문은 “가드를 보유한 채 오래 걸리는 외부 모델 호출을 하면 어떤 일이 생길까?”, “잠금 성공과 DB 저장 성공이 같은가?” 정도면 충분하다.

### Codex 개념 설명 요청문

```text
검토한 HEAD=[SHA]의 [단계]를 Rust 초보자에게 한국어로 설명하라.
먼저 사용자 동작과 앱 내부 흐름을 연결하고, 실제 파일/함수 위치를 표시하라.
이번 변경의 핵심 함수 하나를 필요한 부분만 인용해 새 개념 1~3개를 설명하라.
타입·소유권/참조·오류·동시성 중 실제로 등장하는 개념만 골라라.
설계 대안과 선택 이유, 정상/실패 예, 테스트가 증명한 것/못한 것을 구분하라.
메모리 안전성과 디스크 저장 보장을 혼동하지 마라.
5분 요약과 선택 심화 설명, 이해 확인 질문 2개, 작은 읽기 연습 1개를 작성하라.
코드를 수정하지 마라. 없는 구현을 있는 것처럼 설명하지 마라.
```

먼저 5분 요약으로 동작·위험을 이해하고 선택 심화 학습은 나중에 읽어도 된다. 학습을 모두 마쳐야 개발을 진행할 수 있도록 만들 필요는 없다. 사용자가 이해하지 못한 제품 동작/데이터 손실 위험은 다음 승인 전에 설명한다.
