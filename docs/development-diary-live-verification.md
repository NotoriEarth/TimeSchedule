# Windows Codex에서 TimeSchedule 개발 일지 한 건을 검증한 기록

2026-11-18에 실제 TimeSchedule 프로젝트에서 문서 저장소 CLI 버그를 고쳤다. 새 채팅은 버그 수정만 요청받고 저장소의 기록 스킬을 읽었다. 지정된 `Documents/TimeScheduleData`에 원문 하나, 네이티브 다이어리 DB에 항목 하나가 생겼다. 같은 작업을 두 번 더 처리한 뒤에도 원문과 항목은 각각 한 건이었다.

## 새 채팅에 보낸 요청

> 지금 작업 중인 `codex/verified-project-diary` 브랜치에서 작은 버그 하나를 이어서 고쳐줘. 문서 저장소 CLI에서 `status --id abc`처럼 그 명령이 받지 않는 옵션을 줘도 정상 종료돼서 입력 실수를 알아차리기 어려워. 각 명령에 맞지 않는 옵션은 저장소를 열기 전에 오류로 알려줘.

Windows Codex 앱의 프로젝트 연결 기능으로 별도 채팅을 열었다. 요청에는 작업 ID, 스킬 이름, 테스트 방법, 기록 지시가 없었다. 첫 적용과 이를 검증하는 작은 수정을 한 작업으로 잡았다. 시작 기준은 `ad679cd`, 연동 커밋은 `2da02c8`, CLI 수정 커밋은 `374f954`다. 새 채팅은 스킬을 읽은 뒤 `audit`과 `begin`을 실행해 같은 브랜치의 기존 ID를 받았다. 수정 전후에 `check`를 실행하고 커밋에 ID를 붙인 뒤 스스로 `finish`를 호출했다.

## 안 된 부분과 해결 과정

| 관찰한 증상 | 확인한 원인 | 변경과 검증 |
| --- | --- | --- |
| 기록 도구의 회귀 검사 5개 중 1개가 실패했다. 실행 결과에서 TAP 집계를 읽을 수 없었다. | Node의 테스트 프로세스가 하위 프로세스에 `NODE_TEST_CONTEXT`를 물려줘 독립적으로 실행해야 할 검사를 재귀 실행으로 판단했다. | 하위 테스트 실행 환경에서 해당 표지만 제거했다. 같은 검사 5개가 통과했고, 실패·건너뜀·TODO를 서로 구별하는 회귀 검사도 통과했다. |
| 수정 전 `status --id abc`가 상태 JSON과 종료 코드 0을 반환했다. 손상된 임시 설정에서는 옵션 오류보다 JSON 읽기 오류가 먼저 발생했다. | 공통 파서가 `--id`를 받은 뒤 여러 명령에서 이를 무시했다. | 다섯 명령의 허용 옵션을 한곳에 선언해 설정을 읽기 전에 검사했다. 같은 잘못된 호출은 명령과 옵션 이름을 표시하고 종료 코드 1을 반환했다. 다섯 명령의 정상 호출도 임시 저장소에서 확인했다. |
| 실제 다이어리의 시작 건수를 확인할 때 제한된 프로세스에서 SQLite가 파일을 열 수 없었다. | 같은 경로에서 사용자 권한으로 읽기 전용 연결을 열자 조회가 가능했다. | 네이티브 앱이 사용하는 기존 DB에 SQLite `mode=ro`와 `query_only`를 적용해 건수를 읽었다. 본문 비교는 이 작업 ID로 한정했다. |

## 일지에 적힌 테스트 결과를 독립적으로 대조한 방법

완료 커밋을 임시 폴더에 풀고 Node 24.16.0의 기본 테스트 실행기로 직접 확인했다. 수정 전 재현에서는 같은 회귀 테스트를 유지한 채 CLI 소스 한 파일을 직전 커밋 버전으로 바꿨다. 원문과 다이어리에는 명령, 검사 범위, 종료 코드, 실패한 검사 이름이 보관됐다.

| 실행 범위 | 기대한 결과 | 독립 실행과 일지 대조 |
| --- | --- | --- |
| 수정 전 CLI 회귀 검사 | 13개 중 12개 통과, 1개 실패, 종료 코드 1 | 일치 |
| 수정 후 같은 CLI 회귀 검사 | 13개 통과, 종료 코드 0 | 일치 |
| 완료 커밋에서 기록 도구와 CLI 검사 함께 실행 | 18개 통과, 종료 코드 0 | 일치 |
| 대표 앱 0.18.0을 지정해 프로젝트 Node 테스트 전체 실행 | 네이티브 수신 검사 포함 76개 통과, 건너뜀 0개 | 일치 |

네이티브 수신 검사에는 `TIMESCHEDULE_RECORD_TEST_EXE`로 기존 `artifacts/TimeSchedule.exe`를 지정했다. 이 설정 없이 실행한 새 채팅의 결과도 일지에 별도로 적혔다. 그때는 75개가 통과하고 선택적 네이티브 검사 1개가 건너뛰어졌다.

## 실제 수신과 중복 검증

| 같은 작업 ID의 상태 | 시작 전 | 새 채팅이 완료한 뒤 | 저장된 입력으로 retry | 같은 설명으로 finish 재실행 |
| --- | ---: | ---: | ---: | ---: |
| 문서 폴더의 원문·메타데이터 쌍 | 0 | 1 | 1 | 1 |
| 다이어리 항목 | 0 | 1 | 1 | 1 |
| 보관된 문서 수정본 | 0 | 1 | 1 | 1 |

1. 전체 문서와 다이어리 건수도 전후로 각각 1만큼 증가했다. 문서 카탈로그와 실제 `record.md` 파일 수를 각각 셌다. SQLite에서는 작업 수신표와 다이어리 항목을 연결한 뒤, 같은 출처 ID의 항목 수도 따로 확인했다.
2. 파일의 SHA-256이 메타데이터와 일치했고 원문 전체가 다이어리 본문에 들어 있었다. 대표 앱의 `record status`가 반환한 항목 ID도 SQLite에서 읽은 값과 일치했다. 수신 상태는 `local_complete`였다. 기존 Space 설정은 꺼짐이었고 전달 과정의 모델 호출은 0회였다.
3. `retry`와 `finish` 재실행은 둘 다 `unchanged: true`를 반환했다. 파일과 DB 본문의 SHA-256, 다이어리 항목 ID, 원문 수정본 수, 수신 버전이 모두 첫 수신 때와 같았다. 마지막 `audit`의 누락 목록은 비어 있었다.

앱에서 확인하려면 해당 날짜의 TimeSchedule 프로젝트에서 **문서 저장소 CLI의 잘못된 옵션 거부와 개발 일지 검증**을 열면 된다. 이번 확인에는 네이티브 수신 명령과 실제 DB를 사용했다. 화면을 직접 클릭하는 사용자 확인과 여러 주 동안의 기록 누락률은 이번 측정 범위 밖이다.
