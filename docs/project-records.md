# 작업 종료 로컬 기록과 선택적 Space 연결

Git에 실제 개발 변경이 있는 작업만 **개발 변경 확인 → 독립 로컬 문서 원문 저장 → 다이어리에 요약·상세 원문 반영** 순서로 처리한다. **Space는 기본 꺼짐**이고 로컬 저장만으로 완료된다. 선택 설정을 명시적으로 켠 경우에만 **Space 반영 → 같은 다이어리 항목에 검증된 링크 연결**을 추가한다. 외부 연결이나 앱 실행 파일에 문제가 있어도 먼저 저장된 원문 파일은 남는다. Space 내용은 PR 작성에 도움이 될 때 선택적으로 재사용하며 PR이 없어도 기록한다. 저장소 경로 확정과 일반 프로젝트·공부 자료의 수동 import는 [개인 문서 저장소](document-vault.md)를 참고한다.

자동 개발 기록 대상은 이 스크립트가 있는 저장소다. 다른 채팅·프로젝트를 자동 탐색하지 않는다. 로컬 문서 저장소에는 별도 import로 다른 프로젝트·공부 자료도 넣을 수 있다. Space를 켠 경우에만 [TimeSchedule 개발 포트폴리오](https://chatgpt.com/space/page_6ae1b18a44f08191ad2a86276972476c)를 대상으로 한다. 일반 import 자료는 게시하지 않는다.

## 언제 실행하는가

Codex는 `AGENTS.md`에 따라 해당 작업의 소스·테스트·빌드/설정 변경을 커밋한 뒤 기존 설명을 기록한다. 검색·견적 조사·탐색·비교·설명·계획 논의, 읽기/테스트만 한 작업, 문서만 작성한 작업은 기록 원문/요약/전달 JSON도 새로 만들지 않는다. 다른 작업의 변경이나 기존 사용자 변경을 근거로 가져오지 않는다. 별도 오전 9시 포트폴리오 자동화는 중지했다. 앱은 이미 준비된 대기 기록만 전달하며 새 내용을 작성하지 않는다.

작업 시작 전에 `git rev-parse HEAD`로 기준 커밋을 확보한다. 개발 완료·커밋 후 같은 명령으로 완료 커밋을 확보하고 `git diff --name-only <시작 커밋> <완료 커밋> --`에서 **이 작업에 속한 경로만** 고른다. 입력의 `gitChanges`에는 두 전체 커밋 SHA와 선택 경로를 넣는다. 저장소 전체의 현재 미커밋 변경을 자동 수집하지 않으므로 커밋 후 깨끗한 작업 트리에서도 기록할 수 있다.

`prepare`와 `sync`는 로컬 Git에서 커밋 존재·선후 관계·선택 경로의 실제 변경을 확인한다. `apps/`, `crates/`, `src/`, `src-tauri/`, `scripts/`, `tests/`, `vendor/`, `.github/workflows/` 및 알려진 루트 빌드/의존성 설정을 개발 경로로 인정한다. 그 안에서도 docs/doc/notes/note/research 경로와 Markdown·일반 텍스트 문서는 제외한다. 기록을 위한 문서 추가만으로 조건을 충족시키지 않는다.

근거 누락·문서만 변경·빈 범위·잘못된 커밋/경로이면 `prepare`는 `skipped: true`와 이유를 반환하며 전달 상태, 다이어리, Space를 만들지 않는다. 자동 재시도도 같은 검사를 적용하며, 과거 대기 기록의 근거가 없으면 `excluded`로 보존하고 멈춘다. 이미 완료되었거나 사용자 편집 충돌인 기록은 변경하지 않는다. 기존 조사 글은 자동 삭제하지 않는다.

**Git이 답하지 못한 것과 근거가 없는 것을 구분한다.** 제외 사유는 Git이 확정한 답일 때만 쓴다: 커밋이 없음(`commit_not_found`: `git cat-file -e`가 아무 출력 없이 종료 코드 1), 시작 커밋이 완료 커밋의 조상이 아님(`not_ancestor`: `git merge-base --is-ancestor`가 아무 출력 없이 종료 코드 1), 커밋이 아닌 객체(`invalid_git_changes`), 다른 저장소(`wrong_repository`), 선택 경로가 실제로 바뀌지 않음(`unchanged_selected_paths`). 그 밖의 실패, 즉 Git을 찾지 못함(ENOENT), 10초 시간 초과, 종료 코드 128(저장소 폴더·`.git`을 읽지 못함, 소유자 확인 거절 등), 경고를 출력한 실패, 저장소 폴더를 찾지 못함은 작업 내용에 대해 아무것도 말하지 않으므로 `git_unavailable`(일시 실패)로 본다. Git은 메시지를 번역하므로 메시지가 아니라 종료 코드와 출력 유무로 판단한다. 저장소의 `.git`을 잠시 읽지 못할 때 바깥 폴더의 다른 저장소를 찾아 `wrong_repository`로 오판하지 않도록 저장소 위쪽 폴더 탐색을 막는다.

- `prepare` 중 일시 실패는 `skipped`가 아니라 **오류**로 끝나고 아무 상태도 저장하지 않는다. 원인을 해결한 뒤 같은 입력으로 다시 `prepare`한다.
- `sync` 중 일시 실패는 제외하지 않는다. 그 기록은 이번 실행에서 전달하지 않고(`--retry-now`여도 확인 전에는 전달하지 않는다) 전달 실패와 같은 1분→5분→15분→1시간 간격으로 다시 확인한다. 아직 재시도 시각이 아닌 기록은 확인만 하고 실패 횟수를 늘리지 않는다. `status`의 `lastError`에 실패 횟수와 사유가 보인다. 확인에 성공하면 횟수와 오류를 지운다.
- 연속 12회(앱을 켜 둔 시간 기준 약 9시간) 실패하면 `git_paused`로 바꾸고 앱을 더 깨우지 않는다(`wake.json`의 대기 수에서 뺀다). 원문과 전달 상태는 그대로이며, 이후 어떤 `sync`든 이 기록을 다시 확인해 Git이 답하면 멈추기 전 단계에서 이어 가고, 커밋이 없는 등 확정된 답이면 그 사유로 `excluded`가 된다. 원인을 해결한 뒤 `node scripts/project-records.mjs sync`를 한 번 실행하면 된다. 영구히 1시간마다 깨우는 대신 멈추는 이유는, 그만큼 계속된 실패는 지나가는 문제가 아니어서 사람이 원인을 봐야 하기 때문이다.
- 0.15.3 이전에는 일시 실패와 커밋 없음·조상 아님이 모두 `git_verification_failed`로 `excluded`가 됐다. 이 기록은 **자동으로 되살리지 않는다.** 같은 사유 안에 정말 근거가 없는 기록이 섞여 있어 사유만으로 구분할 수 없고, 저장된 사용자 기록을 확인 없이 다시 전달하게 되기 때문이다. 필요한 기록은 같은 작업 ID와 원래 입력으로 다시 `prepare`하면 새 수정본으로 다시 확인·전달된다. 0.15.3 작업 시점에 등록된 상태 폴더에는 이 사유로 제외된 기록이 없었다.

최초 전달에서 Node·스크립트·상태 폴더 경로를 앱에 등록한다. 앱은 시작 후 약 1분 간격으로 작은 대기 상태 파일을 확인한다. 전송할 기록이 있을 때만 숨겨진 전달 프로세스를 하나 실행하고 한 번에 한 작업을 처리한다. 실패하면 1분→5분→15분→1시간 간격으로 늘린다. 앱을 닫거나 PC를 끄면 다음 앱 실행 후 재개한다. 접속 복구를 즉시 감지하는 서버 알림은 아니며 다음 재시도 시각에 반영한다.

Node.js는 로컬 문서 저장 명령에 필요하다. 로그인된 Codex CLI와 Pages 연결, GPT-6 Luna medium 모델은 선택적 Space 전달에만 필요하다. 앱의 기본 일정·다이어리 사용에는 Node.js가 필요 없다. API 키를 파일에 저장하지 않으며 CLI 인증·이용 한도는 기존 계정을 따른다.

## 작업 전달

아래 JSON을 `.cache/`에 저장한다. 같은 작업의 후속 수정은 같은 workId, 새로운 작업은 새 UUID를 사용한다. 날짜는 작업의 한국 날짜다.

```json
{
  "workId": "96ebef77-f456-4d3b-b82d-30a92b7da0b5",
  "projectTitle": "TimeSchedule",
  "repoPath": "C:\\LSH\\TimeSchedule",
  "date": "2026-10-31",
  "kind": "development",
  "title": "작업 제목",
  "status": "verification_pending",
  "gitChanges": {
    "base": "작업 시작 시 확보한 전체 커밋 SHA",
    "head": "개발 완료 후 전체 커밋 SHA",
    "paths": ["scripts/project-records.mjs"]
  },
  "detailedMarkdown": "확인한 결과와 아직 확인하지 않은 범위를 함께 쓴다.\n\n## 해결 과정\n\n실제 시도와 근거를 기록한다.",
  "diarySummary": "확인한 결과와 아직 확인하지 않은 범위를 함께 쓴다."
}
```

`kind`: development / troubleshooting / portfolio / summary. `status`: in_progress / verification_pending / verified / completed / merged. `verified`는 기록에 명시한 검증 범위이며 사용자 승인·병합을 의미하지 않는다. 요약은 상세 원문의 완전한 문단을 선택하고, 생략하면 첫 일반 문단을 쓴다. 제한·미확인을 잘라 성과만 남기지 않는다. 상세 원문은 UTF-8 48,000바이트 이하로 나눈다.

```powershell
node scripts/project-records.mjs prepare --input .cache/project-record-input.json
node scripts/project-records.mjs sync
node scripts/project-records.mjs status
```

`prepare`가 통과하면 전달 자료 준비에 그치므로 `sync`까지 실행한다. `skipped`라면 거기서 종료하고 요약 모델이나 외부 전달을 호출하지 않는다. `sync --work-id UUID`는 한 작업, `--retry-now`는 대기 시간을 생략한 명시적 재시도이며 개발 변경 조건은 생략하지 않는다. 앱은 `--max-jobs 1`로 한 번에 하나만 처리한다. 전송 중에도 앱의 편집과 inbox 수신은 독립적으로 진행된다.

테스트에서는 `--state-dir DIR --data-dir DIR --exe FILE`로 격리한다. 별도 CLI 설치는 `--codex-exe FILE` 또는 `TIMESCHEDULE_CODEX_EXE`로 지정한다. 인증정보와 본문을 셸 명령 문자열에 끼워 넣지 않는다.

## 상태와 보존

| 상태 | 의미 |
|---|---|
| prepared | 원문 준비. 로컬 문서와 다이어리 저장 확인 전이다. |
| diary_queued | 앱 수신 큐에 접수됐다. 편집·저장이 끝난 안전한 시점에 반영된다. |
| waiting_space | 다이어리에 원문이 저장됐고 Space 연결을 기다린다. |
| publishing | 게시 중이거나 생성 결과 불확실. 불확실한 경우 기존 페이지만 확인한다. |
| waiting_prior | 같은 작업의 앞선 수정본 처리를 기다린다. |
| space_saved | Space를 확인했으며 다이어리 링크 연결을 기다린다. |
| complete | Space 검증과 다이어리 링크 연결까지 확인했다. |
| local_complete | 원문 파일 저장과 다이어리 반영 완료. Space를 기다리는 상태가 아니다. |
| conflict | 사용자 편집·삭제 등 충돌을 보존하며 자동 처리를 중단했다. |
| git_paused | Git 확인이 연속 12회 일시 실패해 자동 재시도를 멈췄다. 앱을 깨우지 않으며, 다음 `sync`가 다시 확인해 이어 가거나 확정된 사유로 제외한다. |
| excluded | 개발 변경 근거가 없음을 Git이 확정해 전달에서 제외했다. 기존 원문·게시 관측·오류는 보존하며 재시도하지 않는다. |

`status`의 `vaultSaved`와 `localFile`은 원문 파일 저장 여부와 위치다. 파일 저장 후 다이어리 실행·등록에 실패하면 파일은 남고 다이어리 반영은 재시도한다. 같은 작업의 새 수정이 대기 중 들어오면 앞선 상태를 `pending-<revision>.json`으로 보존한다. 다른 작업은 하나의 실패 때문에 막히지 않는다. 로컬 저장과 링크 연결은 각각 증가하는 전달 revision을 사용한다. 이미 다이어리나 문서 저장소에 더 최신 수정본이 있으면 이전 전달이 덮어쓰지 않는다. 문서·다이어리의 수동 편집은 자동 왕복 동기화하지 않으며 충돌을 보존한다.

앱이 닫혀 있으면 CLI가 동일 코어로 저장하고, 열려 있으면 `record-inbox`에 접수한다. 앱은 시작 시 및 약 60초 간격으로 처리하되 편집·다른 저장 중에는 미룬다. 결과는 `record-receipts`, 손상된 입력은 `record-failed`에 보관한다. Windows 결과 파일이 신뢰 가능한 확인 수단이며 콘솔 출력은 보이지 않을 수 있다.

Space 제목·전체 본문·위치·URL·부모 링크를 실제 Pages 읽기 결과로 검사한다. 모델의 완료 선언만으로 성공 처리하지 않는다. 원문 차이가 있으면 전달을 보류한다. 연결 실패 전에 게시를 시작하지 않았다는 실행 결과가 확인되면 정상 재시도한다. 생성 여부가 불확실하면 새 페이지로 우회하지 않는다. 사용자 편집·삭제는 자동 덮어쓰기·복구하지 않는다.

전달 상태·원문·로그는 Git에 넣지 않는 `.cache/project-records`에 보관한다. 다이어리와 별도로 재시도·매핑에 필요한 파일이므로 대기 작업이 있을 때 지우지 않는다. Windows named pipe 잠금으로 동시 실행을 막고 앱 소유 프로세스는 실행 시간 제한과 종료 시 정리를 적용한다. 원문 로그를 외부 공유하거나 인증정보·개인 일정·메모를 넣지 않는다.
