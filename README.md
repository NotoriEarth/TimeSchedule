# TimeSchedule

## 최신 앱 · TimeSchedule 0.39.0

0.39.0은 **프로젝트 화면 위쪽을 정리했습니다.** 화면 안의 작은 프로젝트 목록 대신 버튼 줄 맨 앞의 선택 상자로 프로젝트를 고릅니다. 프로젝트 맨 위에는 설명과 ‘프로젝트 수정’, 그리고 Git 저장소 연결 여부와 채팅 자동 수집 상태(‘켜기’·‘끄기’ 버튼)가 한눈에 보입니다.

0.38.0은 **설정 화면을 네 영역으로 나눴습니다.** 설정 제목 아래의 ‘일반’, ‘기록과 하루 정리’, ‘바탕화면 위젯’, ‘AI 연결 (MCP)’ 버튼으로 영역을 고르면 그 영역만 보입니다. 위젯의 ‘설정’ 버튼은 바로 ‘바탕화면 위젯’ 영역을 열고, 배경 불투명도는 위젯 색상 옆으로 옮겼습니다. ‘AI 연결 (MCP)’의 인증 토큰과 연결 도우미는 ‘고급’ 안에 접어 두고 필요할 때 저절로 펼치며, 화면 모드는 ‘어두운 모드’·‘밝은 모드’ 두 버튼으로 고릅니다.

0.37.1은 **프로젝트·설정 화면을 조금 정리했습니다.** ‘오늘’ 버튼은 월간·주간에만 보이고, 왼쪽의 프로젝트 바로가기는 개수 제한 없이 모두 보이며 열린 프로젝트가 강조됩니다. 프로젝트 화면의 ‘근거 요약’·‘자료 발췌 초안’과 ‘채팅에서 경험 검토’는 작업 중에도 사라지지 않고 잠시 막히며, 저장소·채팅·기록이 없을 때는 그 이유를 한 줄로 알려 줍니다. 날짜 제목에 요일이 붙고, 설정 화면의 소제목 크기와 영역 간격을 맞췄습니다.

0.37.0은 **프로젝트의 지난 대화를 한꺼번에 정리합니다.** 프로젝트 화면에서 채팅 자동 수집을 켜면, 그 폴더에서 이미 나눈 대화가 며칠 치인지 먼저 세어 묻고, ‘지금 모두 정리’를 누르면 날마다 하루 정리를 만듭니다. 모델은 하루에 한 번 부르고, 묻기 전에는 부르지 않습니다. ‘정리 멈추기’로 멈출 수 있고, 나중에는 같은 자리의 ‘지난 대화 정리’ 버튼으로 다시 할 수 있습니다. 프로젝트 편집기의 저장소 경로에는 **‘폴더 찾기’ 버튼**이 생겼습니다.

0.36.0은 **앱에서 하루 정리를 만듭니다.** 설정의 ‘하루 정리 만드는 방식’에서 고릅니다. ‘버튼으로 만들기’(기본)는 월간 다이어리에서 날짜를 고르고 ‘하루 정리 만들기’를 누를 때만 만들고, ‘자동으로 만들기’는 앱을 켤 때와 한 시간마다 최근 7일 가운데 끝난 날을 만듭니다. 대화가 바뀌지 않은 날은 모델을 다시 부르지 않습니다. 자동으로 처음 바꾸면 기록이 없는 날마다 모델을 한 번씩 부릅니다(프로젝트마다 최대 7번). 실패한 날은 대화가 바뀌거나 앱을 다시 켤 때까지 다시 부르지 않습니다.

0.35.0은 **하루 정리를 읽기 쉽게 다시 짰습니다.** 하루 기록은 이제 "오늘 한 일" 한 문단, 개발 내역, 트러블슈팅, 결정, "남은 일" 순서로 보입니다. 근거가 있는 칸만 나옵니다. 모델에 주는 지시문을 판 4로 바꿔 며칠 뒤의 내가 1분 안에 읽을 수 있게 쓰도록 했습니다. 예전에 만든 하루 기록도 새 칸 제목으로 보입니다. 지시문 판이 바뀌었으므로 이미 기록이 있는 날도 `record daily`를 다시 실행하면 모델을 다시 부릅니다.

0.34.1은 **다이어리에 사람이 읽을 글만 보여 줍니다.** 하루 정리에서 근거 블록 번호, 인용 글귀, 확인 규칙의 메모, 판·모델 줄을 빼고, 새로 남는 개발 일지에서 테스트 실행 기록, 검증 문단, 커밋 해시를 뺐습니다. 뺀 내용은 문서 저장소의 원문과 전달한 기록에 남아 있고, 항목 시간표의 커밋과 본문을 고치지 않은 항목의 포트폴리오 근거로도 그대로 쓰입니다. 이미 보인 하루 정리는 다음 수집 때 새 형식으로 바뀌고, 직접 고친 항목은 그대로입니다. 이미 들어간 개발 일지도 그대로이며, 고치지 않은 항목은 같은 작업을 다시 기록할 때 새 본문으로 바뀝니다.

0.34.0은 **하루 정리를 만듭니다.** `TimeSchedule.exe record daily --project <프로젝트 폴더> --date <날짜>`를 실행하면 그날 보관된 채팅 원문에서 사람과 AI가 한 말, 다른 세션이 보낸 지시, 에이전트 실행의 마지막 답, 실패한 명령의 종료 코드와 진단 줄만 골라 로그인한 Codex CLI의 모델(기본 GPT-6.1 Terra)에 한 번 보내고, 요약·개발 내역·트러블슈팅·개선 방향·결정을 담은 하루 기록을 문서 저장소의 `daily` 폴더에 남깁니다. 결정마다 누가 제안하고 누가 정했는지를 원문 글귀로 확인한 만큼만 적습니다. 앱은 다음 채팅 수집 때 이 기록을 다이어리에 "하루 정리 · 날짜"로 보여 주며, 본문을 고쳤거나 다른 날짜·프로젝트로 옮겼거나 지운 항목은 건드리지 않습니다(제목이나 종류만 고친 항목은 그 값을 두고 본문을 새 판으로 바꿉니다). 형식 15 이하로 쓰던 DB는 형식 16으로 올리기 전에 `schedule.pre-v16-<UUID>.db`로 백업합니다. 0.33.1 이하 배포판은 이 DB를 열지 않습니다. 하루 대화록에는 사람이 채팅에 친 글이 그대로 들어가 모델 제공자에게 갑니다. [하루 정리](docs/daily-record.md)를 참고하세요.

0.33.1은 프로젝트 화면의 **‘Git 커밋 수집’ 버튼을 없앴습니다.** 이미 가져온 커밋 기록은 그대로 남습니다.

0.33.0은 **채팅 원문을 보관합니다.** 채팅 수집을 켠 프로젝트의 Codex·Claude Code 세션 파일을 문서 저장소의 `originals` 폴더에 압축해 둡니다. 도구가 세션 파일을 지워도 보관본은 남습니다. 수집은 앱을 켤 때, 프로젝트 화면을 열 때, 켜 둔 동안 한 시간마다 돕니다. 보관본에는 채팅에 붙여 넣은 내용과 명령 출력이 그대로 들어 있습니다. [채팅 원문 보관](docs/chat-originals.md)을 참고하세요.

0.32.0은 **Space 게시를 없앴습니다.** 자동 개발 기록은 문서 저장소에 원문을 저장하고 다이어리에 반영하면 끝납니다. 모델 호출과 Codex 로그인이 필요 없습니다. 이미 게시된 Space 페이지와 그 링크가 붙은 다이어리 항목은 그대로 둡니다. 이전 버전이 남긴 기록 상태는 손으로 옮기지 않아도 됩니다. 아래 이전 버전 설명에 나오는 Space 연결과 `config --space`는 더 이상 없습니다. [자동 개발 기록](docs/project-records.md)의 "Space 게시 제거"를 참고하세요.

백엔드 포트폴리오에서 **원문 행 링크**를 열면 함께 저장된 `evidence.md`의 해당 발췌로 이동합니다. 처음 검토한 경험의 인용도 연결된 채팅에서 발화 유형과 행 번호가 일치하면 자동으로 링크됩니다.

**프로젝트 → TimeSchedule → 채팅에서 경험 검토**에서 수집된 채팅을 고르면, 해당 채팅의 발췌를 로그인한 Codex CLI를 통해 GPT-6.1 Terra(medium)에 보냅니다. 모델은 원문 근거와 함께 설계 및 트러블슈팅 후보를 각각 최대 한 건 제시합니다. Codex CLI와 네트워크 연결이 필요합니다. MCP가 꺼져 있어도 동작합니다. 모델 호출 실패 시 오류를 표시합니다. 원문 행 번호와 검증 한계를 읽고 저장할 후보를 체크하세요. 같은 채팅과 종류의 확인 항목은 기존 이력에 연결하며 새로 확인한 인용만 추가합니다. 같은 경험으로 포트폴리오를 생성하면 갱신된 근거의 원문 행 링크와 이전 편집을 담은 새 판본을 저장합니다. 개인 기여 답변을 유지합니다. 생성 버튼 옆에서 새 판본 생성과 기존 판본 재사용 결과를 확인할 수 있습니다.

**프로젝트 → 프로젝트 선택 상자에서 프로젝트 → 정보 줄의 ‘채팅 자동 수집’ 옆 ‘켜기’**(Codex·Claude Code 채팅)를 누르면, 앱이 시작할 때, 프로젝트 화면을 열 때, 실행 중 한 시간마다 해당 저장소의 Windows Codex Desktop 및 Claude Code CLI 채팅을 프로젝트 이력에 반영합니다. 커밋과 MCP 연결 없이 동작합니다. 채팅 제목, 사용자 요청, AI 답변, TAP 검사 출력, 실패 명령의 종료 코드와 선별한 진단 문구, 서비스 상태 출력(예: 연결 수락·거부)과 원문 파일·행 번호를 로컬 메모로 보관합니다. 긴 대화는 발췌하며, 같은 채팅의 새 내용은 기존 항목을 갱신합니다. 사용자가 편집하거나 삭제한 내용은 보존합니다. 첫 실행 시 기존 DB를 `schedule.pre-v16-<UUID>.db`에 백업합니다.

0.30.1에서 Codex 수집을 켜 둔 프로젝트는 기존 범위를 유지합니다. Claude Code CLI도 수집하려면 그 프로젝트에서 수집을 껐다가 다시 켜세요. Claude의 로컬 세션에서 사용자 요청, AI 응답, Bash 실행에 연결된 진단·상태 출력을 읽습니다. 재개한 대화는 같은 이력에 이어지며, 두 도구 모두 같은 경험 검토와 포트폴리오 생성을 사용합니다.


**설정 → AI 연결 (MCP)**에서 MCP를 끄거나 다시 켤 수 있습니다. 끄면 Claude Desktop이 이미 열어 둔 중계가 종료됩니다. 꺼둔 채 Claude를 다시 열어도 중계가 남지 않으므로, TimeSchedule을 완전히 종료한 뒤 EXE를 교체할 수 있습니다. 다시 쓰려면 **MCP 켜기**를 누르고 Claude에서 재연결하세요.

**프로젝트 → 프로젝트 선택**에서 설계 경험·개발 기록·트러블슈팅이 날짜별 이력에 쌓이고, 포트폴리오에 쓸 경험 수를 볼 수 있습니다. 직접 쓴 기록과 자동 수신 기록 모두 대상입니다. 개발 일지 `finish` 입력에 `kind`를 생략하면 개발 기록으로 저장하고, `design` 또는 `troubleshooting`도 지정할 수 있습니다.

1. 프로젝트에 설계 경험이나 트러블슈팅을 저장합니다. 본문에 `## 설계`, `## 검증`처럼 제목을 쓰거나 `실패 복구: 같은 작업을 재시도했다.`처럼 근거를 남길 수 있습니다.
2. **경험 선택**에서 원하는 항목을 체크합니다. 전체를 쓰려면 **전체 경험 사용**을 누릅니다. 마지막으로 생성한 선택은 다음 실행에도 표시됩니다.
3. 직접 맡은 역할이 빠진 경험이 있으면 프로젝트 화면에서 공통 역할에 답하거나 **개인 기여 보류**를 선택합니다. 답변과 보류는 재시작 후에도 유지되며 **답변 수정**에서 바꿀 수 있습니다.
4. **백엔드 포트폴리오 · Markdown 생성**을 누르면 선택한 경험 본문·제목과 프로젝트 이름·역할 답변을 로그인한 Codex의 GPT-6.1 Terra(medium)에 보내 작성합니다. 같은 입력은 기존 판본을 재사용합니다. 이전 버전의 동일 선택에 편집본이 있으면 새 판본에 해당 본문과 Terra 요약을 함께 보관합니다. 생성 뒤 **마지막 Markdown 열기**로 결과를 엽니다. 생성된 폴더의 `portfolio.md`와 `evidence.md`를 함께 보관하면 경험별 근거 링크가 유지됩니다. 파일을 직접 편집한 뒤 같은 입력으로 다시 생성해도 편집본을 보존합니다. 근거 또는 답변이 달라지면 다음 판본을 별도 폴더에 저장합니다.

본문에 명시한 배경·문제, 목표·성공 기준, 개인 역할·기여, 기술 선택·설계, 주요 구현, 문제 해결, 검증·성과, 근거, 협업·의사결정, 회고·개선과 프로젝트의 자동 처리 범위, 사람이 개입하는 조건, 실패 복구를 사용합니다. 자유 형식 기록은 저장된 요약 또는 첫 문단과 전체 근거로 연결합니다. 기준에 따른 원문 정리와 Markdown 근거 링크 연결은 로컬에서 실행됩니다. 0.21.0에서 포트폴리오용 DB 스키마 8을 도입했습니다.

0.20.0은 **프로젝트 기록이 언제, 어떤 커밋으로 이루어졌는지** 보여 줍니다. 달력에는 한 프로젝트의 하루 기록이 `TimeSchedule + 3`처럼 프로젝트명과 건수만 보이고, 카드와 상세에서 작업 시작·완료 일시(또는 현재 상태)·관련 커밋의 한국시간 일시·짧은 해시·제목을 봅니다. 자동 기록은 `원본 열기`로 문서 저장소의 원문을 엽니다. 직접 쓰는 기록에는 `기록 시각`(24시간제 `HH:mm`)을 넣을 수 있고, 비우면 `미상`입니다. 프로젝트 화면은 같은 기록을 최신 날짜부터 날짜별로 묶어 보여 줍니다. **DB 스키마가 7로 바뀌므로 처음 실행할 때 `schedule.pre-v7-<UUID>.db` 백업을 만들고, 이후 이전 버전 앱은 이 DB를 열 수 없습니다.** [변경 내용](CHANGELOG.md)

네이티브 기본 저장 폴더는 `%LOCALAPPDATA%\com.timeschedule.personal.native-experiment`, 파일은 `schedule.db`입니다. 기존 앱의 DB를 자동으로 가져오지 않습니다. `TIMESCHEDULE_DATA_DIR`로 별도 테스트 폴더를 지정할 수 있습니다. 기존 DB의 호환성 확인에는 원본 대신 일관되게 백업한 복사본을 사용하세요.

PR #2–#6의 Rust 이식·테마·위젯·편집·설정·연월 선택 변경은 사용자 승인 후 main에 병합했습니다. 기존 Tauri/Svelte 소스와 빌드 경로도 보존합니다. 두 앱은 공통 SQLite/Git 코어를 사용합니다.

최신 앱에는 날짜 더블클릭 편집, 완료 체크, 배경 전용 투명도, 크기·표시 주 수·글꼴·색상 설정, Windows식 연도→월 선택, 위젯과 다이어리 공통 일정 폼이 포함됩니다.

0.8.1은 작업 시작·완료 커밋과 해당 작업의 변경 파일을 로컬 Git으로 확인한 뒤, 기존 대화의 개발 요약·상세 원문을 다이어리에 보관하고 Space에 연결합니다. 소스·테스트·빌드/설정 변경이 없는 후보는 로컬 저장과 모델 호출을 건너뜁니다. 연결 실패 중에도 개발 기록 원문은 남으며, 앱 실행 중 유효한 대기 기록만 재시도해 복구 후 같은 항목에 링크를 붙입니다. 별도 오전 9시 포트폴리오 자동화는 중지했습니다. Space 내용은 PR 작성에 유용할 때만 재사용합니다. 기록용 CLI는 GPT-6 Luna medium과 원문 검증을 사용합니다. 사용자 편집을 보존하고 편집 중에는 외부 기록 수신을 미룹니다. 외부 전달에는 Git·Node.js와 로그인된 Codex CLI·Pages 연결이 필요합니다.

기존 수동 테스트 EXE는 `artifacts/archive/`에 보관합니다. 앞으로 빌드할 때도 `TimeSchedule.exe`를 교체하고 이전 파일은 보관하므로 실행할 파일 이름은 늘어나지 않습니다. 실행 중이면 저장 후 트레이에서 완전히 종료하고 빌드하세요. 빌드나 버전 검증 실패 시 기존 EXE를 교체하지 않습니다. 의존성이 준비된 환경에서는 `scripts/build-native.ps1 -Offline`을 사용할 수 있습니다.

[선택창 테스트 안내](docs/calendar-picker-verification.md), [공통 폼 안내](docs/diary-navigation-verification.md), [설정 안내](docs/widget-customization-verification.md)는 당시 검증 기록입니다. 그 안의 이전 파일명 대신 현재 `artifacts/TimeSchedule.exe`로 확인하세요.

[네이티브 기능 대조](docs/rust-native/full-port.md)와 [20회 비교 벤치마크](docs/rust-native/benchmark.md)도 보존합니다. 기본 월간 상세창+위젯 유휴 상태에서 전용 상주 RAM은 약 90% 줄었지만 유휴 CPU는 늘었습니다. 수치는 당시 빌드의 측정 결과이며 이번 버전을 다시 측정한 결과가 아닙니다. 아래 설명과 과거 메모리 표는 기존 Tauri 버전 기준입니다.

## 자동 검사 (CI)

GitHub의 모든 PR과 `main` 푸시에서 Windows 환경으로 다음을 자동 실행합니다. Rust 버전은 개발에 쓰는 1.99.1로 고정합니다.

- **CI** (`.github/workflows/ci.yml`): 두 작업을 동시에 실행합니다. *Format and lint*는 `cargo fmt` 검사와 `cargo clippy`(지금은 경고 보고만 하고 실패시키지 않음), *Tests*는 워크스페이스 전체 테스트(`desktop_native` 통합 테스트 포함), PowerShell 스크립트 테스트 2개(메모리 측정·실행 파일 교체), 방금 빌드한 실행 파일을 쓰는 Node 기록·문서 저장소 테스트입니다. 저장소 최상위 Markdown과 `docs/`만 바뀐 변경은 실행하지 않습니다(vendor 크레이트는 README를 코드에 포함하므로 그 밖의 Markdown 변경은 실행). 테스트에는 디버그 정보가 필요 없어 꺼서 컴파일을 줄입니다.
- **Legacy builds** (`.github/workflows/legacy.yml`): 공통 크레이트·Tauri·프런트엔드·실험 코드가 바뀐 PR에서만, 워크스페이스 밖의 기존 Tauri 앱과 UI 실험 크레이트가 계속 컴파일되는지 확인합니다.

GitHub 공식 액션만 쓰고 커밋 SHA로 고정합니다. `build.rs`가 Windows SDK의 `rc.exe`를 쓰므로 CI도 로컬의 `scripts/toolchain.ps1`처럼 Visual Studio 개발자 환경을 먼저 불러옵니다(`.github/actions/msvc-env`). `scripts/tests/benchmark-archive.tests.ps1`과 `benchmark-fixtures.tests.ps1`은 Git에 없는 로컬 벤치마크 산출물과 `.tooling`이 필요한 수동 검사라 자동 검사에서 제외합니다. 실제 바탕화면 위젯 연결, 사용자 AI 앱 연결, 화면 체감은 여전히 사용자 확인 대상입니다.

## 기존 Tauri 앱


오늘의 일정과 작은 할 일을 정리하는 Windows용 개인 달력 프로토타입입니다. Tauri 2, Svelte 5, TypeScript, Rust, SQLite로 구성하며, 계정이나 서버 없이 내 컴퓨터에 데이터를 저장합니다.

2026-10-29 다이어리 개발 브랜치에서는 **상세 창을 주 화면인 만년 다이어리**로 구성했습니다. 월간 달력의 일요일 앞 주간 버튼은 그 다음 월요일부터 다음 일요일까지 열며, **월간으로** 버튼으로 원래 보던 월에 돌아옵니다. 날짜를 누르면 해당 날짜의 일정 편집창이 열립니다. 주간 기록은 제목을 펼쳐 본문과 출처를 보고, 필요한 만큼 추가할 수 있습니다.

프로젝트별 자유 노트·트러블슈팅·개발 기록, 로컬 Git 커밋 가져오기, 편집 가능한 근거 요약과 포트폴리오 초안을 제공합니다. Git은 프로젝트의 저장소 경로에서 **Git 커밋 수집**을 눌러 최근 500개를 가져옵니다. 재수집은 기존 기록과 사용자가 수정한 내용을 보존합니다. 요약은 저장된 자료를 정리한 **로컬 초안**이며 외부 AI 분석 결과가 아닙니다. ChatGPT 공부 내역·Space 연동, 자동 수집 주기, 기기 간 동기화는 아직 연결하지 않았습니다.

전체 검색은 일정·할 일·메모·프로젝트·개발 기록의 제목과 본문을 찾습니다. SQLite FTS5 인덱스(3글자 이상), 짧은 검색어의 문자 검색(최신 항목부터 확인), 최대 50개 결과와 입력 대기를 사용하며 별도 읽기 연결에서 실행합니다([검색 성능 측정](docs/search-performance.md)). 기록 목록은 200개씩 불러오고 본문은 펼칠 때 읽습니다. 이 변경의 메모리 절감량은 아직 측정하지 않았으며 아래 과거 수치와 구분해야 합니다. 당시 테스트 실행 파일은 보관 폴더로 이동했습니다. [직접 확인할 절차](docs/diary-verification.md)를 참고하세요.

현재 사용할 수 있는 기능은 다음과 같습니다.

- 한국어 월간 달력, 오늘 강조 표시, 선택한 날짜의 일정 목록
- 일정 추가·수정·삭제, 하루 종일 또는 시작·종료 시간, 색상, 메모, 완료 표시
- 날짜를 지정할 수 있는 할 일과 별도의 메모 관리
- 날짜 칸마다 일정이 보이는 넓은 바탕화면 월간 달력과 오늘 일정 요약
- 상단의 **이동하기 / 위치 고정**, 넓은 제목 영역을 끌어 위치 이동
- **불투명도 40~100% 조절**과 설정 저장 (기본 82%)
- 위젯에서 날짜를 눌러 관리 창 열기, 저장 후 두 창의 데이터 갱신
- 트레이에서 관리 창 열기, 위젯 표시·숨기기, 완전 종료

관리 창의 닫기 버튼은 앱을 완전히 종료하지 않습니다. 관리 창과 그 WebView를 해제하고 트레이에 남으며, 다시 열면 저장된 데이터를 불러옵니다. 앱을 끝내려면 트레이 메뉴의 **완전 종료**를 선택하세요.

0.1.2에서는 실행 중 해상도·배율이 바뀌거나 모니터가 분리되어 위젯이 화면 밖으로 나가면, 위젯의 위치와 크기를 현재 모니터 작업 영역 안으로 자동 보정합니다. 위치 고정 상태에서도 보정하며 잠금과 불투명도는 유지합니다. 드래그 중에는 개입하지 않고, 창의 메시지 처리가 가능한 상태에서 약 1초 간격으로 검사합니다. 버튼에 접근할 수 없으면 관리 창의 **위젯 위치 복구** 또는 트레이의 **바탕화면 달력 위치 복구**를 사용하세요. 자동 보정은 기존 창을 화면 안에 맞추며 Explorer 재시작으로 파괴된 창을 자동 재생성하는 기능은 아닙니다.

0.1.1에서는 작은 카드 대신 최대 900×560 논리 픽셀의 월간 달력을 표시합니다. 화면이 작으면 자동으로 줄이고, 기존 위치가 화면 밖으로 나가면 안쪽으로 보정합니다. **이동하기**를 누른 뒤 상단 제목 또는 안내 영역을 끌고, 배치를 마치면 **위치 고정**을 누르세요. 이미 **위치 고정** 버튼이 보이면 이동할 수 있는 상태입니다. 하단의 **불투명도**를 낮출수록 바탕화면 배경이 더 비칩니다. 현재는 창 전체를 반투명하게 처리하므로 글자도 함께 조금 옅어집니다. 배경만 투명하게 하거나 흐리게 만드는 방식은 아닙니다.

바탕화면 위젯은 Windows 10의 Explorer 바탕화면 호스트에 연결하는 실험 기능입니다. 일반 창을 최소화해도 바탕화면에 남고 다른 앱보다 앞에 뜨지 않는 동작을 목표로 합니다. 연결 상태를 앱에 표시하며, 지원하지 않는 환경에서는 연결 실패를 알립니다. 2026-10-28 현재 PC에서 0.1.0의 관리자 창과 Win+D 이후 달력 표시, 0.1.1 수정본의 배경 비침과 상단 드래그 이동을 사용자가 확인했습니다. 0.1.2 적용 후에는 가려졌던 위젯 제어 버튼이 다시 보이는 것을 사용자가 확인했습니다. Windows 11 및 다른 Explorer 구성에서의 동작은 별도 확인이 필요합니다.

이 저장소에는 소스와 빌드 방법을 포함합니다. 실행 파일과 개인 데이터는 Git으로 관리하지 않습니다. 아래 Tauri 빌드 결과는 `src-tauri/target/release/timeschedule.exe`입니다. 대표 네이티브 EXE와 구분해 사용하세요. 2026-10-28의 0.1.2 빌드 크기는 7,607,296바이트(7.25MiB)입니다. 실행 환경에는 Microsoft Edge WebView2 Runtime이 필요합니다. Rust, Cargo, Microsoft C++ Build Tools는 소스 빌드에 사용하는 도구이며, 사용자가 실행 파일을 실행하기 위해 함께 배포하는 앱 구성 요소가 아닙니다. 현재는 앱을 한 번만 실행하세요. 중복 실행 방지는 아직 포함하지 않습니다.

소스에서 실행하거나 빌드할 때는 프로젝트 루트의 PowerShell에서 아래 명령을 사용합니다. Node.js와 npm이 필요하며, 먼저 프런트엔드 의존성을 설치합니다.

```powershell
npm.cmd ci
```

이 작업 공간의 Rust 및 C++ 빌드 도구는 `.tooling`에 구성되어 있습니다. `scripts/toolchain.ps1`은 현재 PowerShell 세션에 해당 도구의 환경 변수를 설정합니다. 새 작업 공간에서 도구를 준비할 때는 `scripts/install-rust.ps1`, `scripts/install-buildtools.ps1`을 참고하세요. `.tooling`은 컴파일러와 빌드 의존성 보관 폴더이며, 앱의 실행 시 메모리 사용량이나 배포 크기를 의미하지 않습니다.

네이티브 개발 모드로 실행하려면:

```powershell
. .\scripts\toolchain.ps1
npm.cmd run tauri dev
```

릴리스 빌드는 다음과 같습니다. `build.ps1`은 프런트엔드 타입 검사와 프런트엔드·네이티브 빌드를 실행합니다. 설치 프로그램은 만들지 않으며 대표 네이티브 EXE를 덮어쓰지 않습니다.

```powershell
.\scripts\build.ps1
.\src-tauri\target\release\timeschedule.exe
```

디버그 빌드는 `scripts/build.ps1 -DebugBuild`를 사용합니다. 이때 원본 실행 파일은 `src-tauri/target/debug/timeschedule.exe`에 생성됩니다.

기존 Tauri 앱의 기본 저장 위치는 Tauri의 `app_data_dir()`이 반환하는 `com.timeschedule.personal` 앱 데이터 폴더입니다. Windows에서는 보통 `%APPDATA%\com.timeschedule.personal`이며, 앱의 **내 컴퓨터에 저장** 정보에서 실제 경로를 확인할 수 있습니다.

| 파일 | 내용 |
| --- | --- |
| `schedule.db` | 일정, 할 일, 메모를 저장하는 SQLite 데이터베이스 |
| `preferences.json` | 위젯 위치, 위치 잠금, 표시 설정 |
| `preferences.invalid.json` | (네이티브 앱) 잘못된 값이 있어 고치기 전의 설정 파일 사본. 없을 수 있으며 지워도 됩니다 |
| `prototype.log` | 바탕화면 연결 및 오류 진단 기록 |

앱 실행 중에는 SQLite 보조 파일인 `schedule.db-wal`, `schedule.db-shm`이 함께 생길 수 있습니다. 백업하려면 트레이에서 완전 종료한 뒤 저장 폴더를 복사하세요.

테스트 데이터를 별도 폴더에 저장하려면 실행 전에 `TIMESCHEDULE_DATA_DIR`을 지정합니다. 앱이 지정한 폴더를 생성하고 사용합니다.

```powershell
$env:TIMESCHEDULE_DATA_DIR = Join-Path $PWD '.test-data'
.\src-tauri\target\release\timeschedule.exe
```

다음 실행부터 기본 저장 위치로 돌아가려면 앱을 완전히 종료한 후 같은 PowerShell에서 `$env:TIMESCHEDULE_DATA_DIR = $null`로 지웁니다.

브라우저에서 화면만 확인하려면 `npm.cmd run dev`를 실행하고 `http://127.0.0.1:1420`을 엽니다. 브라우저 미리보기는 해당 브라우저의 **localStorage**에 저장합니다. 네이티브 앱의 **SQLite와 데이터를 공유하거나 동기화하지 않으며**, 브라우저의 위젯 미리보기도 실제 바탕화면 연결 기능을 제공하지 않습니다.

현재 확인된 검증 결과는 다음과 같습니다.

| 검증 항목 | 상태 |

자동화 도구가 이 PC의 네이티브 창 캡처와 좌표 클릭을 수행하지 못해 마지막 행은 검증 완료로 표시하지 않습니다. 표시·반투명·이동 여부는 사용자의 직접 확인을 근거로 기록했습니다. 관리자 화면의 접근성 트리와 기본 데이터 로드는 확인했으며, 브라우저 미리보기에서는 일정 생성·저장과 새 위젯의 월 이동·불투명도 조절을 확인했습니다. [새 달력 미리보기](docs/images/desktop-calendar-preview.png)는 브라우저 화면으로 실제 바탕화면 캡처가 아닙니다.

아래 표는 빈 데이터로 실행한 Windows 10 Pro 22H2, 화면 배율 200% 환경의 메모리 측정입니다. 앱 본체와 그 WebView2 자식 프로세스를 모두 포함합니다. 버전과 열린 창 상태를 구분해 읽어야 합니다.

0.1.1 측정 원본은 로컬 전용 파일 `artifacts/memory-0.1.1-manager-and-widget.json`이며 저장소에 포함하지 않습니다. 넓은 반투명 창으로 바꾸면서 전용 커밋이 늘었으며, 0.1.1의 위젯 단독 상태는 아직 별도 측정하지 않았습니다.

전체 작업 집합 합계는 공유 페이지를 중복 계산하므로 앱만의 실제 추가 메모리와 같지 않습니다. 전용 커밋도 현재 RAM 상주량과 다릅니다. 수치는 이 PC에서 한 번 측정한 기준점이며, OS·WebView2 버전·일정 개수에 따라 달라집니다. 작은 실행 파일 크기만으로 메모리 최적화가 끝났다고 판단하지 않습니다. 0.1.0 원본 결과도 로컬 전용 파일 `artifacts/memory-manager-and-widget.json`, `artifacts/memory-widget-only.json`에 있으며 저장소에 포함하지 않습니다. 실행 중인 앱의 프로세스 ID를 지정해 다시 측정할 수 있습니다.

```powershell
.\scripts\measure-memory.ps1 -AppProcessId <TimeSchedule의_프로세스_ID> -ExpectedExecutablePath <실행한_EXE의_절대경로>
```

저장소 테스트는 재실행 후 데이터 유지, 날짜 범위의 양 끝 포함, 잘못된 날짜·시간·색상 거부, 일정·할 일·메모 수정과 삭제, 실패한 수정의 기존 데이터 보존 등을 확인합니다. 직접 검사하려면:
